# テスト方針

棒人間ダンシングのテストの種類・合格基準・運用を定める。他のコマンド・エージェントが章番号で参照しているので、**章番号は変えない**。

## 1. テストの種類と範囲

本プロジェクトのテストは、**単体テスト**・**結合テスト**・**システムテスト**の3種類とする。単体テストは区分を分けず、Vitestで1種類として実装する。

| 種類          | 区分         | 対象                       | 方法                                                        | 実施者           | 正本                               |
| ----------- | ---------- | ------------------------ | --------------------------------------------------------- | ------------- | -------------------------------- |
| **単体テスト**   | 単体テスト | `src/core`（踊りの物理・ループ・分身・記録）、`src/music`（記録 → 鳴らす音の並び）、`src/share`（記録 ⇔ URL） | Vitest（`src/**/*.test.ts`）。時刻（何刻み目か・音の時計の秒）とキー入力は引数で渡す（→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 6章、[技術選定の設計方針](../02_基本設計/設計方針/技術選定の設計方針.md) 3.1・3.2） | AI（開発者がレビュー）  | テストコード                           |
| **結合テスト**   | E2Eテスト     | 開発サーバーで起動したアプリの画面の流れ（トップ・踊る・鑑賞・共有を開いた画面。画面の構成は基本設計で決める）と、共有URLを開いたときの再生 | Playwright（TypeScript）による自動E2Eテスト。PCのChrome（Desktop Chrome）だけで実行し、全ケースでスクリーンショット証跡を自動取得する | AI（開発者がレビュー）  | テストコード（`e2e/tests/`）と画面ごとのテスト観点表 |
| **システムテスト** | リリース前確認    | 本番と同じビルドを、PCのChromeで実際に遊び、**音を耳で聞いて**確かめる通しのプレイ | リリース前に人が実際に遊んで聞き、確認内容と不良を報告書にまとめる（スクリーンショットは取得しない）              | 人間（開発者） | システムテスト報告書                       |

- **単体テスト**は基本的にAIに実装させ、人がレビューする。テスト内容はドキュメントに残さず、テストコードとテスト名（`describe`・`it` の文言）・コメントで意図が読み取れるようにする。
- **結合テスト**はPlaywrightによるE2Eテストとして自動化する。テストの手順・期待値はテストコードを正本とし、画面単位の**テスト観点表**（`04_テスト/テスト仕様書/`）に観点・確認内容・ケースIDを残す。証跡スクリーンショットは全ケースで自動取得し `e2e/evidence/<画面ID>/<ケースID>_<連番>.png` に保存する。実施結果の判定はテストの成否とし、証跡・HTMLレポートを人がレビューする。操作はキーボード（左手＝WASD・右手＝矢印キー・楽器を選ぶ数字キー）をPlaywrightから押して行う。**音の良し悪しはE2Eで判定しない**（2-1）。
- **`src/audio`（Tone.js）と `src/view`（Canvas 2D・HTML の画面・キー入力）は単体テストの対象にしない。** 音は耳で聞き、画面の流れはE2Eと目視で確かめる（→ [技術選定の設計方針](../02_基本設計/設計方針/技術選定の設計方針.md) 2章）。踊りと曲の中身は、`src/core` が計算する姿勢と `src/music` が作る音の並び（どの拍に、どの楽器の、どの高さ）として単体テストで確かめる。
- **システムテスト（リリース前確認）** は、リリース前に本番と同じビルドで主要シナリオを人が通しで遊んで聞いて確認する。**スクリーンショットは取得せず**、確認内容と検出した不良を**システムテスト報告書**にまとめ、報告書とシステムの両方を**品質管理部門へ確認依頼する**（詳細は6章）。
- **結合テスト以降で検出した不良**（結合テスト・システムテスト）は [02_バグ表](02_バグ表.md) で一元管理する。不良の正本は同表3章の表で、1件が1行。起票だけは番号なしの1件1ファイルを `バグ/未採番/` に置き、`/bug-sync`（または毎朝の Actions）が採番して表へ転記する。不良密度の集計元も同表とする（8章。集計の前に `/bug-sync` で未採番を転記して最新にする）。
- テストは実装より先に作成する（**テストファースト**）。作成タイミングと実装の反復ループの運用は9章を正本とする。

## 2. 合格基準

- 通常の確認では `npm run check` が成功すること（型検査 `tsc --noEmit` の違反ゼロ、`src/` を含む全体に対する ESLint の違反ゼロ、Vitest の単体テストの全件成功）
- リリース前およびクリーンな状態からの確認が必要な場合は、`npm ci` で依存を入れ直したうえで `npm run check` と `npm run build` が成功すること
- E2Eテスト（`npm run e2e`）が全件成功し、観点表の全ケースの証跡（`e2e/evidence/`）が揃っていること
- リリース時は、上記に加えて証跡のスナップショットを `04_テスト/エビデンス/<バージョン>/` へ保存していること（4-6参照）
- リリース時は、システムテスト報告書を作成し、**品質管理部門の確認・承認を得ていること**（6章）
- [02_バグ表](02_バグ表.md) の不良がすべて「確認済」または「取り下げ」になっていること（リリースを妨げない軽微な不良を残す場合は、品質管理部門の承認を得て次リリースへ持ち越す）
- 次節の明示的な除外対象を除き、要件定義（機能要件・非機能要件・受け入れ条件）を満たしていることをテスト項目で確認できること

### 2-1. 要件テストの明示的な除外対象

ここに挙げるのは**自動テスト（単体テスト・E2E）で確認しない**要件で、代替確認の欄で確認する。

| 要件ID | 除外する確認 | 理由 | 代替確認 |
|---|---|---|---|
| AC1・AC2・F5 | 違う踊りが聞いて分かるほど違う曲になること、どちらも曲として聞けること、5人重ねても誰の音か耳で分かり音が濁らないこと | 「聞いて分かる」「曲として聞ける」「濁らない」は耳で判断するもので、自動テストの期待値にできない。判定者は自分（→ [納品・検収要件](../01_要件定義/05_納品・検収要件.md) 6章） | システムテストで、実際に遊んで聞いて確認する（6-1 の条件1）。**数えられる部分は単体テストで固定する**: 違う踊り（違うキー入力）の記録から違う音の並びができること、鳴る音が音階（A マイナーペンタトニックの11段）に丸められること、人ごとに楽器が付き、楽器ごとの段の使い方（→ [音の設計方針](../02_基本設計/設計方針/音の設計方針.md) 3章）どおりの音になること（3章） |
| AC2・F6 | 5人重ねても誰の音か**目で**分かること、鳴った瞬間に頭・音階・分身が光るなどして、どの動きがどの音か分かること | 光るタイミングと見分けやすさは目で判断する。canvas の中身はロケーターで取れない（4-1） | システムテストで見て確認する（6-1 の条件1）。どの拍にどの人の音が鳴るかは `src/music` の単体テストで固定する（3章） |
| AC3 | 共有URLを**別のブラウザ**で開くと、元の鑑賞と**同じ踊り・同じ音**になること | E2Eは音を聞けない。同じかどうかは最後は目と耳で確かめる | 単体テストで「記録 → URL → 記録」の往復で記録が一致し、同じ記録から同じ姿勢の列と同じ音の並びになることを確かめる（3章。N3）。E2Eで共有URLを新しいページで開くと遊ばずに鑑賞が始まることを確かめる（5章）。同じに見え・聞こえるかはシステムテストで確認する（6-1 の条件2） |
| AC4 | 仕組みを知らない人が、説明を読まずに鑑賞まで遊べ、「自分の踊りが鳴っている」と感じること | 作者は仕組みを知っているので判定できない。判定者は**自分以外の1人以上**（→ [判断ログ](../01_要件定義/判断ログ.md) D17） | システムテストで、仕組みを知らない自分以外の1人以上に説明なしで遊んでもらい、鑑賞まで進めたかを観察し、感じ方を聞く（6-1 の条件3） |
| AC5 | GitHub Pages で公開され誰でも遊べること、外から持ってきた素材（絵・音）すべてに出所と権利確認の記録があること | 公開先の状態と記録の有無は、自動テストの対象外 | システムテストで、公開URLを開いて遊べること、素材と記録を突き合わせることを確認する（6-1 の条件4）。CC BY の素材のクレジットがゲーム内（トップページから行ける場所）に出ることはE2Eで確かめる（F10、5章） |
| N1 | Chrome 以外のブラウザでの動作 | どこまで保証するかが未決（基本設計で決める） | 決めたら本表を更新する |
| N2 | 操作から音が鳴るまでの遅れが気にならないこと | 数値が未決（試作で測って決める）。遅れは実際の機材と耳で決まる | システムテストで、実際に遊んで確認する。遅れの内訳（拍への丸め・先読み `DEFAULT_DANCE.noteLeadTicks`・機器の出力の遅れ `AudioContext.outputLatency`）は [音の読み込みと再生機能](../03_詳細設計/処理設計/音の読み込みと再生機能.md) 設計判断 No.10 |
| N5 | 画面が隠れても記録が欠けないこと（隠れたら一時停止し、戻ったら続きから） | 画面を隠したときのブラウザの間引きと音の停止は、実際のブラウザで起きる。E2Eでは spec 側で `visibilitychange` を起こして一時停止の表示と再開を確かめる（4-8）が、ブラウザの実際の間引きは再現できない | システムテストで、踊っている途中に別のタブへ移って戻り、続きから再開して分身の踊りが欠けないことを確認する（6-1 の条件5） |

## 3. 単体テスト方針

- 単体テストは Vitest で書き、対象と同じフォルダに `<対象>.test.ts` として置く（`src/**/*.test.ts`）。`npm test` で単体テストだけを、`npm run check` で型検査・静的解析とあわせて回す。
- **時間は待たずに作る。** `src/core`・`src/music` は時刻を数値（何刻み目か、音の時計の秒）で受け取るため（→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 6章、技術選定 3.2）、「開始から○刻み後」「ループの頭から○秒後」の状態を引数で直接作って確かめる。テストの中で実時間を待たない（`setTimeout` で待つテストを書かない）。
- **同じ入力からは必ず同じ結果になることを確かめる**（→ 技術選定 3.1、N3）。乱数は使わないので種の固定は要らない。同じキー入力の記録から、物理を2回計算して姿勢の列が一致すること、同じ記録から同じ音の並びになることを確かめる。物理は決まった刻み（1/60秒）で進むので、テストも刻みの数で進める（描画の回数に合わせない）。
- **仮の数値はテストに直書きしない。** 引く強さ・揺れ戻りの強さ・分身になるのに要る音の数・頭の高さを段に分ける境目などは、設定1か所にある名前付きの値を参照して境界（ちょうど・直前）を確かめる。数値は遊んで・聞いて変わるため（→ 同9章）、直書きすると調整のたびにテストが壊れる。テンポ・小節数も `DEFAULT_LOOP` などの名前付きの値から計算する（ループの長さは見直し中。→ 音の設計方針 4章）。
- `src/core` では、次を確認する。
  - キーを押している間、決まった体の部分（画面の左側の手＝WASD、画面の右側の手＝矢印キー）が決まった向き（画面の上下左右）に引かれ、体がつられて動き、離すと立ち姿へ戻っていくこと（F1）
  - 経過時間から、何周目の何刻み目（8分音符）かが正しく求まること。境目（ちょうど・直前）で刻みがずれないこと（F3）
  - 1周で一定以上鳴らすと、その周の踊りが分身として残り、次の周から同じ踊りを繰り返すこと。最大5人で、最後の1人を消せること（F4）
  - 記録に入るのが、キー入力（何刻み目に、どのキーが押された・離された）と楽器の選択だけであること（技術選定 3.1）
- `src/music` では、次を確認する。
  - 頭の高さが音階（A マイナーペンタトニックの11段）に丸められること。高さの境目（ちょうど・直前）で段が正しく変わること（F2）
  - 頭が動いた8分音符の拍だけ鳴り、前の拍から頭が動いていなければ鳴らないこと（F2）
  - 人ごとの楽器で、楽器ごとの段の使い方どおりの音になること（ベースは下のオクターブ、和音はパワーコード、高い旋律は1オクターブ上、打楽器は段で種類が変わる。→ 音の設計方針 3章。F5）
  - 違う踊りの記録から、違う音の並びができること（AC1 の数えられる部分）
  - 5人分の音の並びで、どの音がどの人・どの楽器のものかが区別できること（AC2・F6 の数えられる部分）
- `src/share` では、次を確認する。
  - **共有URLの往復**: 記録 → URL の `#` 以降 → 記録 で元の記録と一致し、そこから計算した姿勢の列と音の並びも一致すること（F8、AC3、N3）
  - 形式の版番号が先頭に入ること。壊れた文字列・版の違う文字列を読み戻すと、例外の握りつぶしではなく失敗が戻り値で返ること（→ 同5章・7章）
  - 5人分の記録を入れても、URLが決めた長さの上限に収まること（N4。上限は `#r=` から終わりまで 4000 文字。→ [共有機能](../03_詳細設計/処理設計/共有機能.md)）
- **単体テストから外部へ通信しない。** 外部サービスは使わないため（→ 同8章）、テストもネットワークを前提にしない。
- DBは使わない。テストは実行順に依存させず、実行後にファイルや状態を残さない。

## 4. 結合テストの運用ルール

### 4-1. 画面単位で作成する

- テスト観点表は**機能単位ではなく画面単位**で作成する（`02_基本設計/01_画面一覧・遷移図.md` の画面一覧と1対1。画面一覧は基本設計で作る）。棒人間ダンシングは1ページ内で HTML の表示を切り替えて画面を変えるが（→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 3章、技術選定 1章）、ページ遷移の有無で単位を変えず、画面一覧の画面ごとに観点表を作る。
- `テンプレート/テスト仕様書テンプレート.md` をコピーし、`04_テスト/テスト仕様書/SCRXX_○○画面テスト観点表.md` として保存する。
- **全画面に共通の部品を設けた場合は、その共通動作を部品単位の観点表（`COM01_○○テスト観点表.md`）に置き**、各画面の観点表には重複記載せず参照する。共通部品を設けるかは基本設計で決める。
- Playwrightのロケーターは `getByRole`/`getByLabel` を優先する。CSS IDセレクタ（`#id`）は対応する `<label for="id">` のあるフォーム部品に限り許容する。`data-testid` は使わない。
- **棒人間と舞台は Canvas 2D で描くため、canvas の中身（棒人間の姿勢・分身・光る頭や音階）はロケーターで取れない。** そこで次の2つに分ける。
  - **トップページ・ボタン・案内・クレジットは HTML と CSS で作る**（→ 技術選定 1章）。`getByRole` で取れ、キーボード操作や読み上げにも効く。どのボタンを置くかは画面設計で決める
  - **canvas の中のゲームの状態は、テスト用の読み出し口を置かず、画面に文字で出しているものから読む。** 分身の人数（SCR02「分身 n / 5」）、この周の音の数と出来事（SCR02 いまの案内）、楽器の選択（押した状態）、鑑賞の進み（SCR03・SCR04「鑑賞中 — i / n 人」）は、どれも利用者に見える HTML なので `getByRole`・`getByText` で取れる。姿勢・鳴った音そのものは E2E では確かめず、単体テスト（3章）とシステムテストで確かめる。読み出し口を置かないので、本番ビルドから外す仕組みも要らない
- Claude Codeでspecを作成・追加するときは `/gen-e2e <画面ID>` を使う（`.claude/commands/gen-e2e.md`）。本章の規約と共通fixture・helperの作法を手順として固定してあり、本書と観点表・既存specを読ませたうえでspecを書かせる。

### 4-2. 画面遷移の確認責務は「遷移元」の観点表に置く

- A画面からB画面へ切り替わるテストケースでは、**切り替わった先のB画面が正しい状態で表示されていること**（表示項目・引き継がれたデータ・メッセージ等）まで確認する。例: 踊る画面から鑑賞へ進むと、鑑賞の画面に切り替わり、それまでに残した分身が並んで再生されること。
- このケースは**A画面（遷移元）のテスト観点表に記載する**。B画面の観点表では「他画面から遷移してきた場合」のケースは書かない（重複させない）。
- B画面の観点表は「B画面を起点とした表示・入力・操作・遷移」だけに責任を持つ。

### 4-3. ケースの前提は新しいページから画面操作で作る

- **どのテストケースも、新しいページから始める**（Playwrightはケースごとに新しいブラウザコンテキストを作る）。「前のケースの結果の状態をそのまま使う」ことは禁止する。DBが無く、プレイ中の状態もブラウザに保存しないため（→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 3章）、新しいページで始めればケースは互いに独立する。
- ケースの前提（楽器の選択、分身を何人か残した状態）は、**画面の操作で作る**。手を引く操作（WASD・矢印キー）と楽器の選択（数字キー）はキーボードを押して出す。共有URLを開くケースは、`#` 以降に記録を入れたURLを新しいページで開いて始める。
- specは `@playwright/test` を直接 import せず、`e2e/fixtures/test.ts` から `test`・`expect` を取る。全ケースに共通の前提が必要になったときは、このfixtureで強制する（specごとに書かない）。
- **E2Eでは時間を早送りも固定もせず、実際の音の時計で進める。** キーを押した刻みは実行ごとにぶれるので、specは踊りの細かな結果（どの拍が鳴ったか）を期待値にせず、ぶれても変わらない結果だけを確かめる: 1周のあいだ手を引き続ければ分身が残る（W と S を交互に押し続け、分身が残る音の数を十分に超える）、周の終わりで画面が切り替わる、などの画面に出る結果。待つときは時間ではなく画面の文字が変わるのを待つ（`expect(...).toHaveText` の待ち合わせ。1周は約7.7秒なので、周をまたぐケースは周の数に合わせて待ち時間とケースの制限時間を延ばす）
- **共有URLを開くケースの URL は、ケースの中で遊んで作る。** SCR03 で「共有URLをコピーする」を押し、クリップボードから読む（ブラウザの文脈にクリップボードの読み書きの許可を与える）。固定の文字列は、物理や音の決め方を変えるたびに作り直しが要るため置かない。**壊れたURL・版の違うURLだけは固定の文字列にする**（`#r=1.` に Base64 にない文字を続けたもの、`#r=0.` で始まるもの。どちらも中身が今の形式に左右されない）
- 遊ぶ操作の組み立て（踊って分身を残す・鑑賞を終える・共有URLを作る・画面を隠す）は `e2e/helpers/play.ts` にまとめ、spec はそれを呼ぶ。
- 番号付きのテストデータセット・DBへのデータ投入は置かない（4-4）。

### 4-4. テストデータSQLの作成方針

該当なし（DBを使わないため、テストデータを投入するSQLを作らない。ケースの前提は4-3のとおり画面操作で作る）。

### 4-5. E2Eテストの実行方法

前提: Node.js 22以上。`.env` は不要（並行作業でポートを分けるときだけ `SERVER_PORT` を置く。→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 8章）。E2EはCIでは回さず、ローカルで回す。

```powershell
npm ci                                       # 初回のみ（アプリ側の依存。E2Eが npm run dev でアプリを起動するため）
npm --prefix e2e ci                          # 初回のみ（E2Eの依存）
npx --prefix e2e playwright install chromium # 初回のみ（ブラウザの取得。PCのChromeだけが対象のため chromium だけでよい）
npm run e2e                                  # E2Eテスト全件実行
npm run e2e -- scr01                         # 特定画面だけ実行する場合
npm --prefix e2e run report                  # HTMLレポートの表示
```

- **バグ・Issue対応・レビュー指摘対応で `src/` を直したときは、全件ではなく影響する画面ぶんだけを回す。** 対象specの選び方は [影響調査ルール](../基準書/影響調査ルール.md)「検証コマンド」の節を正本とする。全件成功は1章の結合テストの完了条件で担保する。
- 絞り込みの引数（`npm run e2e -- scr01`）はファイルパスに対する部分一致のため、画面IDを1つ渡せばその画面のspec（機能系・レイアウト系。4-7）がまとめて対象になる。
- DBの初期化・復元は無い。実行前に消えて困るデータも無い。
- アプリは `webServer` 設定（`npm run dev`）により自動起動する。**起動済みのアプリは再利用せず自分で起動する**（並行セッションが別ツリーで立てたアプリを再利用すると、相手の実行終了でこちらが接続拒否になるため）。
- ケースは直列に流す（`workers: 1`）。ゲームは音の時計で進むため、並列に流すと負荷でキーを押した刻みがぶれる。
- **並行作業で作業ツリーを分けたときは、`.env` の `SERVER_PORT` でアプリの待受ポートをツリーごとに変える**（`playwright.config.ts` の `appPort` から `use.baseURL` と `webServer` の待受URLが組まれる）。
- **specに接続先のホスト・ポートを直書きしない。** 画面を開くのは相対パス（`page.goto('/')`、共有再生は `page.goto('/#…')`）、URLの確認も相対文字列で書く。`browser.newContext()` で自分で開いた文脈も `use.baseURL` を継承するため同じでよい。リクエスト監視でURLを判定するときはパス部分で比較し、ホストを含む文字列で前方一致させない。直書きすると既定以外のポートで「必ず落ちる」か「中身を見ずに通る」のどちらかになり、自分の変更が回帰を起こしたかを失敗集合の比較で判定できなくなる。
- **失敗時のトレース（`e2e/test-results/`）とHTMLレポート（`e2e/playwright-report/`）には、画面への入力と通信の内容が記録される。** これらは `.gitignore` の対象でGit管理には入らない。確認はローカルで行い、チケット・PRへ添付しない。

### 4-6. 証跡の保存範囲

- **日常の実行で生成される `e2e/evidence/` はGit管理しない**（`.gitignore` の対象）。実行のたびに全削除・再生成されるため、履歴として残す意味がない。合格基準の確認は、実行直後のローカルの内容で行う。
- **リリース時だけ、その回の実行結果を凍結して残す**。`04_テスト/エビデンス/<バージョン>/` へスクリーンショットをコピーし、実施日・対象コミット・結果を記した `実施記録.md` を添えてコミットする。手順とテンプレートは `04_テスト/エビデンス/README.md` を正本とする（最初のスナップショットを作るときに作成する）。
- スナップショットに含めてよいのは**スクリーンショット（PNG）と実施記録だけ**とする。トレース・HTMLレポートは前項のとおり入力と通信の内容を含むため、コピーしない。

### 4-7. モックアップ依存でspecを分ける

観点表はE2Eの項目が妥当かを判断する基準なので、**必ずE2Eより先に完成させる**。そのうえでspecは、モックアップの完成を待つかどうかで2種類に分ける。

| 種類    | 検証対象                            | 必要なもの      | 作成できる時期      |
| ----- | ------------------------------- | ---------- | ------------ |
| 機能系   | 表示項目、入力、操作、メッセージ文言、画面の切り替え        | 画面設計書      | 画面設計書の完成後すぐ  |
| レイアウト系 | 要素の座標・折り返し・はみ出し・画像幅など、描画結果に依存するもの | 描画された画面   | 仮モックアップの確定後  |

- 機能系は `4-1` のとおり `getByRole`/`getByLabel` と文言で書けるため、**モックアップを待たない**。画面設計書が項目・文言の正本であることが根拠（[画面設計書ガイド](../基準書/画面設計書ガイド・チェックリスト.md)）。canvas の中身の確かめ方は4-1に従う（画面に文字で出しているものから読む）。
- レイアウト系は機能系と別ファイル（`scrXX-<画面の英名>.layout.spec.ts`）へ分ける。1つのspecに両方を混ぜない（モックアップ待ちが機能系まで巻き込むため）。表示幅はPCのChrome（Desktop Chrome）の1種類だけなので、表示幅ごとにファイルを分けない。
- レイアウト系でもロケーターは `4-1` の原則に従う。クラスセレクタが避けられない場合は、実装とspecの双方で安定したテスト用契約として扱い、spec内に使用理由を記す。デザインシステムは共通外観の規定（色・書体・余白・形・部品の決めごと）だけを扱い、実装上のクラス名は記載しない。クラス名は実装とspecの間の契約であり、デザインシステム側に持たせるとリファクタで必ず乖離するため。

### 4-8. 音と時間の再現方式

E2Eは音を聞けず、ゲームは音の時計（`AudioContext.currentTime`。Tone.js の Transport は使わない。→ 技術選定 3.2）で拍と物理の刻みを数える。乱数は使わない（同 3.1）。E2Eでの扱いは次のとおりとする。

- **E2Eでも音の機能を本物のまま動かす。** ヘッドレスの Chrome でも音の時計は進み、楽器の音のファイルは開発サーバーから本番と同じ経路で読む。音を差し替える仕組みは置かない（クリックやキー操作が「利用者の操作」になるので、音を始められる）。時間は早送りしない（4-3）
- **画面が隠れたときの一時停止は、spec の側で `document.visibilityState` を隠れた状態にして `visibilitychange` を起こして確かめる。** アプリには手を入れない。Space での一時停止（SCR02）はキーを押して確かめる
- どう決めても、**テストのためにアプリ側へ「テスト中かどうか」の分岐を入れない**。時刻とキー入力は引数で渡す作りなので（→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 6章）、差し替えは渡す値で行う。分岐させると、本番と同じ経路が未確認のまま残る。
- **再現しないもの**は、曲の聞こえ方（違う踊りで違う曲に聞こえる・曲として聞ける・5人重ねて濁らない）と、操作から音までの実際の遅れ。これらはシステムテストで確認する（2-1、6-1）。踊りと曲の中身は `src/core`・`src/music` の単体テストで固定する（3章）。

## 5. 結合テストの観点

画面ごとに、以下の観点でテストケースを洗い出す（順序の縛りはない。該当しない観点は省略してよい）。

| 観点       | 確認する内容                                                                                | 例                                        |
| -------- | ------------------------------------------------------------------------------------- | ---------------------------------------- |
| 初期表示     | 画面を開いた直後の表示が設計書・モックアップ通りか                                            | トップページから踊り始められる。楽器の音を読み込み終わるまでは「準備中」と出る（技術選定 3.4）                |
| 表示内容・表示順 | 表示項目（今の楽器・分身の人数などの導出項目を含む）、並び順。文言が画面設計の記載と一致するか。表示項目は画面設計で決める                                | トップページから行ける場所に、使った素材の作者とライセンスが表示される（F10・AC5）                      |
| 入力チェック   | 受け付けないキーが無視され、仕様通りに扱われるか（→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 5章） | WASD・矢印キー・楽器を選ぶ数字キー以外のキーを押しても何も起きない               |
| 境界値      | 時間・数の境界で正しく切り替わるか。分身になるのに要る音の数・頭の高さの段の境目などは単体テストで確認し（3章）、E2Eでは画面で観察できる境界だけを扱う | ループの1周が終わったところで分身が現れる（F4）                   |
| 最大文字数の表示 | 最大文字数のデータで、画面表示がレイアウト崩れ・欠けなく表示されるか。利用者が文字を入力する画面は無いため、クレジットの作者名・ライセンス表記など長い文言を決めたときに観点を立てる                                        | —                |
| 最大件数の表示  | 繰り返し表示される要素が最大件数のときに、レイアウト崩れなくすべて表示されるか。分身は最大5人                                                | 5人そろったとき、全員が舞台に収まって表示される（F4・AC2）                |
| ルールどおりのふるまい | 踊り・分身・楽器のルールどおりに状態が変わり、それが画面で分かるか                                                     | 最後の1人を消すと分身が1人減る（F4）／選ばなかったときは、まだ使っていない楽器が順番に付く（F5）             |
| 共有URLの作成   | 共有URLを作れたこと・作れなかったことが、黙らずに画面に出るか（→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 5章）             | 鑑賞の後に共有URLを作ると、`#` 以降に記録の入ったURLが手に入る（F8。渡し方は画面設計で決める）      |
| エラー後の再操作 | 失敗の後、操作し直すと続けられるか                                                 | 楽器の音の読み込みに失敗した後、読み込み直して遊べる（扱いは詳細設計で決める）                 |
| 画面遷移     | 操作・状態の変化ごとに正しい画面へ切り替わるか。**切り替わった先の画面が正しい状態（表示項目・引き継ぎデータ・結果）で表示されるか**（4-2の通り遷移元の観点表に記載） | 踊る画面から鑑賞へ進むと、分身が並んで1周ごとに1人ずつ加わる（F7）／`#` 以降に記録の入ったURLを開くと、遊ばずに鑑賞が始まる（F8・AC3）                |
| 外部通信     | ページの外への通信が発生しないか（リクエスト監視で確かめる）                                               | 共有URLを開いて再生し終わるまで、記録がどこへも送られない（→ [インフラ要件](../01_要件定義/03_インフラ要件.md) I1）。楽器の音は同じサイトから読み、外のサイトへ取りに行かない（技術選定 3.4）             |
| 異常系      | 想定外の状態でも、黙って止まらず画面に出るか                                                    | `#` 以降が壊れたURL・版の違うURLを開いたときの表示（扱いは詳細設計で決める。→ 実装方針5章）                        |
| システムエラー  | 予期しない例外の表示に、内部の詳細が出ていないか | 共有URLの読み戻しに失敗したときの表示に、スタックトレースが出ない |
| 表示幅（PCのChrome） | Desktop Chrome の表示幅でレイアウト崩れ・横スクロールなく表示されるか                     | 踊る画面が崩れずに表示される |

- 「DB反映」「画像反映」「認証」の観点は置かない。DB・画像の登録・ログインが無いため。
- **作り方の規約はE2Eの観点にしない。** 層の依存の方向、仮の数値の直書き禁止、`core/`・`music/`・`share/` で乱数・現在時刻・`Math.sin` などブラウザで結果が変わりうる関数を使わないことなどは静的解析とレビューで確認し（→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 2・6・9章）、観点表に画面ごとのケースを立てない。観点表が担うのは利用者に見える結果までとする。
- **音の聞こえ方はE2Eの観点にしない**（2-1・4-8）。
- **システムエラー**の確認は、E2Eで再現できる経路だけを対象とする。予期しない例外の経路はE2Eで作れないため、単体テストで確認する（3章）。
- **表示幅**の確認は、Playwrightの `chromium` プロジェクト（`devices['Desktop Chrome']`）の1種類だけで行う。スマートフォン・タブレットは対象外とする（→ [判断ログ](../01_要件定義/判断ログ.md) D11、[非機能要件](../01_要件定義/02_非機能要件.md) N1）。

## 6. システムテストの運用ルール

### 6-1. 実施内容と範囲

- リリース前に、本番と同じビルド（GitHub Pages に公開する配信物）をPCのChromeで開き、主要シナリオを人が通しで遊んで聞いて確認する。**対象シナリオは `04_テスト/システムテストシナリオ/` を正本とする**（1シナリオ1ファイル。一覧は同フォルダの README。シナリオを作るときに作成する）。
- **シナリオは [納品・検収要件](../01_要件定義/05_納品・検収要件.md) の完成の定義（2章）と受け入れ条件 AC1〜AC5（6章）を根拠に作る。** 各シナリオに、どのACを確かめるかを明記し、AC1〜AC5のすべてがいずれかのシナリオで確かめられるようにする。ACは「満たすこと」と「同時に守ること」の対なので、**両方を確かめて初めて合格**とする。
- システムテストは、**実際の動作環境で主要シナリオを遊ぶ人の流れに沿って通し、主要な操作・表示・音を合否判定する**。E2Eで画面単位の詳細を確認済みであっても、シナリオの3章で実際に通過する楽器の選択・踊る・分身を重ねる・鑑賞・共有など、遊ぶ流れを成立させる主要な操作・表示は、システムテストでも実施して合否を付ける。E2Eと同じ観点をそのまま網羅し直すのではなく、実際の音と人の耳という条件で通し確認するための判定とする。
- **主要な操作・表示**とは、シナリオの目的を達成するために遊ぶ人が実際に行う操作と、その結果として確認する画面・音・状態をいう。入力の境界、異常系の網羅、細かな文言・並び順、E2Eでしか再現できない状態など、シナリオで実施しない詳細観点はE2Eの専任範囲とする。
- 各シナリオの4章は、次の2つに仕分ける。①シナリオの3章で実施する主要な操作・表示（E2Eにも対応ケースがある場合を含む）は「本シナリオで実施し、合否を付けるもの」として記載する。②シナリオで実施しない詳細観点は「E2E専任（本シナリオでは実施しないもの）」として記載する。後者は操作の途中で偶然目に入っても合否を付けない。
- システムテストで確認する実際の動作環境に固有の条件は、具体的には次の5種を含む。
  1. 曲を耳で聞き、目で見て判断すること（AC1・AC2、F2・F5・F6・F7）。同じ人が違う踊りで遊んで聞き比べる。5人重ねて、どの人がどの音か耳と目で分かり、音が濁らないことを確かめる
  2. 共有URLを別のブラウザで開き、遊ばずに鑑賞が再生され、元の鑑賞と同じ踊り・同じ音になること（AC3、N3）
  3. 仕組みを知らない自分以外の1人以上が、説明を読まずに鑑賞まで遊べ、「自分の踊りが鳴っている」と感じること（AC4、判断ログ D17）。説明や助言をせずに遊ぶ様子を観察し、遊んだ後に感じ方を聞く
  4. GitHub Pages の公開URLで遊べることと、外から持ってきた素材（絵・音）すべてに出所と権利確認の記録があり、CC BY の素材のクレジットがゲーム内に出ること（AC5、N7）
  5. 踊っている途中に画面を隠して戻すと、続きから再開し、記録が欠けないこと（N5）
- **スクリーンショットは取得しない。** 確認内容と結果は次項の報告書に文章で記録する。
- シナリオを追加・変更するときは、シナリオ側のファイルと同フォルダのREADMEの一覧を同じ変更で更新する。

### 6-2. システムテスト報告書

- 報告書は `04_テスト/システムテスト報告書/` に、リリースバージョンごとに**親ファイル `<バージョン>_システムテスト報告書.md` と、シナリオ別ファイル `<バージョン>/<シナリオID>_<シナリオ名>.md`** の2階層で作成する。作成時は [システムテスト報告書テンプレート](../テンプレート/システムテスト報告書テンプレート.md) と [システムテスト報告書シナリオテンプレート](../テンプレート/システムテスト報告書シナリオテンプレート.md) をコピーする。ファイルごとの分担は同フォルダの README を正本とする（最初の報告書を作るときに作成する）。
- 報告書には次を必ず記載する（2はシナリオ別ファイル、それ以外は親ファイルへ書く）。
  1. **実施概要** 実施日、実施者
  2. **確認内容と結果** … 各シナリオのNo.を参照し、実際に観察した結果と判定を文章で記録する。シナリオの操作手順は報告書へ重複して記載しない。判定は`合格`・`不合格`・`対象外`のいずれかとし、`対象外`には理由と代替確認または参照先を記載する
  3. **不良一覧** … 検出した不良の一覧。[02_バグ表](02_バグ表.md) のバグIDを引用し、報告書側では要約と対応状況だけを書く（詳細を二重管理しない）
  4. **判定** … リリース可否の判断と、その根拠
  5. **インフラチームの構築完了確認** … 該当なし（インフラチームによる構築が無いため。GitHub Pages への公開は GitHub Actions で行う。→ [インフラ要件](../01_要件定義/03_インフラ要件.md) I1）
- **判定は、シナリオの `確認内容` に書かれた条件を1つずつに分解し、そのすべてを実際の観察で満たしたことを確認できたときだけ `合格` とする。** 条件が1つでも未確認のまま残る状態を `合格` にしない（未確認は確認してから判定する）。突き合わせでは次を守る。
  1. 受け入れ条件は「満たすこと」と「同時に守ること」の**両方**を確かめる。片方だけで合格にしない（例: AC1 は踊りで曲が変わることに加え、どちらも曲として聞けること）
  2. 曲が同じか・違うかの判断は、**聞き比べた2つの曲が何か**（どの踊り・どの楽器・どの共有URL）を記録してから判定する
  3. **ソースの文字列検索の結果だけで、画面の表示・非表示を判定しない**（文言は文言定義から来る）。画面で確かめる
  4. 確認内容に無い気づき（遊び心地・見た目など）は判定に混ぜず、観察事実または不良として別に記録する
- 実施前に、各シナリオで使う楽器・踊り方・分身の人数・使うPCとブラウザ・音を聞く機材（スピーカー／ヘッドホン）、AC4 では遊んでもらう人が仕組みを知らないこと（名前は書かない）などの事前状態を、**シナリオ別ファイルの「1. 事前条件・テストデータ」**へ記録する。実施回ごとに報告書のバージョンを分け、初回は `v1.0.0`、2回目は `v1.1.0`、3回目は `v1.2.0` とする。既存版は変更せず、再テスト版は前回不合格観点と影響範囲観点に限定して記録する。
- 検出した不良は、報告書に書くだけでなく **[02_バグ表](02_バグ表.md) へ必ず登録する**（不良密度の集計元となるため）。

### 6-3. 品質管理部門への確認依頼

- リリース前に、**システムテスト報告書と稼働中のシステムの両方** を品質管理部門へ提出し、確認を依頼する。稼働中のシステムは、公開前のビルドを開発者のPCで動かして見せる。
- 品質管理部門の**確認・承認を得るまでリリースしない**。
- 指摘を受けた場合は、[管理表/品質管理指摘表](../管理表/品質管理指摘表.md)へ登録し、不良と判定したものは[02_バグ表](02_バグ表.md)へも登録する。対応後に再度確認を依頼する。
- 確認依頼日・確認結果・承認者は、報告書の「品質管理部門の確認」欄に記録する。

### 6-4. システムテスト用のテストデータ

- DBが無いため、シードSQLは置かない。前提（使う楽器・踊り方・分身の人数）は、シナリオの手順として画面で操作して作る。
- **遊んで得た共有URLが、そのままテストデータになる。** 共有URLには記録（キー入力と楽器の選択）が入っているため、開けば物理を計算し直して同じ踊りと音を再現できる（→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 6章・7章、技術選定 3.1）。AC1・AC2 の聞き比べ、AC3 の「同じ踊り・同じ音か」の確認、不良の再現に使う。
- 使ったデータ（楽器・踊り方・共有URL）は、該当シナリオの2章（事前準備）と、システムテスト報告書のシナリオ別ファイル（`システムテスト報告書/<バージョン>/<シナリオID>_<シナリオ名>.md`）の「1. 事前条件・テストデータ」へ記録する。記録の形式・物理・音の決め方が変わると古いURLは別の踊りや曲になりうるため（→ 同7章）、URLは実施した版のビルドと組で記録する。

## 7. テストデータ

- 単体テスト用データ: テストコードの中に書く。記録は、キー入力（何刻み目に、どのキーを押した・離した）と楽器の選択を手で並べて作る。頭の高さから音を確かめるときは、記録から物理を通さず、高さを直接渡してもよい。AIがテストコードとあわせて作成する。記録の形式は [共有機能](../03_詳細設計/処理設計/共有機能.md) の処理設計
- 結合テスト用データ: 用意しない。ケースの前提は新しいページから画面操作で作る（4-3）。共有URLはケースの中で遊んで作り、壊れたURL・版の違うURLだけ固定の文字列にする（4-3）
- システムテスト用データ: 遊んで得た共有URL（6-4）
- ベースデータ: リポジトリに含めた楽器の音のファイル（録音）と、背景・トップページなどの画像（→ [アプリケーション実装方針](../基準書/アプリケーション実装方針.md) 7章、[素材/音の記録](../素材/音の記録.md)、[素材/画像の記録](../素材/画像の記録.md)）
- アカウント: 無い（ログインが無いため）。秘密値も無い
- テストで担保する範囲: 分身は**最大5人**、楽器は**5つ**、ループは**4小節**（124 BPM で約7.7秒。8小節にするかは見直し中）、音階は**11段**（→ [機能要件](../01_要件定義/01_機能要件.md) F3・F4・F5、[音の設計方針](../02_基本設計/設計方針/音の設計方針.md) 1・3・4章）

## 8. 品質指標（テストケース密度・不良密度）

目標値（テストケース密度・不良密度）は要件定義に定めていない。**目標値は未決とする**（担当: kashiwagi、決定期限: 結合テストの開始まで）。決まるまでは、次節の方法で実績を記録し、下表のIPA中央値を参考として並べるだけにする（0.5〜2倍の判定はしない）。本章は計測と判定の方法を定める。

### 8-1. 計測方法

| 計測対象 | 数え方 |
|---|---|
| 規模（KS） | `src/` 配下のTypeScriptソース（`*.ts`。`*.test.ts` を除く）の実効行数（空行・コメント行を除いた行数）÷ 1,000 |
| 単体テストのケース数 | `src/` 配下の `*.test.ts` にある `it`・`test` の総数（`it.each`・`test.each` は1件と数える） |
| 結合テスト（E2E）のケース数 | `e2e/tests/` 配下の `test()` の総数（観点表のケースIDと1対1） |
| 不良数 | [02_バグ表](02_バグ表.md) のうち、検出工程が該当し「密度計上」が○の件数。アプリケーション（`src/`）の修正に至ったものだけを計上し、テストコード・テストデータ・環境設定の誤りは数えない |

- **結合テストの不良数は「結合テスト（人間）」と「結合テスト（AI）」の合計で数える。**バグ表1章のとおり、検出工程は誰が最初に事象に気づいたかで2つに分かれるが、工程としてはどちらも結合テストで、不良密度の分母（規模）も同じであるため。人の目視とAIの自動テストのどちらが効いているかを見たいときだけ、値ごとに分けて数える。

### 8-2. 判定の運用

- 目標値が決まったら、実績が目標値の**0.5〜2倍**に収まることを目指す。範囲を外れた場合は原因を分析する（テスト観点の漏れ、ケース粒度の変化、実装規模の急増など）。
- 不良密度は、規模が小さいうちは目標値から算出される絶対数が数件にとどまり、0.5〜2倍の判定が機械的には機能しない。**規模が数KSに満たない間は、目標値から算出した絶対数を目安として扱い、0件の下振れは、テストケース密度が目標範囲に収まっていること（テスト不足の兆候がないこと）をもって許容する。**
- 目標値を決めるときの参考は、次のIPA「ソフトウェア開発分析データ集」（新規開発）の中央値。

| 指標 | IPA中央値（参考） |
|---|---|
| 結合テスト密度 | 37.63件/KS |
| 結合テスト不良密度 | 1.111件/KS |
| 総合テスト不良密度 | 0.197件/KS |

- IPAの値と比べるときは、**数え方が異なる**ことに注意する。IPAは試験項目単位で数えるのに対し、本プロジェクトは1ケース内で複数の確認（アサーション）を行うケース単位で数える。

## 9. テストの作成タイミングと反復ループ（テストファースト）

機能追加の全体手順は[アプリケーション実装方針](../基準書/アプリケーション実装方針.md)10章を正本とする。本章はそのうち、テストをいつ書くか・テストを使って実装をどう進めるかの運用を定める。

### 9-1. テストファースト（ハーネスエンジニアリング）

- 実装より先にテストを書き、設計書の仕様を合格条件としてテストコードに固定する。この先に用意したテスト群を実装の**ハーネス**として使い、実装の完了判定は人の目視ではなくテストの全件成功で行う。
- 先に書いたテストは、実装が存在しない・未完成の間は失敗してよい（失敗するテストから始める）。ただし型検査が通らない状態を放置しないよう、テスト対象のモジュール・関数・型の骨格（シグネチャ）までは先に用意する。
- テストの期待値は設計書（処理設計・画面設計・テスト観点表）から導く。実装の都合に合わせて期待値を弱めない。仕様自体を変える場合は、先に設計書を直してからテストを直す。

### 9-2. 実装の反復ループ（ループエンジニアリング）

- 実装は「実装・修正 → `npm run check` → 失敗があれば原因を直す」の反復ループで進め、全件成功をもって完了とする。AIに実装させる場合も、この反復を9-1のハーネスに合格するまで自律的に繰り返させる。
- E2Eテストも同様に「`npm run e2e` → 失敗の修正」を全件成功まで繰り返す。
- E2Eループで検出した失敗のうち、`src/`（アプリ本体）の修正に至ったものは不良として[02_バグ表](02_バグ表.md)へ起票する（検出工程は「結合テスト（AI）」、修正コミット確定後に記入する）。テストコード側だけの修正や環境起因の失敗は起票しない。
- ループの途中でテストの期待値を書き換えて通すことは禁止する（9-1参照）。テストコード自体の不良を直した場合は、アプリの修正と区別できるようコミットを分ける。
- ループが収束しないとき（同じ失敗を3回以上繰り返す等）は機械的な修正を続けず、設計とテストのどちらに問題があるかを立ち止まって判断し、必要なら設計書へ戻る。
