# バグ表

結合テスト以降で検出した不良を一元管理する。運用の前提は [01_テスト方針](01_テスト方針.md) を正本とする。他のコマンド・エージェントが章番号で参照しているので、**章番号は変えない**。

## 1. 管理対象

| 検出工程 | 管理 | 理由 |
|---|---|---|
| 単体テスト（Vitest） | **管理しない** | 実装とテストコードの修正サイクル内で完結するため。テストコードを正本とする |
| **結合テスト（人間）** | **管理する** | 人が画面・挙動を見て気づいた不良 |
| **結合テスト（AI）** | **管理する** | AIが自動テスト・探索・突合で見つけた不良 |
| **システムテスト（リリース前確認）** | **管理する** | 品質管理部門への報告対象でもある |
| 品質管理部門からの指摘 | **不良と判定したものだけ管理する** | 指摘そのものは [管理表/品質管理指摘表](../管理表/品質管理指摘表.md) が正本。不良と判定したものを検出工程「システムテスト」として本表へも起票し、品質管理指摘表の `バグID` で紐付ける |
| **実装完了後の画面へのUI変更** | **管理する** | デザイン修正・見た目の変更・設計書との乖離修正を含め、内容が改善であってもバグとして扱う。検出工程は見つけた側に合わせて「結合テスト（人間）」「結合テスト（AI）」のどちらかで登録する |

**結合テストを「人間」「AI」に分ける理由**: 同じ結合テスト工程でも、人の目視とAIの自動テストでは見つかる不良の種類が違う。どちらがどれだけ効いているかを後から見られるようにする。判定は**誰が最初に事象に気づいたか**で決め、起票・修正を誰がやったかでは決めない。

| 値 | 該当するもの |
|---|---|
| `結合テスト（人間）` | 人が画面・挙動を見て気づいたもの。発注元・顧客のレビューでの指摘、社内メンバーの目視での気づきを含む |
| `結合テスト（AI）` | AIが見つけたもの。E2Eの失敗、モンキーテスト（探索テスト）、設計書とコードの突合、調査中に見つけた副産物 |

- 実装の反復ループ（テスト方針9-2）中に実行したE2Eで検出した不良も、`src/`（アプリ本体）の修正に至ったものは検出工程「結合テスト（AI）」として登録する。テストコード側だけの修正は登録しない。
- リリース後に発覚した不良も、検出工程を「リリース後」として本表に追加する。
- 実装完了後の画面へのUI変更のうち、実施すると決めていない改善の気づきは本表ではなくIssue（[課題・アイデア管理手順](../基準書/課題・アイデア管理手順.md)）に起票する。有識者紙面レビュー起因の修正はレビュー指摘表で管理する（本表と二重起票しない）。
- 本表は[テスト方針](01_テスト方針.md) 8章の**不良密度の集計元**とする。

## 2. 記入ルール

### 2-0. 起票は1バグ1ファイル、記録は3章の表

不良の記録は **3章の表を正本** とし、1件が1行に入る。起票のときだけ、番号を取り合わないために1件1ファイルをいったん置く。**対応が終わる（`状態` が `修正済`・`確認済`・`取り下げ` のいずれかになる）までは、そのファイルが記入先。**終わったものだけを `/bug-sync` が採番して表へ転記し、ファイルを消す。

| 場所 | 役割 |
|---|---|
| `バグ/未採番/<担当者>-<YYYYMMDD>-<HHmmss>.md` | 起票から対応が終わるまでの不良1件。**番号を付ける前の置き場**で、修正・確認の記入も対応が終わるまではここで行う。見出しはファイル名と同じ（例: `# yamada-20260908-193012`）。`/bug-new` が作業ブランチに作り、通常のPRで master へ入る。列は3章と同じ14項目を「項目 \| 内容」の2列表で持つ（[未採番/README](バグ/未採番/README.md) を手本にする） |
| 本ファイル 3章 | **不良の正本**。`<!-- bug-table:start -->` と `<!-- bug-table:end -->` の間が表で、1件が1行。転記（採番）は毎朝9時の GitHub Actions（`.github/workflows/bug-table-sync.yml`）またはkashiwagiの `/bug-sync` が master 上で行い、**対応の終わった未採番ファイルだけ**を転記して、そのファイルを消す。転記後に記入を直すときはこの行を直接書き換える |

- **なぜ起票だけ分けるか**: バグIDはブランチをまたぐ共有カウンタで、各ブランチで番号を採ると必ず取り合いになる。起票を番号なしのファイル追加に閉じておけば、採番する場所（master）を1つに保てる。
- **なぜ対応が終わるまで据え置くか**: 採番は master 上で行い、転記できたファイルを消す。まだ書き足している最中のファイルを消すと、修正内容を書いた作業ブランチとの間で「片方が消し、片方が書き換えた」競合になる。書き終わったものだけを移せば、この競合は起きない。
- 起票時に埋めるのは `検出工程`・`検出日`・`検出者`・`対象`・`事象`・`重要度`・`状態`（`未対応`）の7項目とし、残りは空欄のまま行だけ置く。`混入工程`・`原因`・`対応内容`・`修正コミット`・`確認日`・`密度計上` は修正時に記入する。**採番は対応が終わってから行うので、修正の記入先は通常 `未採番/` のファイル。**すでに採番されている場合だけ3章の該当行へ書く。
- 項目を増やさない（[影響調査ルール](../基準書/影響調査ルール.md)）。3章の表の列数・値の書式と、未採番ファイルの名前・見出し・項目名は、PR の CI（`node .github/scripts/bug-table.mjs check`）が検査する。

### 2-1. バグID

`BUG-001` の形式で、プロジェクト全体を通した連番とする。取り下げた番号を再利用しない。

**起票（`/bug-new`）では番号を付けない。** バグIDはブランチをまたぐ共有カウンタで、各ブランチで採ると並行しているブランチと必ず取り合いになる。起票は `バグ/未採番/<担当者ローマ字>-<YYYYMMDD>-<HHmmss>.md`（担当者と起票時刻で一意。例: `yamada-20260908-193012.md`）を作業ブランチに作り、通常のPRで master へ入れる。

**番号を付けるのは master 上の `/bug-sync` と毎朝9時の GitHub Actions だけ。** `未採番/` のうち**対応の終わったファイル**（`状態` が `修正済`・`確認済`・`取り下げ`）を検出日→ファイル名の順に並べ、3章の表にある最大番号＋1 から順に `BUG-nnn` を付けて表の末尾へ1行ずつ転記し、転記できた未採番ファイルを消す。`状態` が `未対応`・`対応中` のファイルは採番せずそのまま残す。`/bug-sync` を手で実行するのはkashiwagiだけとし、他の担当者は翌朝の自動実行を待つかkashiwagiに依頼する。番号を付ける場所が1つなので取り合いは起きない。

- 手で `BUG-nnn` を付けない。3章の表へ手で行を足さない（起票は必ず `未採番/` のファイルで行う）。
- **番号は対応が終わってから付く。**修正中は未採番の名前（例: `yamada-20260908-193012`）で呼び、採番後は表の行の `修正コミット` 列で修正と紐付ける。
- 転記済みのバグを直すときは3章の該当行を書き換える。行が隣り合うためコンフリクトすることがあるが、そのときは両方の行を残す（同じ行を2人が直したときだけ内容を突き合わせる）。

同じIDの行が2つあること、列数の違い、値の書式違反、未採番ファイル名・見出しの不一致、表の外にあるバグの行はPRのCIが落とす（[ci.yml](../../.github/workflows/ci.yml) の「バグ表の検査」）。

### 2-2. 重要度

| 重要度 | 判断基準 |
|---|---|
| 致命的 | ステージが進まなくなる・画面が止まる、種明かしの曲が鳴らない、共有URLを開いても再生されない。リリースを中止する |
| 重大 | 主要機能が使えない（配達が完了しない、書き出しができないなど）、共有URLや書き出しで元のプレイと違う曲になる、伴奏と旋律がぶつかる。修正するまでリリースしない |
| 中 | 機能は動くが仕様と異なる、回避策がある。原則リリース前に修正する |
| 軽微 | 表示崩れ・文言の誤りなど、遊ぶのに支障がない。品質管理部門の承認を得て次リリースへ持ち越してよい |

### 2-3. 状態

`未対応` → `対応中` → `修正済` → `確認済` の順に遷移する。不良でないと判断した場合は `取り下げ` とし、理由を備考に書く。

- `修正済` … 修正をコミットした状態。まだ再確認していない
- `確認済` … 再テスト実施者が修正後に再テストして、事象が解消したことを確認した状態。確認した担当者名は「備考」に記録する

### 2-4. 混入工程

不良が作り込まれた工程を記録する（`要件定義` / `基本設計` / `詳細設計` / `実装` / `テスト設計` / `環境設定`）。後工程での検出が多い工程を把握し、レビュー強化の判断材料とする。

### 2-5. 密度計上

不良密度（テスト方針 8-1）に数えるかどうかを `○` / `—` で記入する。

- `○` … アプリケーション（`src/` のうち `*.test.ts` を除くもの）の修正に至ったもの
- `—` … アプリケーションを変更していないすべてのもの。要件・設計・テスト設計・テストコード・テストデータ・環境設定だけの修正、仕様どおりで取り下げたものを含む

## 3. バグ一覧

不良の正本。1件が1行で、転記後に `混入工程`・`原因`・`対応内容`・`修正コミット`・`状態`・`確認日`・`密度計上` を直すときはこの行を直接書き換える。**行を手で足さない**（起票は `/bug-new` が `バグ/未採番/` に置き、毎朝9時の GitHub Actions かkashiwagiの `/bug-sync` が master 上で採番して末尾へ転記する。2-0・2-1）。**対応中の不良はここに載らない。**転記されるのは対応が終わったものだけで、それまでは `バグ/未採番/` のファイルが記入先（2-0）。マーカー（`<!-- bug-table:start -->` / `<!-- bug-table:end -->`）の内側にある**空行を消さない**。空行が無いとマーカーのHTMLコメントに表が飲み込まれ、表として描画されずに生のテキストで出る（CIの `check` が落とす）。

## 4. 集計

リリースごとに、不良密度の判定（テスト方針 8-2）のため次を集計する。

| リリース | 規模（KS） | 結合テスト不良数 | 結合テスト不良密度 | システムテスト不良数 | システムテスト不良密度 | 判定 |
|---|---|---|---|---|---|---|
| （記入例）v1.0.0 | 0.0 | 0 | 0.0 件/KS | 0 | 0.0 件/KS | 参考（目標値未決） |

- 不良数は「密度計上」が `○` の件数を検出工程ごとに数える。
- 規模（KS）の計測方法はテスト方針 8-1 に従う。
- 目標値と許容範囲はテスト方針 8章を正本とする（目標値は未決。決まるまでは実績を記録するだけで、判定欄は「参考」とする）。
- 集計結果はシステムテスト報告書にも記載する。
