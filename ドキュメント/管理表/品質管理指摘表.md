# 品質管理指摘表

**品質管理部門（社内）がテスト工程で挙げた指摘**と、その対応結果を一元管理する。品質管理部門の確認・承認を得るまでリリースしない（[01_テスト方針](../04_テスト/01_テスト方針.md) 6-3）ため、指摘が放置されたまま、または対応の証跡が残らないままリリース判定に進むことを防ぐ。他のコマンド・エージェントが章番号で参照しているので、**章番号は変えない**。

## 1. 管理対象

品質管理部門が次の確認で挙げた指摘を本表で管理する。

- **システムテスト報告書の確認**（報告書の記載・判定・対象外の妥当性への指摘）
- **稼働中のシステム（公開前のビルドを開発者のPCで配信したもの）の確認**（動作・表示・運用への指摘）

指摘のうち**アプリケーションの不良と判定したもの**は、[04_テスト/02_バグ表](../04_テスト/02_バグ表.md)（検出工程 `システムテスト`）へも起票する。不良の原因・修正内容・不良密度はバグ表が正本で、本表には `バグID` で紐付けるだけとし、二重に書かない。本表が持つのは「品質管理部門が何を指摘し、どう決着し、誰がいつ確認したか」である。

以下は対象外。それぞれの記録先に従う。


| 指摘・不良                                             | 記録先                                                                             |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| 開発者自身がテストの実施中に見つけた不良               | [04_テスト/02_バグ表](../04_テスト/02_バグ表.md)（`/bug-new` で起票）              |
| 有識者の紙面レビュー・納品前の最終確認（内部RV）の指摘 | [レビュー指摘表](レビュー指摘表.md)                                                |
| 顧客から受けたレビュー・質問                           | QA表（共有フォルダのExcel）                                                                    |
| チーム内で気づいた課題・アイデア                       | GitHub の Issue（→ [課題・アイデア管理手順](../基準書/課題・アイデア管理手順.md)） |


- その場で即座に合意・修正が完了した軽微な指摘（報告書の誤字など）は、本表への登録を省略してよい。判断が分かれたもの、対応を見送ったもの、後続対応にしたもの、不良として起票したものは必ず登録する。
- 対応方針をその場で決められない指摘は、本表へ `未対応` として登録した時点で停止する。人間が「対応」または「見送り」を決めた後に、対応を再開する。



## 2. 記入ルール



### 2-1. 指摘ID

`QC-001` の形式で、プロジェクト全体を通した連番とする。取り下げた番号を再利用しない。

`REV-`（レビュー指摘表）、`BUG-`（バグ表）、`QA-`（QA表）、`ST01`（システムテストシナリオ）と混同しないよう、接頭辞は `QC-` に固定する。

### 2-2. 対象バージョン

指摘を受けたリリース候補のバージョン（例 `v1.0.0`）を記入する。[システムテスト報告書](../04_テスト/システムテスト報告書/README.md) のファイル名のバージョンと同じ表記にする。

### 2-3. 指摘者

指摘した品質管理部門の担当者の氏名を記入する。記入例や過去行から推定せず、確認結果の連絡から転記する。

### 2-4. 区分

指摘が何に対するものかを記入する。


| 区分         | 内容                                                 | バグ表への起票                                               |
| ------------ | ---------------------------------------------------- | ------------------------------------------------------------ |
| `不良`       | アプリケーションの動作・表示が仕様と異なる           | **必須**。`バグID` に未採番ファイル名または `BUG-nnn` を書く |
| `報告書`     | システムテスト報告書の記載・判定・対象外の理由の不備 | しない                                                       |
| `手順・運用` | 実施手順、テストデータ、リリース手順、運用上の懸念   | しない                                                       |
| `設計書`     | 要件・設計書と実装の乖離、設計書の記載不備           | 実装を直す場合だけ起票する                                   |
| `改善提案`   | 仕様どおりだが改善したほうがよいもの                 | しない（実施すると決めたら Issue または機能追加シートへ）    |
| `質問`       | 判断材料として品質管理部門が確認を求めたもの         | しない。回答を `対応内容` に書く                             |




### 2-5. 重要度


| 重要度   | 判断基準                                                                                       |
| -------- | ---------------------------------------------------------------------------------------------- |
| `要修正` | 仕様・基準に反する、またはリリース判定に影響する。**対応して再確認を受けるまでリリースしない** |
| `要検討` | 妥当性の判断が必要。対応するか見送るかを品質管理部門と合意してからリリース判定に進む           |
| `提案`   | 内容に問題はないが、改善したほうがよいもの。見送ってよい                                       |


`不良` の重要度（致命的／重大／中／軽微）はバグ表側に書く。本表の重要度は「リリース判定を止めるか」の観点だけで付ける。

### 2-6. 追跡情報


| 列           | 記入方法                                                                                                                                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 対象         | 指摘の対象を特定できる名前を書く。報告書なら `v1.0.0_システムテスト報告書.md 3章`、画面なら `SCRXX ○○画面` のように、ファイル名・章番号・画面IDで書く                              |
| バグID       | 区分 `不良` の場合に必須。起票直後は `バグ/未採番/` のファイル名（例 `yamada-20260910-133025`）、採番後は `BUG-nnn` に書き換える                                                                |
| PR           | 修正を含むPRの番号を `#12` 形式で記入する。PR作成後に追記する                                                                                                                                      |
| 修正コミット | リポジトリ内の実際の修正内容を含むコミットのハッシュを記入する。管理表だけを更新したコミットは記入しない。区分 `不良` でバグ表に修正コミットを書いた場合は、本表は空欄でよい（バグ表を正本とする） |
| 確認日       | 品質管理部門が対応内容を確認した日を記入する                                                                                                                                                       |
| 確認者       | 確認した品質管理部門の担当者の氏名を記入する。指摘者と別の人が確認した場合は `備考` に理由を書く                                                                                                   |
| 備考         | 代理確認、例外判断、補足事項がある場合だけ記入する                                                                                                                                                 |




### 2-7. 状態

`未対応` → `対応中` → `対応済` → `確認済` の順に遷移する。対応しないと判断した場合は `対応不要` とし、理由を `対応内容` に必ず書く。

- `対応済` … リポジトリ内の修正をコミットした、または報告書・手順書の修正を保存した状態。まだ品質管理部門の再確認を受けていない
- `確認済` … 品質管理部門が対応内容を確認し、指摘が解消したと合意した状態
- `対応不要` … 指摘が誤り、または今回対応しないと品質管理部門と合意したもの。**理由を書かずに** `対応不要` **にしない**

区分 `不良` の行は、バグ表側の状態が `確認済` または `取り下げ` になり、かつ品質管理部門の再確認を受けてから `確認済` にする。バグ表側だけを見て `確認済` にしない。

## 4. 運用

- 品質管理部門の確認結果を受け取ったら、その日のうちに指摘を本表へ起票し、区分 `不良` のものは `/bug-new` でバグ表へも起票する。
- リリース判定の前に、対象バージョンの `要修正`・`要検討` の指摘がすべて `確認済` または `対応不要` になっていることを確認する。残っている場合はリリース可と判定しない。`提案` は品質管理部門と合意のうえ次リリースへ持ち越してよい。
- 確認依頼日・承認者・最終結果は [システムテスト報告書](../04_テスト/システムテスト報告書/README.md) の「品質管理部門の確認」欄にも記録する。報告書は「そのバージョンが承認されたか」を、本表は「個々の指摘がどう決着したか」を持ち、役割を分ける。
- 同種の指摘が繰り返される場合は、[01_テスト方針](../04_テスト/01_テスト方針.md) とシステムテストシナリオの観点に不足がないかを見直す。見直したときは、その旨を `対応内容` に残す。
