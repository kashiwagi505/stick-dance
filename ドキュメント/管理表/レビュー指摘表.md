# レビュー指摘表

有識者から受けた紙面レビューの指摘と、その対応結果を一元管理する。指摘が放置されたまま次工程に進むことを防ぐ。他のコマンド・エージェントが章番号で参照しているので、**章番号は変えない**。

新規指摘は本表の3章へ直接追記する。担当者別の作業ファイルへ分けて起票しない（採番の運用は [管理表/AGENTS.md](AGENTS.md) を参照する）。

## 1. 管理対象

次の2つを本表で管理する。**社内で行うレビューの指摘を1つの表にまとめ、表を増やさないため。**

- **有識者からの紙面レビュー**（要件定義・基本設計・詳細設計・テスト観点表などを紙またはPDFに出力して有識者に確認してもらうレビュー）
- **納品前の最終確認（内部RV）**（納品直前に開発側で行う、納品物が納品できる状態かの確認。完成の定義と受け入れ条件は [納品・検収要件](../01_要件定義/05_納品・検収要件.md) を正本とする）。

以下は対象外。それぞれの記録先に従う。

| レビュー・不良 | 記録先 |
|---|---|
| 顧客から受けたレビュー | QA表（共有フォルダのExcel） |
| チーム内のPRレビュー（人） | PR上のやり取りで完結（→ [Git運用手順](../基準書/Git運用手順.md) 2章⑤） |
| AIによる自動レビュー（PR作成時） | PR上のやり取りで完結（→ [Git運用手順](../基準書/Git運用手順.md) 2章⑤） |
| テストで検出した不良 | [04_テスト/02_バグ表](../04_テスト/02_バグ表.md) |
| 品質管理部門がテスト工程で挙げた指摘 | [品質管理指摘表](品質管理指摘表.md) |

- **その場で即座に合意・修正が完了した軽微な指摘（誤字など）は、本表への登録を省略してよい。** 判断が分かれたもの、対応を見送ったもの、後続対応にしたものは必ず登録する。
- 対応方針をその場で決められない指摘は、GitHub Issueを起票せず、本表へ`未対応`として登録した時点で停止する。人間が「対応」または「見送り」を決めた後に、対応を再開する。

## 2. 記入ルール

### 2-1. 指摘ID

`REV-001` の形式で、プロジェクト全体を通した連番とする。取り下げた番号を再利用しない。

起票時に、本表3章の最大番号＋1 を付ける。起票直前に本表を再読み込みし、番号を確かめてから追記する。並行するブランチで同じ番号を付けてしまった場合は、後から `dev/自分の名前` または master へ取り込む側が自分の行を最大番号＋1へ振り直し、`備考` の末尾に「採番修正（日付）: 旧ID …」の形で当時の番号を残す。CI（`node .github/scripts/review-table.mjs check`）が本表のID形式と重複を検査する。

### 2-2. 固定値で記入する項目

有識者の紙面レビューは、次の固定値で記入する。

| 列 | 記入値 |
|---|---|
| レビュー種別 | `設計レビュー` |
| レビュー観点 | `有識者紙面レビュー` |
| 指摘者 | 未決（紙面レビューを依頼する有識者。担当: kashiwagi、決定期限: 最初の紙面レビューまで） |

納品前の最終確認（内部RV）は、`レビュー観点` を `納品前の最終確認` とし、`指摘者` に確認を実施した設計担当の氏名を記入する。`レビュー種別` は対象の成果物に合わせる。

指摘者の固定値が決まるまでは、依頼時に必ず氏名を明示する。決まった後も、固定値以外の人が指摘者となる場合だけ依頼時に氏名を明示する。記入例や過去行から指摘者を推定しない。

### 2-3. 区分

指摘がどの成果物に対するものかを記入する（`要件` / `基本設計` / `詳細設計` / `実装` / `テスト` / `ドキュメント` / `その他`）。

### 2-4. 追跡情報

| 列 | 記入方法 |
|---|---|
| PR | 修正を含むPRの番号を`#12`形式で記入する。PR作成後に追記する |
| 修正コミット | リポジトリ内の実際の修正内容を含むコミットのハッシュを記入する。管理表だけを更新したコミットは記入しない。デザインシステム（`02_基本設計/画面設計/デザインシステム/`）を含むすべての正本がリポジトリ内にあるため、変更は必ずコミットとして残る |
| 確認日 | 指摘者が修正内容を確認した日を記入する |
| 確認者 | 元の指摘者（通常は2-2の固定値の人）が確認した場合に氏名を記入する。別の人が代理確認する場合は「備考」に理由を書く |
| 備考 | 代理確認、例外判断、補足事項がある場合だけ記入する |

### 2-5. 重要度

| 重要度 | 判断基準                             |
| --- | -------------------------------- |
| 要修正 | 仕様・基準に反する。**修正するまで次工程に進まない**     |
| 要検討 | 妥当性の判断が必要。対応するか見送るかを合意してから次工程に進む |
| 提案  | 内容に問題はないが、改善したほうがよいもの。見送ってよい     |
|     |                                  |

### 2-6. 状態

`未対応` → `対応中` → `対応済` → `確認済` の順に遷移する。対応しないと判断した場合は `対応不要` とし、理由を「対応内容」に必ず書く。

- `対応済` … リポジトリ内の修正をコミットした、または外部正本の変更を保存・公開し、対象システム・更新日・更新箇所を記録した状態。まだ指摘者の確認を受けていない
- `確認済` … 指摘者が修正内容を確認し、指摘が解消したと合意した状態
- `対応不要` … 指摘が誤り、または今回対応しないと合意したもの。**理由を書かずに `対応不要` にしない**

## 4. 運用

- 紙面レビューの実施後、次工程に進む前に、そのレビューで受けた `要修正`・`要検討` の指摘がすべて `確認済` または `対応不要` になっていることを確認する。
- 同種の指摘が繰り返される場合は、[基準書](../基準書/)のレビュー観点に不足がないかを見直す。基準書を直したときは、その旨を対応内容に残す。
