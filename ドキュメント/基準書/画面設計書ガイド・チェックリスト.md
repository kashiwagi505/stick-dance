# 画面設計書ガイド・チェックリスト

画面設計書の作成・レビュー基準。新規作成には [画面設計書テンプレート](../テンプレート/画面設計書テンプレート.md) を使用し、同名モックアップも同時に更新する。

## 1. 基本方針

- 利用者から見える表示、入力（キーボード・クリック）、操作、音の鳴り方、メッセージ、画面の切り替えを定義する。
- 画面はブラウザ1枚の中での HTML の表示切り替えであり、ページ遷移ではない（→ [アプリケーション実装方針](アプリケーション実装方針.md) 3章）。切り替えの条件は外部仕様として記載し、関数名・モジュール名は記載しない。
- 外部への通信は無い（サーバーを持たない）。共有URLの作成・読み込みと楽器の音の読み込みは、画面から見た外部仕様（いつ起き、失敗したら画面がどうなるか）として記載する。
- モックアップで分かる見た目を文章で繰り返さず、表示条件・動作・例外を補う。
- 画面IDは画面一覧、機能IDは機能要件、共通外観は[デザインシステム](../02_基本設計/画面設計/デザインシステム/readme.md)とその同フォルダ配下を正本とする。
- 設計完了時に空欄、`TODO`、`TBD`を残さない。対象外は「対象なし」と書く。

## 2. 記載する内容

### 基本情報

画面ID、ページタイトル、表示条件（どの画面からどの操作で切り替わるか）、描画の実装場所（`src/view/` のどのファイルか）、モックアップ、関連機能を記載する。ページタイトルはデザインシステム「ブラウザのタブ名」の規則に従う。

### 表示・入力・操作

- 表示項目: データ、表示条件、時間とともに変わる表示（棒人間の動き・ループの進み・分身の数・鳴った瞬間に光る頭や音階など）を記載する。
- 入力項目: 種別、初期値、編集可否、選択肢、入力補助を記載する。
- 操作項目: ボタン・リンク・行クリック、表示・活性条件、処理概要を記載する。
- 一覧（楽器・分身など）: 並び順、件数、選択済みの表示を記載する。

### 入力チェックとメッセージ

- チェックタイミング、入力値保持、エラー表示、ゲームに渡すかどうかを記載する。
- 必須、文字数などは1条件1行とする。
- 具体的な入力上限値と利用者に表示するメッセージは画面設計を正本とし、`src/view/` の文言定義と一致させる（→ [アプリケーション実装方針](アプリケーション実装方針.md) 4章）。
- 受け付けない操作、共有URLの不備（壊れている・版が違う）、音の読み込みの失敗、ブラウザの制約（利用者の操作より前には音を鳴らせない）を区別する（→ 同5章）。
- 文言、表示位置、エラー後の画面状態を明記する。

### イベント・URL・遷移

- 初期表示と全操作について、切り替わる先の画面と、音の始まり・止まりを書く。
- URL の `#` 以降に記録が入っているときに開く画面（遊ばずに鑑賞を再生する）を書く。共有URLの形式は共有の処理設計と [アプリケーション実装方針](アプリケーション実装方針.md) 7章を正本とする。
- 共有URLの作成・読み込みの成功時と失敗時で、画面の状態と切り替え先を分けて書く。

## 3. 原則として記載しない内容

- TypeScriptの関数・型・モジュールの構成
- 描画処理（DOM操作・Canvas）、CSSの具体的コード
- デザインシステムやモックアップだけで一意に分かる色・位置・形
- 決定に至った経過（確定日、誰の承認で決まったか、どの確認事項で確定したか、「当初は〜としていた」「〜を削除した」等の変更の履歴）と、不採用になった案
- 表の分類名に付ける状態ラベル（「（採用確定）」「決定」など）。分類名は「デザイン」「URL」のように対象で書く

決まった結果だけを現在形で書く。経過はGitログと [レビュー指摘表](../管理表/レビュー指摘表.md) を正本とする。日付を残すと、後から読む人が「この日以降に変わっていないか」を確かめられないまま古い決定と誤読する。ただし**設計判断の理由**（なぜその仕様なのか）は経過ではないため残し、8章に書いてよい。日付も、画面に表示する文言（制定日・更新日）や測定条件の一部であれば残す。管理表の日付列・起票日・期限など、日付自体が記載内容である項目は対象外とする（[ドキュメント/AGENTS.md](../AGENTS.md)「書き方」）。

## 4. 作成手順

1. 機能要件、画面一覧、関連画面を確認し、[デザインシステム](../02_基本設計/画面設計/デザインシステム/readme.md)を開いて該当規定を確認する。
2. テンプレートから設計書と同名モックアップを作る。
3. 表示・入力・操作・エラー時の状態を両者で一致させる。
4. 共有URLを扱う画面なら、`#` 以降の扱いを共有の処理設計と照合する。
5. 次のチェックリストでレビューする。

## 5. レビューチェックリスト

### 基本・整合

- [ ] 画面ID、機能IDが関連文書と一致する。
- [ ] ページタイトルがデザインシステムの規則と実装（`index.html`・`src/view/`）・同名モックアップに一致する。
- [ ] 設計書、モックアップ、実装（`src/view/`）の意図が一致する。
- [ ] 共通の見た目が、確認時点のデザインシステムと一致する。
- [ ] 目的、利用者、表示タイミングが分かる。

### 項目・一覧

- [ ] 表示・入力・操作項目に漏れがない。
- [ ] 初期値、選択肢、並び順、選択済みの表示が分かる。
- [ ] 画像や楽器の音が読み込めないとき・読み込み中、分身が最大人数（5人）のときの表示を考慮している。

### 入力・メッセージ

- [ ] 必須・上限・境界が1条件1行で定義されている。
- [ ] 入力値保持とエラーの表示方法が分かる。
- [ ] 受け付けない操作、共有URLの不備、音の読み込みの失敗、ブラウザの制約が区別されている。

### URL・遷移

- [ ] 初期表示と全操作イベントが記載されている。
- [ ] 共有URLの扱い（`#` 以降・版違い）が共有の処理設計と一致する。
- [ ] 正常時と失敗時の表示・切り替え先が分かる。
- [ ] 踊っている途中で再読み込みしたとき・画面が隠れたときの扱いが実装方針3章と矛盾しない。

### 完了

- [ ] 表示幅・表示高さがデザインシステム「対応端末と表示幅」に沿っている（対象はPCのChromeだけ。→ [非機能要件](../01_要件定義/02_非機能要件.md) N1）。
- [ ] キーボード操作、色以外の状態表現を考慮している。
- [ ] 実装詳細の写経がない。
- [ ] 決定の経過（確定日、承認者、「当初は〜」）と、分類名の状態ラベルがない。
- [ ] 空欄、`TODO`、`TBD`がない。
- [ ] 納品対象でない資料（QA表の`QA-000`番号など）を参照して済ませていない。確定した内容が設計書の本文に書き切られている（[ドキュメント/AGENTS.md](../AGENTS.md)「書き方」）。
- [ ] 確定日・検討の経緯・不採用案が本文に残っていない（3章）。

AIレビューは最初に「問題なし」「要修正」「要確認」のいずれかを示し、対象、根拠、重要度、修正案または確認事項を報告する。
