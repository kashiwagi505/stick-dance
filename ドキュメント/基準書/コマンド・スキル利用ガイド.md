# コマンド・スキル利用ガイド

このプロジェクトで使えるAIエージェント向けのスラッシュコマンド・サブエージェント・外部スキルを、人間の開発メンバー向けに解説する。

- 本書は**解説**であり、手順の正本ではない。記述が食い違う場合は各正本（`.claude/commands/`、`.agents/`、各基準書）が優先する。
- ただし**一覧としては本書が唯一の置き場**。ルートの [AGENTS.md](../../AGENTS.md) はAI向けの入口であり、一覧を重複させない（コマンド・エージェントの説明文はツール側が自動で読み込むため）。コマンド・スキルを追加・削除したら本書を同じ変更で更新する。
- コマンド・スキル自体を追加・変更するときのルールは [エージェント・スキル設計基準書](エージェント・スキル設計基準書.md) を正本とする。

## 全体像

仕組みは4種類ある。

| 種類 | 呼び出し方 | 実体の置き場所 |
|---|---|---|
| スラッシュコマンド | ユーザーが `/コマンド名` で明示的に呼ぶ | `.claude/commands/` |
| サブエージェント | 依頼内容に合致するとAIが自動で委譲する | 入口 `.claude/agents/`、手順の正本 `.agents/` |
| 外部スキル | 依頼内容が説明文に合致するとAIが自動で読み込む | `.claude/skills/` |
| フック | ファイル編集などのイベントで機械的に発動する（Claude Codeのみ。AIの判断を介さない） | 定義 `.claude/settings.json`（`hooks`）、スクリプト `.claude/hooks/` |

## テストファースト開発パイプライン

機能実装は次の順でコマンドをつなぐ（正本: `04_テスト/01_テスト方針.md` 9章）。1人1ブランチ運用のため、PR作成はパイプラインの最後（`/run-impl-loop`）で1回だけ行う。

```text
/gen-e2e-scenario ──▶ 人レビュー・承認 ──▶ /gen-e2e ──▶ /gen-unit-test ──▶ /run-impl-loop（PR作成まで）
（E2E観点表を作る）                        （specを作る）  （単体テストを先に作る）（全件合格まで実装を反復）
```

パイプラインを使わない変更（ドキュメント修正など）は、作業完了後に `/create-pr` でPRを作る。PRを経ずにmasterへ反映してよいのは、`WBS/` 配下だけの変更を `/wbs-push` で反映する場合と、バグの採番と転記（毎朝9時に GitHub Actions の `bug-table-sync.yml` が自動で行い、すぐ確定したいときはkashiwagiだけが `/bug-sync` を実行）の2つだけ。バグの起票（`/bug-new`）は作業ブランチにファイルを足すだけで、通常のPRで流れる。PRのマージは、レビュー指摘への返信漏れを機械チェックする `/merge-pr` で行う。

ファイル編集を伴う作業は、1件目から `/worktree-start` で作業ツリーと作業ブランチ（`dev/自分の名前-作業名`）を作り、そこで行う。本体ツリーは `dev/自分の名前`（統合ブランチ）を置いて master を取り込み・作業ブランチを集め・PRを出すだけの場所で、編集しない（正本: [Git運用手順](Git運用手順.md)「1. ブランチ構成」「2. 日々の作業の流れ」）。作業が終わったら `/worktree-end` で `dev/自分の名前` へマージしてツリーを消し、続けて `/create-pr` で master へPRを出す。

## スラッシュコマンド一覧

### 開発パイプライン系

#### `/gen-e2e-scenario` — E2Eテスト観点表を作る

- **いつ使うか**: 画面の実装に着手する前。`/gen-e2e` の前工程。
- **入力**: 対象の画面ID・画面名。画面設計書が存在しない場合は作らずに終了する。
- **やること**: テスト方針とテンプレートに沿って観点表を作成し、ケースID（`SCRXX-NN`）を採番する。Codexレビューを通したうえで観点表だけをコミットする。
- **終わり方**: **人レビュー依頼で止まる**。承認前に自動で `/gen-e2e` へは進まない。

#### `/gen-e2e` — Playwright spec を作る

- **いつ使うか**: 観点表が承認された後。
- **入力**: 対象の画面ID。承認済み観点表がなければ `/gen-e2e-scenario` を案内して終了する。
- **やること**: 規約準拠のspecを作成し（`test`・`expect` は `fixtures/test` からimport、`saveEvidence` 必須）、`npm --prefix e2e test -- scrXX` で実行確認する。テストファーストの場合は「未実装が理由の失敗」までを確認し、`src/` は変更しない。
- **終わり方**: 観点表の自動化欄を `済` に更新してコミットする。

#### `/gen-unit-test` — 単体テストを実装より先に作る

- **いつ使うか**: 処理設計が完成した後、実装に入る前。
- **入力**: 対象機能名。処理設計がなければ着手しない。
- **やること**: 処理設計から単体テスト（Vitest、`src/**/*.test.ts`）を作成する。未存在の関数・型は骨格（中身は `throw new Error('未実装')`）だけ追加し、既存実装は変更しない。新規テストが「未実装が理由で失敗」し、既存テストが全件成功することを確認してコミットする。
- **終わり方**: 失敗するテストまでで止まる。実装本体は書かない（`/run-impl-loop` へ）。

#### `/run-impl-loop` — テスト全件合格まで実装を反復し、PR作成まで行う

- **いつ使うか**: 単体テスト・観点表・specといったハーネスが揃った後。
- **入力**: 対象機能名・画面ID。ハーネスがなければ各生成コマンドを先に実行するよう案内する。
- **やること**: 単体テストループ→対象E2Eループ→全件E2Eの順で、合格するまで実装と修正を繰り返す。区切りごとにコミットし、最後に設計書の連動更新確認・master取り込み・`npm run check`・push・PR作成まで行う。デザインシステムを変更した場合は、変更した節・影響成果物をPR本文へ記録する。
- **安全装置**: テストの期待値書き換え禁止。同じ失敗が3回続いたら停止して報告する。
- **証跡の残り方**: E2Eのスクリーンショット証跡は実行のたびに `e2e/evidence/` へ再生成され、Git管理しない（ローカルで人がレビューする）。PRに残るのはテスト結果の記載とCIの `npm run check` 結果。リリース時だけ `04_テスト/エビデンス/<バージョン>/` へ凍結してコミットする（正本: テスト方針4-5・4-6）。

#### `/create-pr` — 統合ブランチへのマージ・テスト・push・PR作成

- **いつ使うか**: パイプラインを使わない作業（ドキュメント修正・小さな変更）の完了時。通常は `/worktree-end` がマージと片付けを済ませたあと、本コマンドの「push と PR 作成」へ続けて入る。`/run-impl-loop` 実行中は対象外（そちらがPRを作る）。
- **入力**: 今回作業の一言説明（省略可）。`master` ブランチにいる場合は停止する。
- **やること**: 未コミット変更のコミット→設計書の連動更新確認→`dev/自分の名前` のmerge取り込み（rebase禁止）→`npm run check`→`dev/自分の名前` へマージ（**PRは出さない**）→push→`gh pr create`（本体ツリーの `dev/自分の名前` → `master`）。既にPRが開いていれば新しく作らずpushで更新する。デザインシステムを変更した場合は、変更した節・影響成果物をPR本文へ記録する。
- **終わり方**: PRのURL・変更概要・テスト結果を報告する。既存PRを更新した場合はその旨を明記する。

#### `/merge-pr` — レビュー指摘への返信漏れをチェックしてPRをマージする

- **いつ使うか**: PRのレビューが済んでマージするとき。マージはこのコマンド経由で行う（正本: Git運用手順⑥）。GitHubのマージボタンは使わない。
- **入力**: PR番号（省略時は現在ブランチのPR）。
- **やること**: コンフリクトの確認→CI相当のローカル検査（向き先・バグ表・レビュー指摘表）→AIレビュー（未実施のときだけ。指摘はPRへ投稿して停止）→全レビュースレッドを取得し、**返信がない指摘**があれば一覧を提示して停止→approveの有無を確認→コードが変わっていれば `npm run check`→問題なければ Create a merge commit でマージする。このコマンド自体は指摘への**返信**を投稿せず、マージ可否の判定だけを行う（返信の書き分けは Git運用手順⑥）。
- **終わり方**: マージしたPRのURLとチェック結果、または停止理由と次にやる操作を報告する。
- **Actions に依存しない**: CI相当の検査とAIレビューをローカルで回すので、Actions が止まっていても（課金・無料枠超過）マージできる。Actions を常用する場合は [merge-pr.md](../../.claude/commands/merge-pr.md) の「Actions を常用する場合」。

#### `/front-design` — 画面UIをデザインシステムの流儀で設計・実装する

- **いつ使うか**: 画面の見た目を追加・変更するとき。
- **入力**: 対象画面と直したい点。
- **やること**: `ドキュメント/02_基本設計/画面設計/デザインシステム/` を開き、画面設計書・同名モックアップとあわせて確認する。公式プラグイン `frontend-design` を併用し、既存トークン・規則を踏襲した設計→自己批評→実装を行う。
- **終わり方**: 設計書とモックアップの両方を更新する。**コミットはしない**。

#### `/reverse-docs` — 実装の内容を設計書へ反映する（リバース反映）

- **いつ使うか**: 実装が確定しているのに設計書が古い・存在しないとき。設計書側を実装へ追従させる（コードは変更しない）。
- **入力**: 対象範囲（機能名・画面ID・ファイルパスのいずれか。省略時は `origin/master` との差分）。
- **やること**: 乖離検出を `doc-sync-checker` に委譲し、乖離ごとに「実装が正／実装バグ疑い／要確認」へ仕分けて一覧を提示、**人の承認を得た項目だけ**を各設計書ガイドに従って設計書へ反映する。バグ疑いはバグ表への起票を案内し、設計書には反映しない。
- **終わり方**: 反映した設計書だけをコミットし、除外した項目と要確認事項を報告する。PRは `/create-pr` で作る。

### タスク管理（WBS）系

#### `/wbs-new` — タスクを起票する

- **入力**: やること・担当・期日・見積（分かる範囲でよい。不足分は聞かれる）。
- **やること**: `WBS/タスク/` の重複を確認し、所定のプロパティでタスクファイルを作成する。1日7hを超える負荷には警告が出る。マイルストーンは `【MS】` 接頭辞・見積0で起票する。
- **注意**: コミットはしない（共有は `/wbs-push`）。

#### `/wbs-close` — タスクの状態と実績工数を反映する

- **入力**: 今日やったこと（話し言葉でよい）。
- **やること**: 該当タスクを特定し、実績工数を**加算**、状態を更新、メモを追記する。時間を伝えていなければ実績は変更されない。他人が担当のタスクは実行前に確認される。
- **注意**: コミットはしない（共有は `/wbs-push`）。

#### `/wbs-push` — WBS配下だけの変更をPRなしでmasterへ反映する

- **入力**: 変更の一言説明（省略可）。
- **やること**: `WBS/` 配下だけをコミットし、一時worktree経由でmasterへcherry-pick＆pushし、自分のブランチにも取り込む。タスクだけでなく、ダッシュボード・テンプレート・振り返り・`WBS/AGENTS.md` などWBS配下すべてが対象。`WBS/` 以外のファイルが混ざっている場合は対象外（`/create-pr` を使う）。

### 作業ツリー系

`/pull` で master を取り込み（①）、作業1件＝作業ツリー1つを `/worktree-start` で始め（②）、`/worktree-end` で閉じる（④）。正本: [Git運用手順](Git運用手順.md)「2. 日々の作業の流れ」。

#### `/pull` — 本体ツリーに master の最新を取り込む

- **いつ使うか**: セッション中に master が進んだとき、人が明示的に取り込みたいとき。**開始時の取り込みは人が呼ばなくてよい**——本体ツリーのセッションは `session-start` フックが知らせた未取り込み件数を見て、指示を待たずに取り込む（正本①）。
- **入力**: なし。
- **やること**: 本体ツリーで `dev/自分の名前` にいることと未コミット変更が無いことを確認 → `git fetch origin` → 未取り込み件数の確認（0なら何もせず終了）→ `git merge origin/master` → コンフリクトの解消 → `git commit --no-edit` → `git push`。
- **コンフリクトの扱い**: どちらを採るかを**AIが勝手に決めない**。両側の内容と解消案を示してユーザーに決めてもらう。「片側が起票直後の空欄・もう片側が記入済み」のように履歴から新しい意図が一方に確定するものだけ解消して報告に回す。途中のままセッションを終えず、続けられなければ `git merge --abort` で戻す。
- **対象外**: 作業ツリーにいるセッション（作業ツリーへ最新を入れるのは `dev/自分の名前` からの取り込みで、`/worktree-end` が行う）。
- **終わり方**: 取り込んだコミット数、コンフリクトがあれば採った側とその理由、push 後に master より何コミット先行しているか（溜まっていれば `/create-pr` を提案）を報告する。

#### `/worktree-start` — 作業ツリーと作業ブランチを作って移る

- **いつ使うか**: ファイル編集を伴う作業を始めるときすべて（他のセッションがいるかどうかは関係ない）。本体ツリーで最初の Edit / Write をする前。
- **入力**: 作業名（英小文字とハイフン。例 `scr14-impl`）。
- **やること**: 本体ツリーの未コミット変更の確認（あれば誰の変更かを確認。`git stash` は使わない）→ `dev/自分の名前` から作業ブランチ `dev/自分の名前-<作業名>` を切って `.claude/worktrees/<作業名>` にツリーを作成 → そのツリーへ移動。**置き場所を `.claude/worktrees/` の外にしない**（外へ移ると Claude Code が移動のたびに確認を求め、許可設定では抑制できない）。**実装（`src/`・`e2e/`・`index.html`・`package.json` などの設定ファイル）を触る場合だけ**、`.env` を複製する。実装ツリーが自分1本だけなら既定のポートのまま使い、2本以上並ぶときだけ空きを実測して `SERVER_PORT` を分ける。
- **軽量版が既定**: ドキュメント・設計書・モックアップ・WBSだけの作業では `.env` を作らない。途中で実装を触ることになったらそこで追加する。
- **対象外**: `WBS/` 配下だけの作業（`/wbs-push` がパス指定で反映するため分離不要）。すでに作業ツリーにいるセッション。
- **終わり方**: ツリーのパス・ブランチ名・軽量版かフル版か（フル版ならポート）を報告する。分離できない場合は原因を報告して停止する（本体ツリーのまま作業を続けない）。

#### `/worktree-end` — 作業ツリーを閉じる（`dev/自分の名前` へマージ → 片付け → PR）

- **いつ使うか**: 作業ツリーでの作業がひと区切りついたとき（1日1回以上を目安に溜めない）。`session-start` フックが知らせた片付け忘れのツリーを、作業名指定で消すとき。
- **入力**: 作業名（省略時は現在のツリー）。
- **やること**: 未コミット変更のパス指定コミット → 作業ツリーで `dev/自分の名前` を取り込み（rebase禁止）`npm run check` → 作業ブランチを push → `ExitWorktree` で本体ツリーへ戻り `git merge --no-ff` で `dev/自分の名前` へマージして push（**PRは出さない**）→ ツリー（`git worktree remove` が失敗したら実体を消して `git worktree prune`）・ローカルとリモートの作業ブランチの削除 → 続けて `/create-pr` の「push と PR 作成」を実行する。
- **終わり方**: `git worktree list` の結果、消したツリー・ブランチ、PRのURL、`npm run check` の結果を報告する。判断できない未コミット変更や未マージのブランチがあれば消さずに停止する。

### ルール整備系

#### `/rule-new` — 繰り返している指示を仕組みに上げる

- **いつ使うか**: 同じ趣旨の指示を3回以上打っていると気づいたとき（`prompt-log` フックが提案する）。
- **入力**: 毎回打っている指示の内容。
- **やること**: 対象を1文にし、曖昧な言葉を数値・明確な条件へ置き換える。そのうえで**人に2問聞く**。①恒久か暫定か（暫定なら撤回条件・撤回時にやること・Issueを決める）②守る道は守らない道より手間か（手間でなければ正本に1行書くだけ。手間なら**ブロックする**仕組みを決める）。決められなければ**書かずに止まる**。
- **やらないこと**: ルールの自動生成。リマインドだけの仕組み。
- **終わり方**: 書いた1文・置き場・検査方法とその動作確認の結果を報告し、パス指定でコミットする。

#### `/rule-review` — 繰り返している指示と失効した暫定ルールを棚卸しする

- **いつ使うか**: 週1回。
- **やること**: `.claude/tmp/prompt-log.jsonl` を**意味でまとめ**（フックが拾えるのは字面の近いものだけのため）、3回以上のグループを「未記載＝仕組みに上げる候補」と「**記載済みなのに繰り返されている＝検査方法が無い**」に仕分ける。あわせて [暫定ルール](暫定ルール.md) の撤回条件を確認する。
- **終わり方**: 一覧を提示する。ルールの追加・撤回は人の判断を得てから行う。

### 記録・起票系

#### `/bug-new` — バグを起票する（番号は付けず、未採番ファイルを作業ブランチに1つ足す）

- **いつ使うか**: [バグ表](../04_テスト/02_バグ表.md) 1章の管理対象に当たる不良を**起票**するとき。作業ツリーの作業ブランチで呼ぶ（本体ツリー・master では動かない）。
- **入力**: 対象・事象・検出工程がわかる説明。不足していれば聞かれる（推測で埋めない）。
- **やること**: `origin/master` のバグ表3章と自分のブランチの `未採番/` で重複を確認 → `04_テスト/バグ/未採番/<担当者ローマ字>-<YYYYMMDD>-<HHmmss>.md` を1つ作る（見出しはファイル名と同じ。`BUG-` は書かない）→ 書式を検査してそのファイルだけをパス指定でコミット。push はしない（作業の区切りで `/worktree-end` → `/create-pr` が通常どおり流す）。番号と表は触らない。
- **なぜ必要か**: バグIDはブランチをまたぐ共有カウンタで、各ブランチで採ると並行ブランチと取り合う（前案件では採番のやり直しが繰り返し発生した）。起票では番号を付けず、番号を付ける処理を master 上の `/bug-sync`・Actions に限ることで取り合いを無くす（バグ表2-1）。起票が master への直接 push を伴わないので、通常の作業と同じ流れで自動化できる。
- **対象外**: 既存バグの更新（`対応内容`・`修正コミット`・`状態`・`確認日`・`密度計上`）。これは修正と同じ作業ブランチでバグ表3章の該当行を編集し、通常のPRに含める。採番と表への転記（`/bug-sync`・Actions）。レビュー指摘表も対象外（表へ直接起票する。正本は `ドキュメント/管理表/AGENTS.md`）。
- **安全装置**: コミットが未採番ファイル1つだけであることを検証する。ファイル名・見出し・書式の違反はPRのCI（「バグ表の検査」）が落とす。

#### `/bug-sync` — 未採番のバグに BUG-nnn を付け、バグ表3章の表へ転記する（kashiwagiだけが実行）

- **いつ使うか**: 日中にすぐ番号を確定したいとき（修正に着手する前、顧客提出・不良密度の集計・リリース判定の前）。毎朝9時（JST）に GitHub Actions（`.github/workflows/bug-table-sync.yml`）が同じ処理を自動で行うので、翌朝まで待てるなら呼ばなくてよい。自動実行が動かなかったとき（Actions の失敗・無効化）にも手で呼ぶ。**実行者はkashiwagiだけ**。他の人が呼ぶと何もせず停止する。
- **入力**: なし。
- **やること**: 一時worktreeを `origin/master` の上に作り、`node .github/scripts/bug-table.mjs check`（表と未採番ファイルの書式・重複の検査）→ `sync`（`未採番/` を検出日→ファイル名の順に最大＋1から採番して3章の表の末尾へ転記し、元のファイルを消す）→ `バグ/` 配下と `02_バグ表.md` だけをコミットして master へ push → 自分のブランチへ取り込む。未採番が無ければ何もしない。
- **なぜ必要か**: 番号を付ける場所を master の1か所に限れば採番の取り合いが起きない。
- **対象外**: バグの起票（`/bug-new`）と内容の変更（作業ブランチでファイルを編集して通常のPR）。`check` で見つかった書式違反もここでは直さない（停止して報告する）。

#### `/bug-verify` — `修正済` のバグを再テストして `確認済` にする（再発したものは直す）

- **いつ使うか**: 修正が一区切りついたあと、リリース判定の前。リリース判定の基準は「バグ表の不良がすべて `確認済` または `取り下げ`」（[テスト方針](../04_テスト/01_テスト方針.md) 2章）で、`修正済` が残っているかぎり判定を通せない。`/worktree-start bug-verify` の**フル版**で呼ぶ。
- **入力**: なし（1件だけ確認するときは `BUG-nnn` か未採番ファイル名）。
- **やること**: バグ表3章と `未採番/` の両方から `状態` が `修正済` のものを洗い出す → 1件ずつ、事象に書かれた期待結果を根拠に合格条件を決め、**自動／目視／環境待ち**へ仕分ける → 自動分は `npm run check`・該当E2Eを実行して全件成功を確かめる → **事象が再発していたらその場で直し、落ちたテストと `check` が通るまで最大3回繰り返す**（通れば `確認済`。3回で通らなければ途中の修正コードを捨てて `対応中` へ戻し、人の判断待ちへ積んで次のバグへ進む） → 目視分は「開くURL・前提・見る場所・期待」を書いた一覧にして人へ渡し、人の確認を待つ → 環境待ちは `修正済` のまま据え置き、備考の「残る確認」を書き直す → 確認できたものに `状態`＝`確認済`・`確認日`・備考（確認方法と確認者、再発して直した件は原因と追加修正のコミット）を書いてパス指定でコミットする。
- **なぜ必要か**: `修正済` は「直したつもりだが事象が消えたのを見ていない」状態で、修正した本人の記憶では消化できない。自動で確かめられるものを機械的に片づけ、**人が見るしかないもの・人が決めるしかないものだけを、見る場所や選択肢つきで人へ渡す**ことで、リリース判定に必要な「残り `修正済` 0件」へ寄せる。再発を突き返さずここで直すのは、`修正済` → `対応中` → `修正済` の往復が1件あたり数日かかるため。
- **対象外**: `未対応`・`対応中` のバグの修正（このコマンドが直すのは**再テストで落ちた `修正済` だけ**）、採番と転記（→ `/bug-sync`）、起票（→ `/bug-new`）。再テストで見つかった**別の**事象は元のバグ票へ書き足さず `/bug-new` で起票する。
- **安全装置**: 自動テストが**あっても事象を検知できない**ものは目視へ回す（名前で要素を取るE2Eは並び順の不良を落とせない）。AIのスクリーンショット判断で `確認済` にしない。環境待ち（耳で聞かないと分からない音の不良、公開先の GitHub Pages でしか起きない不良など）を代替手段（音符の並びの単体テスト・開発サーバーでのE2E）の確認で `確認済` にしない。**修正は同じバグにつき3回まで**で、設計書と実装のどちらを直すか決まらないもの・他機能の仕様に波及するものは回数に関係なく人の判断待ちへ回す。前の修正で何が足りなかったかを言えないまま直さない。打ち切った件の途中までのコードはコミットしない。直した件は備考にその経緯を残し、**自分で直して自分で `確認済` にしたことがPRのレビューで見える**ようにする。

#### `/issue-new` — 課題・アイデアをGitHub Issueに起票する

- **入力**: 気づいたこと・アイデアの一言。
- **やること**: 重複を確認し、ラベル（`課題`/`アイデア`）を付けて起票する。本文は分かる範囲だけ書き、担当・期日・優先度は付けない（選別は週1回別途）。
- **対象外**: PM・顧客からの指摘、PRレビュー指摘、決定済みタスク（それぞれの記録先を案内される）。

#### `/issue-start` — Issueの内容と現状を報告してから着手する

- **入力**: Issue番号。
- **やること**: Issueとコメントを読んで平易に要約し、**ファイルを変更する前に**該当箇所の現状（実装・設計書・テストの今の姿、事象が今も再現するか）を調べて報告する。1ブランチ1PRで終わる規模かを判定し、直し方が2つ以上あるものは選択肢を示して人に決めてもらう。承認を得てから `/worktree-start` で作業ツリーへ移る。
- **いつ使うか**: 「issue#Nに対応したい」「#Nについて教えて」と言うとき。
- **対象外**: 起票（→ `/issue-new`）、複数PR・日をまたぐ規模（→ `/wbs-new`）、システムテストの不良（→ `/bug-new`）、PRのレビュー指摘（→ `pr-review-resolution`）。

## フック一覧

Claude Codeがツールを実行したタイミングで機械的に発動する。AIの判断を介さないため、リマインドの抜けが起きない。Codexにはフック機構がないため、同じルールはルート `AGENTS.md` の作業表とPRレビュー（`codex-pr-reviewer`）で担保する。

**標準入力の読み取りは `.claude/hooks/hook-input.ps1` に共通化している。** Claude Code はフックへUTF-8のJSONを標準入力で渡すが、Windows PowerShell の `[Console]::InputEncoding` は既定が shift_jis で、そのまま読むと日本語が化ける。さらにバイト境界によっては2バイト文字がJSONの区切り記号（`"` や `}`）を飲み込み、パース自体が失敗する。各フックはパース失敗時に素通りする作りのため、`prompt-log` は記録を落とし、`worktree-guard` と `safe-commit-guard` は拒否すべき操作を通していた（前案件で発生）。日本語を含む依頼で不定期に起きるため気づきにくい。

共通関数はコンソールのエンコーディングに依存せず標準入力をUTF-8として読み、**パースに失敗したら `.claude/tmp/hook-errors.log` へ1行（日時・フック名・理由・入力の先頭120文字）残す**。フックの振る舞い（素通り）は変えない。正常なら作られないファイルなので、**存在すること自体が異常のサイン**になる。前案件で5日間気づかなかったのは、失敗が何の痕跡も残さなかったため。

#### `ui-change-bug-reminder` — UI変更のバグ起票リマインド

- **発動条件**: `src/view/` 配下またはルートの `index.html` を Edit / Write で変更したとき（セッションにつき1回）。
- **やること**: 「実装完了後の画面へのUI変更はバグ表への起票が必須（[02_バグ表](../04_テスト/02_バグ表.md) 1章）」というリマインドをAIのコンテキストへ注入する。起票の書式は `.agents/harness-resolution.md` のバグ書式。
- **実体**: `.claude/hooks/ui-change-bug-reminder.ps1`（Windows PowerShell 5.1で動作）。

#### `safe-commit-guard` — 巻き込みコミット・統合ブランチへの直接コミット・stash を拒否する

- **発動条件**: `git commit` または `git stash` を含むコマンドを実行しようとしたとき（`PreToolUse`）。`git -C <パス>` があればそのリポジトリで判定する。
- **やること**: 次を**拒否**する。①パス指定のない `git commit`、`git commit -a`、`git commit --amend`。②`master`・`dev/自分の名前`（統合ブランチ）上でのコミット（`WBS/` 配下をパス指定した `/wbs-push` のコミットは例外）。③stash を作る操作（`git stash`、`git stash push`・`save`）。コンフリクト解消中（`.git/MERGE_HEAD`・`CHERRY_PICK_HEAD` がある）は index 全体のコミットが正しいため許可し、`git merge --no-ff` による統合ブランチへのマージもこれで通る。`git stash list`・`show`・`pop`・`apply`・`drop` は残った stash の確認・復元・破棄のために許可する。
- **なぜ拒否か**: 素の `git commit` は `git add <パス>` の直後でも index 全体を拾い、並行セッションの変更まで取り込む。統合ブランチへの直接コミットは作業ブランチのマージ先を塞ぐ。stash は他セッションの未コミット変更を巻き上げ、復元されずに残る（正本: [Git運用手順](Git運用手順.md)「1. ブランチ構成」「4. 並行作業（複数セッション）」）。
- **実体**: `.claude/hooks/safe-commit-guard.ps1`。

#### `worktree-guard` — 本体ツリーでの編集を拒否する

- **発動条件**: ファイルを Edit / Write しようとしたとき（`PreToolUse`）。
- **やること**: 本体の作業ツリーにいれば、他のセッションの有無にかかわらず編集を**拒否**し、`/worktree-start` で作業ツリーを作るよう求める。他セッションが動いていればその件数、同じファイルを編集済みならその旨も伝える。作業ツリーにいても、ブランチが `master` か `dev/自分の名前` なら拒否する。
- **対象外**: `WBS/` 配下、リポジトリ外のファイル、`.claude/hooks/` 配下。
- **なぜ拒否か**: 本体ツリーは `dev/自分の名前` を集めてPRを出す場所で、index がきれいでないとマージを受けられない。「他のセッションがいるときだけ分ける」運用では、2本目が本体ツリーで始まった時点で両方が編集できなくなった。
- **実体**: `.claude/hooks/worktree-guard.ps1`。

#### `prompt-log` — 繰り返している指示を数えて仕組み化を提案する

- **発動条件**: 人がプロンプトを送ったとき（`UserPromptSubmit`）。スラッシュコマンドの呼び出しと4文字未満は対象外。
- **やること**: プロンプトを正規化（全角→半角、記号除去、依頼表現の語尾「〜してほしい／〜して下さい」を除去）して `.claude/tmp/prompt-log.jsonl` へ記録し、同趣旨が**3回目**になったら `/rule-new` の提案を1回だけ注入する。同趣旨の判定は文字bigramの包含率0.8かつJaccard係数0.4以上。
- **なぜ3回か**: 2回だと失敗時のリトライ（実測23回）まで拾ってしまう。3回以上に絞ると仕組み化に値する候補だけが残る。
- **限界**: 拾えるのは字面の近い繰り返しだけ。言い回しの違う繰り返しは `/rule-review` が読んでまとめる。
- **記録の扱い**: `.claude/tmp/` はGit管理しない（`.gitignore` 済み）。ローカル限定で、作業ツリーごとに別のファイルになる。
- **実体**: `.claude/hooks/prompt-log.ps1`。

#### `session-start` / `session-track` — セッション登録簿、master未取り込みと片付け忘れの点検、暫定ルールの読み込み

- **発動条件**: セッション開始時（`SessionStart`）と、ファイルを Edit / Write した直後（`PostToolUse`）。
- **やること**: 稼働中セッションを `%TEMP%\棒人間ダンシング-sessions\` へ登録し、心拍（最終更新時刻）と編集したファイルを記録する。最終更新から15分を過ぎた登録は死んだものとして無視し、24時間を過ぎた登録はファイルごと消す。`session-start` は本体ツリーにいるセッションへ「ここでは編集せず `/worktree-start` で作業ツリーを作る」ことを伝え、あわせて次を点検して知らせる。①**master の未取り込み**（`git fetch origin` して `dev/自分の名前..origin/master` を数え、1以上なら「人の指示を待たず取り込む」ことを伝える。取り込みそのものは行わない——コンフリクトの判断が要るため。`FETCH_HEAD` が10分以内に更新されていればfetchを省く）、②本体ツリーの未コミット変更、③残っている作業ツリー（`dev/自分の名前` へ取り込み済みで未コミット変更のない「片付け候補」、未反映の「作業中」、`git worktree list` に載っていない「残骸」に分けて）、④残っている `git stash`。**有効な暫定ルールがあればコンテキストへ読み込ませる**（「着手前に読む」と書くだけでは守られないため、機械的に入れる）。
- **なぜ必要か**: `/worktree-end` を呼ばずにセッションが終わるとツリー・ブランチが残り、次の判断を誤らせる。開始時に機械的に点検することで片付け忘れを翌セッションで回収する。登録簿は `worktree-guard` が「他に何本動いているか」「どのファイルが取り合いになっているか」を伝える材料にもなる。
- **実体**: `.claude/hooks/session-start.ps1`、`.claude/hooks/session-track.ps1`、共通処理は `.claude/hooks/session-registry.ps1`。

## モデルの使い分け（要点）

原則は「仕様を決める側は上位モデル、仕様に従う側は低コストモデル」。工程ごとの目安は次のとおり（サブエージェント・コマンドの実際の指定は各入口ファイルを正本とする）。

- 計画・タスク分解・テスト設計: Claude Opus（メインセッション）
- 調査・E2Eコード化・レビュー系サブエージェント: Claude Sonnet
- 実装本体: Codex Terra、定型実装: Codex Luna
- PR最終レビュー: Codex（`codex-pr-reviewer` 手順）
