# エージェント・スキル設計基準書

Claude Code、Codex等で再利用するエージェント手順・スキルを作成または変更するときのルール。

## 正本と入口

手順の全文はツール非依存の正本へ集約し、ツール別入口には複製しない。

```text
.agents/<name>.md              ← 手順の正本
.claude/agents/<name>.md       ← Claude Code入口（frontmatter＋正本参照のみ）
.codex/agents/<name>.toml      ← Codex入口（モデル設定＋正本参照のみ）
AGENTS.md                      ← 全ツール共通の作業入口
.claude/skills/<name>/SKILL.md ← Claude固有スキルが必要な場合だけ
.claude/hooks/<name>.ps1       ← フック（Claude Code固有。定義は .claude/settings.json の hooks）
```

フックはAIの判断を介さず機械的に発動する仕組みで、Codexには存在しない。フックで担保するルールは、Codex側でも効くようにルート `AGENTS.md`・各正本・レビュー手順のいずれかへ同じルールを明文化する。

エージェントを作成するときは、次の3ファイルを同じ変更で揃える。

| ファイル | 書くこと |
|---|---|
| `.agents/<name>.md` | 手順の全文（正本）。モデル・エフォートは書かない |
| `.claude/agents/<name>.md` | frontmatterに`name`・`description`・`tools`・`model`（必要なら`effort`）。本文は正本を読ませる1行だけ |
| `.codex/agents/<name>.toml` | `name`・`description`・`model`・`model_reasoning_effort`。`developer_instructions`で正本を読ませる |

### 例外

片方のツールでしか成立しないエージェントは、その入口だけを置いてよい。組み込みエージェントの上書き（`.claude/agents/explore.md`によるClaude Codeの`Explore`のモデル固定）のように、内容が入口の仕組みと不可分でツール非依存にできないものは、`.agents/`の正本を置かなくてよい。例外にした場合は、その理由を`.agents/README.md`の一覧に書く。

### ファイル名

- `.agents/` と `.claude/agents/` はケバブケース（`harness-resolution`）。
- `.codex/agents/` はスネークケース（`harness_resolution`）。Codexのエージェント名にハイフンを使えないため。
- 3者の対応関係は `.agents/README.md` の一覧で示す。

## 作成判断

- 同じ依頼を繰り返す、手順飛ばしが起きる、専門的な検査順序が必要な場合に作成する。
- 一度しか使わない作業や、数行のルート規約で十分な内容は独立エージェントにしない。
- レビュー専用と自動修正を混ぜない。状態変更を伴う手順は権限・停止条件・確認方法を明示する。
- 状態変更を伴うClaude Code入口は、frontmatterの`tools`に必要最小限のツールを明示する。`tools`は実行可能な能力を限定するものであり、編集・Bash実行に対するClaude Codeの承認設定を無効化しない。

## 書き方

既存の `.agents/impl-policy-reviewer.md` を手本に、原則として次の順で書く。

1. 対象と対象外
2. 実行手順
3. チェック項目と根拠
4. 出力形式と終了条件

- パス、コマンド、ファイル名は棒人間ダンシングで実在するものを使う。

### レビュー系手順書の場合

- レビューは `git diff HEAD` または指定ブランチとの差分を基本にする。
- 指摘にはファイル、行、根拠、重要度、修正案を含める。
- 指摘ゼロを明言し、断定できない事項は「要確認」とする。
- 依頼がない限りファイルを修正しない。

## モデル設定と自動委譲

モデルとreasoning effortはツール別入口で指定し、ツール非依存の`.agents/<name>.md`には記載しない。

- Claude Codeは`.claude/agents/<name>.md`のfrontmatterに`model`と必要な`effort`を指定する。`model`省略時は`inherit`とする。
- Codexは`.codex/agents/<name>.toml`に`name`（ファイル名と一致させる）、`description`、`developer_instructions`、`model`、`model_reasoning_effort`を書く。
- レビュー系Claude Codeエージェント（impl-policy-reviewer、doc-sync-checker、codex-pr-reviewer）は`model: sonnet`を明示し、呼び出し元のモデルに依存させない。
- Fableは1アカウント限定のため工程の前提にしない。使える環境では難所の再診断・重要機能のテスト設計に任意で充てる。

### 自動委譲の仕組み

Claude Codeは各サブエージェントの `description` を見て、明示指示がなくてもタスクに合致すれば自動委譲する。したがって:

- `description` には「何をするか」に加えて「どういうときに使うか」を書く。
- 調査の自動委譲先は組み込みの `Explore` だが、モデルが呼び出し元に追従してしまうため、`.claude/agents/explore.md` で同名エージェントを定義して `model: sonnet` に固定している（組み込みを上書きする公式の仕組み）。

Codexのカスタムエージェントも`.codex/agents/<name>.toml`の`description`に使用条件を書く。確実な委譲が必要な手順は、ルート`AGENTS.md`の該当作業行でカスタムエージェント名を指定する。

### テスト先行と検証ループ

運用の正本はテスト方針9章。工程は次のスキルで運転する（`.claude/commands/`）。

1. Planモードで該当設計書を読み、計画を立てる。
2. `/gen-e2e-scenario <画面ID>` で観点表を作り、Codexレビュー→人のレビューの順で通す（承認前にコード化へ進まない）。
3. `/gen-e2e <画面ID>` で観点表からPlaywright specとテストデータ実体を作る（レビューなし。実行による失敗理由の確認とPRレビューで担保）。
4. `/gen-unit-test <機能名>` で処理設計から失敗する単体テストと骨格を作り、Codexレビューを経てコミットする。
5. `/run-impl-loop <機能名・画面ID>` で `npm run check`・E2Eが全件成功するまで実装を反復し、連動更新→PR作成まで行う。
6. PR作成時の自動レビュー（codex-pr-reviewer＋実装方針レビュー）の指摘には必ず返信する。対応した事実はAIが書いて投稿してよいが、対応しない判断は人が決める（[Git運用手順](Git運用手順.md)⑥）。

各スキルは成果物を対象ファイル明示でコミットして終了する。PR作成は `/run-impl-loop` の完了時だけ（1つの作業ブランチにつきPRは1つ）。パイプラインを使わない変更（ドキュメントのみの修正・小さな改修など）のPRは `/create-pr` でGit運用手順③〜⑤を実行して作成する。

### 画面のループ改善

- チェックは「実装画面のスクリーンショットと同名モックアップの比較」。差分を列挙→修正を1ループとする。
- 終了条件（差分ゼロ、または該当E2Eシナリオの通過）を開始前に決める。

## 連動更新

スラッシュコマンド・サブエージェント・スキル・フックを追加・削除した場合は次を同じ変更で更新する。

- [コマンド・スキル利用ガイド](コマンド・スキル利用ガイド.md) の該当一覧。**人間向けの一覧はここが唯一の置き場**で、ルート `AGENTS.md` には一覧を転記しない
- `.agents/README.md` の一覧
- `.claude/agents/` の入口
- `.codex/agents/` の入口
- レビュー系を追加・削除した場合は、ルート `AGENTS.md` の「レビューを依頼されたとき」の表
- 必要に応じて本書

## 検証

- Windowsパス、日本語パスを扱える。
- 正本と入口のリンク切れ・手順重複がない。

### レビュー系手順書の場合

- 違反を含む小さな差分で期待する指摘が出る。
- 違反がない差分で誤検知せず、「問題なし」を返す。
- ステージ済み差分を扱える。
