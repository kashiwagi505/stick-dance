# 影響調査ルール

## 目的

有識者の紙面レビュー指摘とシステムテスト不良について、現在のリポジトリから必要な要件、設計、実装、テストを同じ順序で調査する。AIは起票から影響調査、修正、検証、プルリクエスト作成までを事前承認なしに連続して行い、人間の承認はPRのレビューで受ける。

目的は、案件ごとの管理ファイルを増やすことではない。既存のバグ管理表・レビュー指摘表を変えずに、何度行っても同じ品質で調査と修正を進めることである。

## 情報の置き場所と役割

| 場所 | 役割 | 運用 |
|---|---|---|
| レビュー指摘表<br>`ドキュメント/管理表/レビュー指摘表.md` | 顧客へ提出する指摘管理 | 既存項目だけを使用し、影響調査用の列や項目を追加しない |
| バグ表<br>`ドキュメント/04_テスト/02_バグ表.md`（記入ルールと不良の正本。3章の表に1件1行）<br>`ドキュメント/04_テスト/バグ/未採番/`（起票直後の1件。番号なし） | 顧客へ提出する不良管理 | 既存項目だけを使用し、影響調査用の列や項目を追加しない。起票は `未採番/` にファイルを置き、更新は3章の該当行に書く。表へ手で行を足さない（採番と転記は `/bug-sync`） |
| AIとのチャット | 着手報告、進捗、停止理由、完了報告 | 下記の定型で表示する。案件ごとの新規ファイルは作らない |
| プルリクエスト | 人間が承認する場所。変更の最終証跡 | 対応ID、影響範囲、調査根拠、検証結果、未解決事項を記載する |
| WBS | 個人タスクと工数の管理 | **本手順では更新しない。** 工数記録が必要な場合は人間が別途行う |

**人間の承認はPRのレビューで行う。** AIは起票から修正、検証、PR作成までを事前承認なしに進め、PRをマージしない。したがってPR本文には、レビュー担当者がその場で妥当性を判断できるだけの影響範囲・調査根拠・検証証拠を必ず含める。

チャットはプロジェクトごとの継続的な作業ログとして扱う。毎回新しいチャットを作らず、継続チャット内で案件ごとにバッチIDと対象IDを付けて区切る。着手報告、進捗、停止理由、完了報告を今回のバッチ単位で記録し、最終結果はPR本文へ残す。

### バッチIDとPRの単位

- バッチIDは`<依頼を受けた日付YYYYMMDD>-<その日の連番2桁>`とする（例: `20260817-01`）。同じ日に2回目の依頼を受けた場合は`-02`とする。AIが依頼受領時に採番し、以後その依頼の全報告で同じ値を使う。
- **1バッチにつきPRは1つ**とする。個人ブランチは1人1本の固定運用のため、バッチ内の複数IDを1つのPRにまとめる。
- PR本文には対応IDごとに節を設け、IDごとの変更内容・影響範囲・検証結果を分けて書く。レビュー指摘表・バグ表とPR本文は`REV-001`または`BUG-001`形式の同じIDで対応付ける。表に追加のリンク列は作らない。並行ブランチと番号が重なって振り直した行は、備考に旧IDが残るため、PR本文に残る当時の採番から行を引ける（→ [管理表/AGENTS.md](../管理表/AGENTS.md)）。

## 起票時の分岐

起票項目が異なるため、起票時だけは次のように分岐する。影響調査、修正、検証、PR作成は共通の手順で行う。

| 入力の種類 | 起票先 | ID | 起票前に必ず読むもの |
|---|---|---|---|
| 有識者の紙面レビュー指摘 | `ドキュメント/管理表/レビュー指摘表.md` 3章（記入規則は同2章、採番は `ドキュメント/管理表/AGENTS.md`） | `REV-001` | 表の見出し、記入規則、直近1件 |
| 開発者がシステムテストで発見した不良 | `ドキュメント/04_テスト/バグ/未採番/`（`/bug-new` で作る。採番後は `02_バグ表.md` 3章の行） | `BUG-001` | `02_バグ表.md` 2章の記入規則、3章の直近の行 |

顧客レビューは本手順の対象外とする（発注元が本人のためQA表は置かない）。顧客レビューとして渡された場合は停止して人間へ確認する。AIは2表に共通する項目名を仮定せず、対象表にある必須項目と記入規則を使い、存在しない項目は追加しない。入力種別を判断できない場合は、起票前に人間へ確認する。

## 人間から受け取る情報

依頼プロンプトの形式は`.agents/harness-resolution.md`の「人間からの依頼プロンプト」を正本とする。人間が渡すのは、レビュー指摘なら「種別・対象・内容」、バグなら「対象・期待結果・実際の結果」とし、それ以上の項目を求めない。レビュー指摘の`種別`は`有識者紙面レビュー`または`顧客レビュー`のいずれかを必須とする。ID、指摘日、検出日、検出者、検出工程、重要度、混入工程、原因、密度計上、影響範囲はAIが補う。`指摘者`は対象表の記入規則に定められた固定値を使い、AIが記入例や過去行から推定しない。固定値の定めがなく依頼にも氏名がない場合は起票せず停止する。再現手順は、対象の画面IDから該当のテスト観点表をAIが読んで特定する。

スクリーンショット、ログ、テストケースIDは任意の証拠として扱う。

## 影響調査ルートの分類

| ルート | 対象 | 最初に確認するもの |
|---|---|---|
| 機能単位 | 機能要件、画面、処理、画面単位のテスト | 機能ID、画面ID、対象文書 |
| 横断 | 非機能要件、秘密値・公開範囲、デザイン基準、共通部品、インフラ、テスト方針、開発基準 | 対象の基準書と`ドキュメント/AGENTS.md`の連動更新規則 |
| 両方 | 特定機能と横断規則の両方に関係する変更 | 機能単位と横断の両ルート |
| 要確認 | 代替経路をたどっても対象を特定できないもの | 調査済み資料と不足情報を人間へ提示 |

判定は次の基準で行う。複数の条件に該当する場合は、`両方`を選ぶ。共通部品、秘密値・公開範囲、非機能要件、インフラ、テスト方針、開発基準に関係する可能性がある場合は、機能単位だけで完了させない。

| 判定条件 | ルート |
|---|---|
| 1機能固有の要件・画面・処理・テストだけに閉じる | 機能単位 |
| 秘密値・公開範囲、共通部品、共通の描画処理・文言定義、非機能、インフラ、テスト方針、開発基準に関係する | 横断 |
| 機能固有の影響と横断的な影響の両方がある | 両方 |
| 下記「設計書が未整備な場合の代替経路」をたどっても対象を特定できない、または複数ルートを判定できない | 要確認 |

## 設計書が未整備な場合の代替経路

設計書は工程の進行に応じて順次作成される。**設計書が存在しないことだけを理由に`要確認`として停止しない。**

- 調査順序にある文書は、実在すれば読む。ファイルが存在しない、または表が見出し行だけで中身が空の場合は、その段を飛ばす。飛ばした文書名と理由を着手報告の「参照できなかった文書」に必ず記載する。
- 設計書から対象を特定できない場合は、`要確認`とする前に次の順で特定を試みる。

| 順 | 代替経路 | 見るもの |
|---|---|---|
| 1 | テスト観点表 | `ドキュメント/04_テスト/テスト仕様書/SCRxx_*.md` の対象画面・操作・期待結果 |
| 2 | E2Eテスト | `e2e/tests/` の該当specと`e2e/helpers/` |
| 3 | 実装 | `src/view/` のシーンと文言定義、`src/core/`・`src/music/`・`src/share/`・`src/audio/` のモジュール名・関数名、`src/data/` のステージのデータ |

- 代替経路で対象を特定できた場合は、その根拠（ファイルパスと該当箇所）を着手報告に記載したうえで修正へ進む。
- 3つの経路をすべてたどっても対象を特定できない場合だけ`要確認`とし、たどった経路と見つからなかった内容を提示して停止する。
- 対象の設計書が存在しないまま実装を修正した場合、設計書を新規作成するかどうかは本手順では判断しない。未解決事項としてPR本文とチャットに記載する。

## 採番・重複・並行起票

- 起票前に対象表の全行を検索し、同一または類似案件がないか確認する。検索に使う列は表ごとに異なるため、次のとおりとする。

| 対象表 | 検索する列 | 検索語 |
|---|---|---|
| レビュー指摘表 | `対象`、`指摘内容` | 依頼の対象文書名、指摘内容の要点 |
| バグ表 | `対象`、`事象` | 依頼の対象（画面ID・機能名）、実際の結果の要点 |

- 同一または類似案件がある場合は起票せず、人間へ確認する。
- 対象表の見出し・記入規則からID形式を確認し、起票直前に表を再読み込みして採番する。形式が不明な場合は推測しない。
- 同一表への起票は同時に行わず、1件ずつ処理する。起票後に表を再読み込みし、ID重複、意図しない変更、採番形式の不一致がないことを確認する。
- 異常があれば修正作業を開始せず、状態と差分を人間へ報告する。

## 調査からPRまでの手順

1. **前提を確認する**: ルートの`AGENTS.md`、`.agents/harness-resolution.md`、既存の目的・決定事項・未解決事項に相当する文書を確認する。必須資料が見つからない場合は、実行環境の入口に書かれた正本の場所を確認し、それでも見つからなければ人間へ確認する。バッチIDを採番する。
2. **入力種別を判定して起票する**: 入力が有識者紙面レビュー、顧客レビュー、システムテスト不良のいずれかを判定する。顧客レビューは停止して人間へ確認する。それ以外は上表に従って起票先、ID体系、起票前に読むものを選ぶ。選んだ表の見出し、記入規則、直近1件を確認し、重複を確認したうえで、その表にある既存項目だけを使って起票し、IDを確定する。判断できない場合は人間へ確認する。
3. **起票後を確認する**: 起票後に対象表を再読み込みし、ID、変更行、重複、意図しない変更、採番形式の不一致がないことを確認する。異常があれば修正作業を開始せず、状態と差分を人間へ報告する。
4. **影響調査ルートを分類する**: 指摘または不良を、`機能単位`、`横断`、`両方`、`要確認`のいずれかへ分類する。機能単位と横断の双方に該当する場合は`両方`とし、「設計書が未整備な場合の代替経路」をたどっても特定できない場合だけ`要確認`とする。
5. **必要な情報だけを調査する**: 選択したルートに応じて、関係する要件・設計・実装・テストを調査する。機能単位では、対象名から機能ID・画面IDを特定し、機能要件、画面一覧、画面設計、処理設計、テスト観点表の順に、**実在するものだけを**対象に関係する箇所だけ読む。存在しない文書は飛ばし、飛ばした事実を着手報告に残す。機能ID、画面ID、画面名、関数名・型名、ステージ名を検索語として、関係する実装とテストだけを検索する。横断では、対象の基準書と実在する`AGENTS.md`の連動更新規則から、共通実装、対象画面、設定、テストを調べる。`両方`の場合は機能単位と横断の両ルートを実施し、重複する影響先を1つにまとめる。
6. **着手報告をして修正へ進む**: 調査結果、根拠、確認した範囲、変更予定、検証方法を、下記の定型で継続チャット内の今回のバッチ欄に提示する。これは記録のための着手報告であり、承認は待たない。
7. **修正・検証する**: 修正に着手し状態を`対応中`へ変更する前に、作業ブランチとベースブランチを確認し、`git status --short`を開始時ベースラインとして記録する。修正対象と競合する未コミット変更がある場合だけ停止し、対象と無関係な変更は残したまま進める。影響調査で特定した範囲だけを修正し、実際の変更ファイルを`git diff`で確認する。コード変更時はリポジトリで定められたビルド・テスト、画面変更時は再現手順とスクリーンショットで確認する。検証に失敗した場合は原因を`仕様`、`実装`、`データ`、`環境`、`テスト`に分類し、影響調査の範囲内で**最大2回まで**修正・再検証する。2回の自己修正でも通らない場合は停止し、下記「停止報告」の内容をチャットへ報告する。修正中に`.agents/harness-resolution.md`の中断条件（層の分け方・読んでよい層の変更、共有URLの形式（版番号）の変更、公開範囲・配信の変更、要件定義そのものの変更、影響調査結果と大きく食い違う場合）に該当した場合も、そこで停止して人間の判断を待つ。
8. **完了処理を行う**: 検証に成功した場合は、下記「PR作成の手順」に従い、修正コミット、管理表更新コミット、PR作成、必要なPR番号追記を順に行う。レビュー指摘表は`対応済`、バグ表は`修正済`へ更新し、修正コミットのハッシュを記録する。最終差分が同じPRに含まれ、作業ツリーに開始時ベースライン以外の未コミット差分がないことを確認してから完了報告を残す。AIはPRをマージせず、レビューによる承認を待つ。

## 検証コマンド

ルート`AGENTS.md`に定められた標準コマンド（`npm run check`）を実行する。標準コマンドが実行できない、または対象変更に別の検証が必要と判断した場合は、推測で実行せず人間へ確認する。

### src/ を変更した場合のE2Eテスト

**`src/`（`src/core/`・`src/music/`・`src/share/`・`src/audio/`・`src/view/`・`src/data/`）または `index.html` を変更した場合は、E2Eテストのうち影響範囲ぶんもあわせて実行し、全件成功を確認する。** 対象は次の2つ。

| 対象 | 選び方 |
|---|---|
| 影響ありと判定した画面のspec | 手順5で特定した画面IDについて、`e2e/tests/` の画面IDで始まるspecを**すべて**。1画面が観点ごとに複数ファイルへ分かれていることがあるため、片方だけでは崩れを拾えない |
| 全画面共通部品のspec（`e2e/tests/com*.spec.ts`。あれば） | 変更した画面がどこであっても実行する。共通部品は全画面に載るため、1画面の描画処理の変更でも失敗しうる |

**変更した画面だけを対象にしない。** 共通の描画処理・文言定義、`src/core/`・`src/music/`・`src/share/`・`src/audio/`・`src/data/` のように複数の画面から使われる処理を触った場合は、手順5の影響調査で影響ありと判定した画面すべてが対象になる。

**全件（`npm run e2e`）は個々の修正では要求しない。** 結合テストの完了条件が「E2Eテスト全件成功と全ケースの証跡」であり（[テスト方針](../04_テスト/01_テスト方針.md) 1章）、全件は工程の節目で担保されるため。

```powershell
npm ci; npm --prefix e2e ci            # 作業ツリーには node_modules が無いので初回だけ
npm --prefix e2e test -- scr02 com     # 画面IDで絞る（例: SCR02と共通部品）。アプリの起動を含む
```

絞り込みの引数はファイルパスに対する部分一致のため、画面IDを1つ渡せばその画面のspecがまとめて対象になる（[テスト方針](../04_テスト/01_テスト方針.md) 4-5）。実装ツリーが2本以上並ぶときは`.env`の`SERVER_PORT`を分ける（[Git運用手順](Git運用手順.md)「4. 並行作業（複数セッション）」）。

チャットとPR本文には、実行したコマンド、実行環境、終了結果、ログまたは画面確認の証拠を記載する。コマンドが対象外の場合は、対象外とした理由を記載する。

## PR作成の手順

PR作成はGit運用手順②〜④に従う。`/create-pr`スキルが利用できる場合はmaster取り込み・push・PR作成に使い、本手順で独自の代替手順を作らない。

1. コミット前に、作業ブランチが`dev/<自分の名前>`であることを確認する。`master`へ直接コミット・pushしない。開始時ベースラインにあった対象外の変更はステージせず、対象ファイルだけをコミットする。
2. 修正・設計・テストの変更をコミットし、そのハッシュを修正コミットとする。
3. 対象表の`対応内容`、`修正コミット`、必要な原因・集計項目を更新し、レビュー指摘表は`対応済`、バグ表は`修正済`へ変更して、管理表更新を別コミットにする。バグ表の更新先は3章の該当行（採番前なら `バグ/未採番/` のファイル）。
4. **PRを出す前に`master`の最新を自分のブランチへ取り込み直し、`npm run check`を再実行する。** マージは成功してもビルドが壊れることがあり、テストでしか検出できない。
5. pushしてPRを作成する。PRは必ず`dev/<自分の名前>` → `master`に向ける。
6. レビュー指摘表を更新した場合は、作成したPR番号を`PR`へ記入して別コミットにし、`npm run check`を再実行して同じPRへpushする。バグ表だけを更新した場合はこの手順を省略する。
7. PRの最終差分に修正コミット、管理表の状態・修正コミット、レビュー指摘表のPR番号が含まれ、作業ツリーに開始時ベースライン以外の未コミット差分がないことを確認する。
8. PR説明には、Git運用手順で必須とされている次の2点を必ず含める。
   - [ ] 対応する設計書を更新した
   - [ ] `npm run check` が通ることを確認した
9. AIはPRをマージしない。approveはPRレビュアーが行い、レビュー指摘表の`確認済`は元の指摘者、バグ表の`確認済`は再テスト実施者が設定する。

## チャットで提示する着手報告の形式

起票と影響調査を終えた時点で、起票した全件について次の形式で日本語で表示する。承認は待たず、表示後そのまま修正へ進む。

```text
### <BUG-001またはREV-001形式のID> <対象画面・機能>

- 記録単位: <プロジェクトの継続チャット識別子／バッチID>
- 起票先: <レビュー指摘表またはバグ表>
- 状態: 対応中
- 現在の記述・動作: <実際の結果>
- 期待結果: <期待結果>
- 影響調査ルート: <機能単位、横断、両方、要確認>
- 選択理由: <ルートを選んだ根拠>
- 確認した範囲: <調べた要件・設計、画面、実装、テスト。ファイルパスと見出しまたは行を含める>
- 参照できなかった文書: <存在しない・空だったため飛ばした文書と、代わりにたどった代替経路。なければ「なし」>
- 変更予定: <これから変更する内容>
- 検証方法: <実行するチェックと期待結果>
- 未確認事項: <なし、または内容と、修正内容を確定できるかどうか>
```

表示後は次を表示して修正へ進む。

```text
上記の範囲で修正に着手します。承認はPRのレビューでお願いします。
```

ただし、次のいずれかに該当する件は修正へ進まず、その件だけを停止して人間の判断を求める。他の件は継続してよい。

- 影響調査ルートが`要確認`
- 起票先の判定不能、重複の疑い、ID形式不明
- 修正すべきでないと判断した（`対応不要`／`取り下げ`に相当する）
- **未確認事項があり、それによって変更内容を確定できない場合**。変更内容に影響しない未確認事項は、着手報告に記載したうえで修正へ進んでよい

## 完了報告とPR

全検証後、AIはチャットで次を報告する。同じバッチ内に停止した件がある場合は、この完了報告に続けて「停止報告」も出す。

```text
- 対応したID: <ID一覧>
- 記録単位: <プロジェクトの継続チャット識別子／バッチID>
- 変更ファイル: <ファイル一覧>
- 影響調査結果: <ルートと最終的な影響範囲>
- 調査根拠: <確認したファイル、該当箇所、検索語>
- 実行した検証: <実在する検証コマンド、実行環境、確認内容>
- 検証結果: <成功・失敗と証拠>
- 自己修正回数: <0、1、2>
- 修正コミット: <コミットハッシュ>
- 管理表更新コミット: <コミットハッシュ>
- PR番号追記コミット: <レビュー指摘表を更新した場合のコミットハッシュ。対象外なら「なし」>
- プルリクエスト: <URL>
- 未解決事項: <なし、または内容。設計書が未整備で新規作成の要否が残る場合もここに書く>
- 同一バッチで停止したID: <なし、または ID一覧（詳細は停止報告）>
- PRレビューによる承認待ち: はい
```

PR本文には、対応ID、バッチID、変更内容、影響範囲、影響調査ルートと根拠、検証結果、未解決事項、プロジェクトの継続チャット識別子を記載する。バグ表を更新した場合は、`混入工程`と`密度計上`をその値にした判断根拠もPR本文に書く。これらは不良密度の集計元であり、レビュー担当者が検証できる必要があるため。事前承認を挟まない運用のため、PR本文はレビュー担当者がその場で妥当性を判断できる情報量にする。チャットの内容を案件別ファイルへ転記しない。

## 停止報告

自己修正2回でも検証が通らない場合、中断条件に該当した場合、PR作成に失敗した場合、人間への確認事項があり回答待ちになった場合は、継続チャット内の今回のバッチ欄へ次を記録する。修正コミットを作成する前に停止した場合は対象表を`対応中`に留める。修正コミットと管理表更新コミットの後にPR作成で失敗した場合は、対象表の`対応済`／`修正済`を戻さず、レビュー指摘表の`PR`を空欄のままとして、PR未作成であることと再開地点を報告する。起票前に停止した場合は対象表に行がないため状態は更新しない。`確認待ち`はチャット上の一時停止であり、状態列には記入しない。

```text
- 停止したID: <ID一覧。起票前に停止した場合は「なし（起票前）」とし、対象と内容を併記する>
- 記録単位: <プロジェクトの継続チャット識別子／バッチID>
- 停止理由: <要確認／判定不能／対応不要相当／中断条件に該当／自己修正2回で不成功／PR作成失敗／人間への確認待ちのいずれか>
- 失敗した検証: <コマンドと出力の該当箇所。検証まで進まなかった場合は「なし」>
- 試行記録: <各試行で何を変更し、なぜ失敗したかを試行ごとに書く。修正に着手していない場合は「なし」>
- 原因分類: <仕様／実装／データ／環境／テスト>と判断根拠。分類できない場合はその理由
- 確認事項: <人間へ確認したい質問。停止理由が「人間への確認待ち」のときは必須。それ以外は「なし」>
- 再開地点: <回答後に再開する手順と地点（例: `.agents/harness-resolution.md`「3. 起票・採番・重複確認」の4から）。再開しない場合は「なし」>
- 作業ツリーの状態: <変更を残した／戻した>
- 次に必要な人間の判断: <内容>
```

作業ツリーは原則として変更を残したまま停止する。人間が差分を見て判断できるようにするため。ビルドが通らず他の作業を妨げる場合だけ戻し、戻したことを報告に明記する。

## 完了条件

- レビュー指摘表またはバグ表は既存項目だけで更新されている。
- 着手報告が定型でチャットに提示されている。参照できなかった文書と代替経路が記載されている。
- 実際の変更差分が影響調査結果の範囲に収まっていることを`git diff`で確認している。
- 修正と検証が完了している（自己修正は2回以内）。
- 状態を`対応中`にする前に作業ブランチと開始時ベースラインを確認し、コミットに対象外ファイルを含めていない。
- 修正コミットのハッシュと`対応済`／`修正済`への状態更新が、管理表更新コミットに含まれている。
- PR作成前に`master`を取り込み直し、`npm run check`を再実行している。
- レビュー指摘表を更新した場合、PR番号の追記を同じPRへpushし、PRの最終差分と作業ツリーを確認している。
- PR説明にGit運用手順の必須2項目（設計書の更新、`npm run check`の通過）が含まれている。
- PR本文に、影響範囲、調査根拠、検証結果、未解決事項が記載され、レビュー担当者が承認判断できる状態になっている。
- AIはPRをマージしていない。
