# アプリケーション実装方針

棒人間ダンシングの「作りの考え方」をまとめた文書。機能を追加・変更するときは、まず本書を読んで全体の仕組みを理解する。AIに実装させるときも本書に従わせる。他のコマンド・エージェントが章番号で参照しているので、**章番号は変えない**。

技術構成: TypeScript（strict）、Vite（開発サーバーとビルド）、Vitest（単体テスト）、ESLint（静的解析）、Playwright（E2E）、Phaser 4（画面の描画・入力）、Tone.js（音の合成・拍・書き出し用の録音）。DB・サーバーは持たず、GitHub Pages から静的ファイルとして配信する（→ [インフラ要件](../01_要件定義/03_インフラ要件.md) I1）。動作環境はPCのChrome最新版を基準にする（→ [非機能要件](../01_要件定義/02_非機能要件.md) N1）。使う技術と版、コードの分け方の理由は [技術選定の設計方針](../02_基本設計/設計方針/技術選定の設計方針.md) を正本とし、本書はそれを実装のルールとして書き下ろす。

## 1. アプリの全体像（記録から曲までの流れ）

プレイヤーの操作は、次の順で処理されて1曲になる。

```
キーボード（矢印キー・WASD・Shift・Space）
  │ ① 押されたキー
  ▼
画面（src/view） …… Phaser のシーン。キー入力を受け、音の時刻を読んで core に渡す（F2）
  │ ② 操作＋時刻
  ▼
ゲーム（src/core） …… 街・移動・配達を進め、通ったマス・速さ・止まった時間・操作を時刻つきで記録する（F1・F3）
  │ ③ 記録（乱数の種を含む）
  ▼
曲作り（src/music） …… 記録とステージのデータ（src/data）から、伴奏と旋律の音符の並びを作る（F4・F5）
  │ ④ 曲（音符の並び）
  ├─▶ 音（src/audio） …… Tone.js で鳴らす。プレイ中は控えめに、種明かしでは曲として（F6・F7）
  └─▶ 共有（src/share） …… 記録を URL の `#` 以降に詰める／曲を WAV に組み立てる（F8・F9）
```

ポイントは「**各層は自分の仕事だけをする**」こと。ゲームと曲作りの中身（`core`・`music`）は、描画（Phaser）も音（Tone.js）も知らない（→ [判断ログ](../01_要件定義/判断ログ.md) D18）。そのため、街と曲作りの規則は画面を開かずに単体テストで確かめられる。

**曲は「記録（種を含む）→ 音符の並び」の1つの関数で作る。** プレイ中・種明かし・共有URLからの再生・WAVの書き出しは、すべて同じ関数の結果を使う（→ 技術選定 3.1）。同じ記録からは必ず同じ曲になることが、受け入れ条件 AC4・AC5 の前提になる。

## 2. フォルダと層の役割

| フォルダ | 役割 | やってよいこと / いけないこと |
|---|---|---|
| `src/core/` | 街・移動・配達・記録（純粋な TypeScript） | 状態と時刻を受け取り、次の状態と記録を返す。Phaser・Tone.js・DOM・時計（`Date.now()`・`performance.now()`）・`Math.random()` に触れない（例外: 種を作る `seed.ts` だけは `Math.random()` を使う） |
| `src/music/` | 記録 → 曲（音符の並び）（純粋な TypeScript） | 記録とステージのデータから音符の並びを作る。Phaser・Tone.js・DOM・時計・`Math.random()` に触れない。乱数は記録に入った種から動く乱数だけを使う（6章） |
| `src/share/` | 記録 ⇔ URL、曲の WAV 書き出しの組み立て | 記録をバイト列に詰めて圧縮し URL の `#` 以降に入れる・読み戻す。録音した音から WAV のバイト列を組み立てる。ゲームや曲作りの規則を書かない |
| `src/audio/` | Tone.js。曲を鳴らす・拍を刻む・書き出し用に録音する | 音符の並びを受け取って鳴らす。曲の中身（どの音を鳴らすか）を決めない |
| `src/view/` | Phaser。シーン（タイトル・ステージ・種明かし・共有再生） | キー入力・描画・画面の切り替えを担い、各層をつなぐ。ゲームや曲作りの規則を書かない |
| `src/data/` | ステージの街・区画・マスの音・伴奏のデータ | データだけを置く。処理を書かない |

### 依存の方向

各層が import してよい層は次の表のとおりとする（→ 技術選定 2章）。表にない向きの import はしない。

| 層 | 読んでよい層 |
|---|---|
| core | data |
| music | core, data |
| share | core, music |
| audio | music |
| view | すべて |
| data | なし |

- `core`・`music` は Phaser と Tone.js を import しない。描画と音を差し替えても中身が変わらないようにするため。
- `view` 以外の層から `view` を import しない。
- 層をまたいで使う型（記録・音符など）は、その型を作る層（記録は `core`、音符は `music`）に置き、使う側が上の表の向きで import する。

## 3. 画面の切り替え

- 画面はブラウザ1枚（1ページ）で動かし、タイトル・ステージ・種明かし・共有再生の切り替えは、ページ遷移ではなく Phaser のシーンの切り替えで行う。画面の一覧と切り替えの条件は `02_基本設計/01_画面一覧・遷移図.md` を正本とする。
- URL の `#` 以降に記録が入っているときは、遊ばずに共有再生の画面を開く（F8）。
- ステージの途中でページを再読み込みしたら、タイトルから始める。プレイ中の状態はブラウザに保存しない（→ 判断ログ D25、[画面一覧・遷移図](../02_基本設計/01_画面一覧・遷移図.md) 3章 No.10）。

## 4. メッセージの管理

- 利用者向けの文言（ボタン・案内・エラー表示）は、`src/view/` の文言定義1か所にまとめ、シーンの描画処理に直接書かない。
- ステージ名・区画の名前など、ステージのデータとして持つ名前は文言定義に書かず、`src/data/` から受け取る。

## 5. 入力とエラー処理の役割分担

| 種類 | 例 | どこで扱うか |
|---|---|---|
| 操作 | 移動・ブレーキ・ベル以外のキー、同時押し | `src/view` で受け付けるキーだけを `src/core` に渡す。どう扱うかは `src/core` の規則が決める |
| 共有URLの不備 | `#` 以降が壊れている、形式の版が違う | `src/share` が失敗を戻り値で返す。画面での扱い（版違いをどう見せるか）は詳細設計で決める（→ 技術選定 3.3） |
| 書き出しの失敗 | WAV の録音・組み立てが失敗した | `src/share`・`src/audio` が失敗を戻り値で返し、`src/view` が画面に出す。黙って続けない |
| ブラウザの制約 | 利用者の操作より前には音を鳴らせない（ブラウザの自動再生の制限） | `src/view` で、利用者の操作（キー・クリック）を受けてから音を始める。共有再生でも同じ |

- 予期しない例外を握りつぶさない。内部の詳細（スタックトレース等）を画面に出さない。

## 6. 依存の渡し方と時間

- 外から差し替えたいもの（時刻・乱数の種・ステージのデータ）は、関数の引数またはコンストラクタで渡す。モジュールの中で直接生成したり、グローバルな変数で共有したりしない。
- **時刻の基準は音にする**（→ 技術選定 3.2、判断ログ D14）。拍は Tone.js の Transport が刻み、`src/view` はその時刻を読んで動く。画面のフレーム数から時刻を数えない。
- **`src/core`・`src/music` の中で時計を読まない。** 時刻は呼び出し側（`src/view`）が音の時刻を読み、数値として渡す。
  - **移動・配達・記録の時刻を単体テストで確かめるため。** 時刻を引数で受け取れば、テストで「開始から○秒後」の状態を待たずに作れる。
  - **種明かしで光と音をずらさないため。** 記録の時刻と再生の時刻を同じ時計で数える。
- **乱数は使う。ただし同じ記録からは必ず同じ曲にする**（→ 技術選定 3.1、判断ログ D19）。
  - ゲーム開始時に乱数の種を1つ作り、記録に入れる。種を作るときだけ `Math.random()` を使ってよい（作るのは `src/core/seed.ts` の `createSeed()`。ゲーム開始時に `src/view` が呼び、記録へ渡す）。
  - `src/music` では `Math.random()` と現在時刻を直接使わない。乱数はすべて、記録に入った種から動く乱数（seed付きの擬似乱数）から取る。
  - 種は共有URLにも入れる。URLを開いた人の手元でも同じ乱数が出て、同じ曲になる。
  - 乱数で変えてよいのは脇役（マスへの音の割り当ての並び・伴奏パターンの選択・飾りの音・キーやテンポの小さな揺れ）に限る。走った道・速さ・操作が曲に効く部分を乱数で変えない。曲の違いの主役は走りにする（→ 技術選定 3.1）。どこまで効かせるかは試作で聞いて決める。

## 7. データと記録の形式（ステージデータ・共有URL・WAV）

外部から取得するデータは無い。実行時に読むのは、リポジトリに含めたステージのデータと画像、利用者が開いた共有URLだけとする。

- **ステージのデータ**（街・区画・マスの音・伴奏）は `src/data/` に TypeScript のデータとして手で書く。マップエディタを使うかは、街が大きくなったら見直す（→ 技術選定 4章）。
- **画像**は自宅Macの Codex で生成し、リポジトリに含める。作り直せるものでも `.gitignore` に入れない（→ インフラ要件 I4）。どの画像をいつ何で作ったかを記録する（→ 非機能要件 N3、受け入れ条件 AC6）。記録は `ドキュメント/素材/画像の記録.md` に1画像1行で書く（ファイル名・生成日・生成元・規約を確認した日）。
- **共有URL**は、記録を詰めたバイト列 → `CompressionStream` で圧縮 → base64url にして `#` 以降に入れる。先頭に**形式の版番号**を入れる。ステージのデータや曲作りの規則を変えると、古いURLが別の曲になるため。版が違うURLの扱いと長さの上限は詳細設計で決める（→ 技術選定 3.3、非機能要件 N4）。
- **形式を変えたら版番号を上げる。** 記録の詰め方・ステージのデータ・曲作りの規則のどれかを、同じ記録から違う曲になる形で変えたときが対象。
- **WAV** は `Tone.Offline` で画面の再生とは別に録音し、PCM の WAV に組み立てる。追加のライブラリは使わない。録音に使う曲は1章の同じ関数の結果を使う（→ 技術選定 3.4）。

## 8. サーバーと秘密値を持たない・公開範囲

- **サーバーと秘密値を持たない。** サーバー側の処理・外部API・鍵は使わない（→ インフラ要件 I1・2章）。共有も URL の `#` 以降だけで完結させる。`#` 以降はサーバーに送られない。
- `.env` は秘密値の置き場として使わない。並行作業で作業ツリーを分けたときの開発サーバーの待受ポート（`SERVER_PORT`）を変えるためだけに使い、無くても既定値で動く。
- **一般公開する**（→ 判断ログ D5・D11）。GitHub Pages でリポジトリ名のパス（`/stick-dance/`）から配信されるので、Vite の `base` を合わせる。
- 公開する画像はすべて、生成元と規約の確認の記録があるものに限る（→ 非機能要件 N3、受け入れ条件 AC6）。記録の無い画像を配信物に含めない。
- 外部の音源ファイルを使わない。音はブラウザの中で合成する（→ 要件定義 README 3章「最初の版でやらない」）。

## 9. 実装の共通ルール

- **後方互換性を維持しようとしない。** 互換レイヤーやフォールバックを追加するのではなく、古い実装や不要になったコードは削除する。使われなくなった関数・設定・ファイルを「念のため」残さない。共有URLの古い版の扱いだけは、詳細設計で決めたとおりにする（7章）。
- **現在の要件を完全に満たす、最もシンプルな実装を選ぶ。** 将来を見越した過剰な抽象化・設定項目・間接化は避ける。インターフェースは実装が複数必要になった時点で作る（例: 曲を作る関数は1つで、プレイ中・種明かし・共有再生・書き出しが同じものを呼ぶ。呼び出し元ごとに別の実装を作らない）。
- **仮の数値（制限時間・速さとリズムの対応・休符を縮める長さ・音量など）は、設定1か所にまとめて名前を付ける。** 数値は遊んで・聞いて決めるため（→ [要件定義](../01_要件定義/README.md) 7章）。処理の途中に数値を直書きしない。設定は `src/data/tuning.ts` の1か所に置く（値の一覧と意味は [ゲーム進行の設計方針](../02_基本設計/設計方針/ゲーム進行の設計方針.md)・[曲作りの設計方針](../02_基本設計/設計方針/曲作りの設計方針.md)）。
- **音の遅れ（N2）を後付けにしない。** 操作から音が鳴るまでの遅れを、試作で測れる形で作る。
- TypeScriptは `strict` で書き、`any` と型アサーション（`as`）で型検査を黙らせない。外から来るデータ（共有URLから読み戻した記録）は、受け取った場所で形を確かめてから使う。
- **Phaser は 4 の公式ドキュメントと型定義を見て書く。** AIの学習データは Phaser 3 の情報が多く、4 で変わった API がある（→ 技術選定 1章）。
- **実装（`src/`）では外部CDNを参照しない。** 必要なライブラリは npm の依存として入れる。
- 公開する関数・型には、役割が分かる日本語のコメントを書く。
- 変更したコードには対応する単体テスト（Vitest、`src/**/*.test.ts`）を用意する。特に `src/core`・`src/music`・`src/share` はテストで仕様を固定する。
- 1コミット＝1つの意図（機能追加とリファクタリングを混ぜない）。

## 10. 機能追加の流れ

新しい機能を追加するときは、いきなりコードを書かず、次の順で進める。実装とテストは**テストファースト**で進める。設計を終えたらまずテストを書いて合格条件（ハーネス）を先に固定し、そのテストが全件成功するまで実装と修正を反復する（テスト側の運用詳細は [テスト方針](../04_テスト/01_テスト方針.md) 9章）。

1. **起票** — `テンプレート/機能追加シート.md` をコピーして、影響範囲を整理する。
2. **要件に追記** — `01_要件定義/01_機能要件.md` に機能を追加する。
3. **画面の設計** — 画面が増える・変わるなら `02_基本設計/画面設計/` と `モックアップ/` を追加し、`01_画面一覧・遷移図.md` を更新する。
4. **処理の設計** — `03_詳細設計/処理設計/` の機能単位ファイルに機能固有の設計判断を書く。共有URLの形式が変わるなら共有の処理設計と本書7章（版番号）を、ステージのデータの形が変わるならそれを読む層の処理設計を更新する。
5. **テストの作成（テストファースト）** — 実装より先に、設計書の仕様を合格条件として表す単体テストを書く（実装がない間は失敗してよい）。画面がある機能は、画面単位の観点表を `04_テスト/テスト仕様書/` に追加し、PlaywrightによるE2Eテスト（`e2e/tests/`）を実装する。
6. **実装（テストが通るまで反復）** — 本書のルール（層の役割・時間と乱数の渡し方・同じ記録から同じ曲）に沿って実装し、`npm run check`（型検査＋静的解析＋単体テスト）が成功するまで「実行 → 失敗の修正」を繰り返す。E2Eテスト（`npm run e2e`）も同様に全件成功させる。音は手で聞いて確かめる。
7. **設計書の更新** — コードとあわせて設計書・README を更新し、乖離させない。
