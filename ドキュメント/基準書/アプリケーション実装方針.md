# アプリケーション実装方針

棒人間ダンシングの「作りの考え方」をまとめた文書。機能を追加・変更するときは、まず本書を読んで全体の仕組みを理解する。AIに実装させるときも本書に従わせる。他のコマンド・エージェントが章番号で参照しているので、**章番号は変えない**。

技術構成: TypeScript（strict）、Vite（開発サーバーとビルド）、Vitest（単体テスト）、ESLint（静的解析）、Playwright（E2E）、Canvas 2D（棒人間と舞台の描画。ライブラリなし）、HTML と CSS（トップページ・ボタン・案内）、Tone.js（楽器の音の読み込みと鳴らし方。Transport は使わない）。体の動き（物理）は自作する。DB・サーバーは持たず、GitHub Pages から静的ファイルとして配信する（→ [インフラ要件](../01_要件定義/03_インフラ要件.md) I1）。動作環境はPCのChrome最新版を基準にする（→ [非機能要件](../01_要件定義/02_非機能要件.md) N1）。使う技術と版、コードの分け方の理由は [技術選定の設計方針](../02_基本設計/設計方針/技術選定の設計方針.md) を正本とし、本書はそれを実装のルールとして書き下ろす。音の中身（テンポ・音階・楽器の割り当て）は [音の設計方針](../02_基本設計/設計方針/音の設計方針.md) が正本。

## 1. アプリの全体像（キー入力から踊りと音までの流れ）

プレイヤーの操作は、次の順で処理されて踊りと音になる。

```
キーボード（左手＝WASD、右手＝矢印キー）
  │ ① 押された・離されたキー
  ▼
画面（src/view） …… キー入力を受け、音の時計から「何刻み目か」を数えて core に渡す。Canvas に描く
  │ ② キー入力＋刻みの番号
  ▼
踊り（src/core） …… 物理を1/60秒ずつ進め、ループ・分身を管理し、キー入力と楽器の選択を記録する（F1・F3・F4・F5）
  │ ③ 記録（キー入力と楽器の選択）・頭の高さ
  ▼
音の並び（src/music） …… 記録から、どの拍に、どの楽器の、どの高さを鳴らすかを決める（F2・F5）
  │ ④ 鳴らす音の並び
  ├─▶ 音（src/audio） …… Tone.js で鳴らす。拍は音の時計を見て先読みして予約する
  └─▶ 共有（src/share） …… 記録を URL の `#` 以降に詰める・読み戻す（F8）
```

`src/main.ts` は各層をつなぐだけにする。

ポイントは「**各層は自分の仕事だけをする**」こと。踊りと音の並びの中身（`core`・`music`）は、描画（Canvas・DOM）も音（Tone.js）も知らない（→ 技術選定 2章）。そのため、物理・ループ・分身・音の決め方は画面を開かずに単体テストで確かめられる。

**踊りと音は「記録 → 物理の計算し直し → 音の並び」の1つの流れで作る。** 踊っている最中・分身の再生・鑑賞・共有URLからの再生は、すべて同じ関数の結果を使う（→ 技術選定 3.1）。同じ記録からは必ず同じ踊りと同じ音になることが、非機能要件 N3 と受け入れ条件 AC3 の前提になる。

## 2. フォルダと層の役割

| フォルダ | 役割 | やってよいこと / いけないこと |
|---|---|---|
| `src/core/` | 踊り（物理）・ループ・分身・記録（純粋な TypeScript） | キー入力と刻みの番号を受け取り、次の状態と記録を返す。Tone.js・Canvas・DOM・時計（`Date.now()`・`performance.now()`）・`Math.random()`・ブラウザで結果が変わりうる `Math` の関数（6章）に触れない |
| `src/music/` | 記録 → 鳴らす音の並び（純粋な TypeScript） | 記録と頭の高さから、拍・楽器・高さの並びを作る。`core` と同じく Tone.js・DOM・時計・乱数に触れない |
| `src/share/` | 記録 ⇔ URL | 記録をバイト列に詰めて圧縮し URL の `#` 以降に入れる・読み戻す。踊りや音の決め方を書かない。時計・乱数に触れない |
| `src/audio/` | Tone.js。楽器の読み込み・拍の予約・エフェクト | 音の並びを受け取って鳴らす。どの音を鳴らすかを決めない |
| `src/view/` | Canvas の描画と HTML の画面。キー入力 | キー入力・描画・画面の切り替えを担う。踊りや音の決め方を書かない。Tone.js を直接読まない（音は `src/audio` を通す） |
| `src/main.ts` | 各層をつなぐ | 処理の中身を書かない |

### 依存の方向

各層が import してよい層は次の表のとおりとする（→ 技術選定 2章）。表にない向きの import はしない。境界は `eslint.config.js` の import 制限で機械的に止めている。

| 層 | 読んでよい層 |
|---|---|
| core | なし |
| music | core |
| share | core, music |
| audio | core, music |
| view | core, music, share, audio（Tone.js は読まない） |
| main.ts | すべて |

- Tone.js を import するのは `src/audio` だけ。描画と音を差し替えても中身が変わらないようにするため。
- `view` 以外の層から `view` を import しない。
- 層をまたいで使う型（記録・音の並びなど）は、その型を作る層（記録は `core`、音の並びは `music`）に置き、使う側が上の表の向きで import する。

## 3. 画面の切り替え

- 画面はブラウザ1枚（1ページ）で動かし、画面の切り替えはページ遷移ではなく HTML の表示切り替えで行う（→ 技術選定 1章）。シーンの仕組みを持つライブラリは使わない。
- 画面の候補はトップページ・踊る画面・鑑賞・共有を開いた画面。**画面の一覧と切り替えの条件は未決で、基本設計で決める**（→ 要件定義 README 7章）。決めたら `02_基本設計/01_画面一覧・遷移図.md`（未作成）を正本とする。
- URL の `#` 以降に記録が入っているときは、遊ばずに鑑賞を再生する（F8）。
- 画面が隠れたら（`visibilitychange`）、音と物理を止め、戻ったら続きから再開する（→ 技術選定 3.3、判断ログ D20）。
- 途中でページを再読み込みしたときの扱いは未決。基本設計で画面一覧とあわせて決める。

## 4. メッセージの管理

- 利用者向けの文言（ボタン・案内・エラー表示）は、`src/view/` の文言定義1か所にまとめ、描画処理に直接書かない。
- 楽器の名前など、音の設定として持つ名前は文言定義に書かず、それを定義した層から受け取る。置き場所は基本設計で決める。

## 5. 入力とエラー処理の役割分担

| 種類 | 例 | どこで扱うか |
|---|---|---|
| 操作 | WASD・矢印キー以外のキー、同時押し、押しっぱなし | `src/view` で受け付けるキーだけを `src/core` に渡す。どう扱うかは `src/core` の規則が決める |
| 共有URLの不備 | `#` 以降が壊れている、形式の版が違う | `src/share` が失敗を戻り値で返す。画面での扱いは詳細設計で決める |
| 音の読み込みの失敗 | 楽器の音のファイルが読めない | `src/audio` が失敗を戻り値で返し、`src/view` が画面に出す。黙って続けない。読み込み中は「準備中」と出す（→ 技術選定 3.4） |
| ブラウザの制約 | 利用者の操作より前には音を鳴らせない（ブラウザの自動再生の制限） | `src/view` で、利用者の操作（キー・クリック）を受けてから音を始める。共有URLの再生でも同じ |

- 予期しない例外を握りつぶさない。内部の詳細（スタックトレース等）を画面に出さない。

## 6. 依存の渡し方と時間

- 外から差し替えたいもの（時刻・キー入力・設定の数値）は、関数の引数またはコンストラクタで渡す。モジュールの中で直接生成したり、グローバルな変数で共有したりしない。
- **時刻の基準は音の時計にする**（→ 技術選定 3.2）。拍は `AudioContext.currentTime` を基準に、`src/audio` が先読みして予約する。**Tone.js の Transport は使わない**（前作で、1つしかない Transport を前の画面の後始末が止める不具合が出た。判断ログ D19）。画面のフレーム数（`requestAnimationFrame`）から時刻を数えない。
- **物理は決まった刻み（1/60秒）で進める。** 音の時計が何秒進んだかで、物理を何刻み進めるかを決める。描画の回数に合わせて刻みを変えない（→ 技術選定 3.1）。
- **`src/core`・`src/music`・`src/share` の中で時計を読まない。** 時刻は呼び出し側が音の時計を読み、刻みの番号や秒の数値として渡す。
  - **物理・ループ・分身を単体テストで確かめるため。** 刻みを引数で受け取れば、テストで「○刻み後」の状態を待たずに作れる。
  - **分身と鑑賞で、動きと音をずらさないため。** 記録の刻みと再生の刻みを同じ時計で数える。
- **同じ記録からは必ず同じ踊りと音にする**（→ 技術選定 3.1、判断ログ D19）。
  - 記録するのは**キー入力（何刻み目に、どのキーが押された・離された）と楽器の選択だけ**。姿勢は記録しない。再生では記録から物理を計算し直す。
  - **乱数は使わない。** 使う必要が出たら、種を記録に入れた自作の乱数にする（技術選定 3.1 を先に更新する）。
  - **ブラウザによって結果が変わりうる計算を使わない。** `Math.hypot`・`Math.sin`・`Math.cos`・`Math.pow` などは使わず、平方根は `Math.sqrt(dx * dx + dy * dy)` で書く。`Math.sqrt` と四則演算は規格で結果が決まっている。
  - これらは `src/core`・`src/music`・`src/share` で ESLint が止める（`eslint.config.js`）。誤検知で外すときは、対象ファイルとルールの両方に絞る。

## 7. データと記録の形式（記録・共有URL・素材）

外部から取得するデータは無い。実行時に読むのは、リポジトリに含めた画像と楽器の音、利用者が開いた共有URLだけとする。

- **記録**はキー入力と楽器の選択だけを持つ（6章）。**詰め方（バイト列の形）の詳細は未決で、詳細設計で決める**（→ 非機能要件 N4、要件定義 README 7章）。
- **共有URL**は、記録を詰めたバイト列 → `CompressionStream` で圧縮 → URL で使える文字にして `#` 以降に入れる（→ 技術選定 1章）。先頭に**形式の版番号**を入れる。物理・ループ・音の決め方を変えると、古いURLが別の踊りや音になるため。版が違うURLの扱いと長さの上限は詳細設計で決める（→ 非機能要件 N4）。
- **形式を変えたら版番号を上げる。** 記録の詰め方・物理の規則や数値・音の決め方のどれかを、同じ記録から違う踊りや音になる形で変えたときが対象。
- **画像**（背景・トップページの絵）は自宅Macの Codex で生成し、リポジトリに含める。作り直せるものでも `.gitignore` に入れない（→ インフラ要件 I4）。記録は `ドキュメント/素材/画像の記録.md` に1画像1行で書く（→ 非機能要件 N7）。絵が届くまでは仮の絵で進める（→ N8）。
- **楽器の音（録音したサンプル）**はリポジトリに含めて同じサイトから配信する。外のサイトから直接読まない（→ 技術選定 3.4）。1素材ずつ出所と権利を `ドキュメント/素材/音の記録.md` に残す（→ 非機能要件 N7、技術選定 4章）。形式・サイズの上限は未決（→ 技術選定 4.2）。

## 8. サーバーと秘密値を持たない・公開範囲

- **サーバーと秘密値を持たない。** サーバー側の処理・外部API・鍵は使わない（→ インフラ要件 I1・2章）。共有も URL の `#` 以降だけで完結させる。`#` 以降はサーバーに送られない。
- `.env` は秘密値の置き場として使わない。並行作業で作業ツリーを分けたときの開発サーバーの待受ポート（`SERVER_PORT`）を変えるためだけに使い、無くても既定値で動く。
- **一般公開する**（→ 判断ログ D9・D14）。GitHub Pages でリポジトリ名のパス（`/stick-dance/`）から配信されるので、Vite の `base` を合わせる（→ 技術選定 3.5）。
- 公開する絵と音の素材はすべて、出所と権利確認の記録があるものに限る（→ 非機能要件 N7、受け入れ条件 AC5）。記録の無い素材を配信物に含めない。CC BY の素材は、ゲームの中にクレジットを表示する（F10）。

## 9. 実装の共通ルール

- **後方互換性を維持しようとしない。** 互換レイヤーやフォールバックを追加するのではなく、古い実装や不要になったコードは削除する。使われなくなった関数・設定・ファイルを「念のため」残さない。共有URLの古い版の扱いだけは、詳細設計で決めたとおりにする（7章）。
- **現在の要件を完全に満たす、最もシンプルな実装を選ぶ。** 将来を見越した過剰な抽象化・設定項目・間接化は避ける。インターフェースは実装が複数必要になった時点で作る（例: 記録から踊りと音を作る流れは1つで、踊っている最中・分身・鑑賞・共有URLの再生が同じものを呼ぶ。呼び出し元ごとに別の実装を作らない）。
- **仮の数値（引く強さ・ばねの強さ・分身が残る音の数・テンポ・音量など）は、設定にまとめて名前を付ける。** 数値は遊んで・聞いて決めるため（→ [要件定義](../01_要件定義/README.md) 7章、[音の設計方針](../02_基本設計/設計方針/音の設計方針.md) 4章）。処理の途中に数値を直書きしない。今あるループの設定は `src/core/loop.ts` の `DEFAULT_LOOP`。設定をどこに集めるかは基本設計で決める。
- **音の遅れ（N2）を後付けにしない。** 操作から音が鳴るまでの遅れを、試作で測れる形で作る。
- TypeScriptは `strict` で書き、`any` と型アサーション（`as`）で型検査を黙らせない。外から来るデータ（共有URLから読み戻した記録）は、受け取った場所で形を確かめてから使う。
- **Tone.js は使う版の公式ドキュメントと型定義を見て書く。** Transport を前提にした書き方（`Tone.Transport`・`Tone.getTransport()`・`Tone.Loop`・`Tone.Sequence` など）を持ち込まない（6章）。
- **実装（`src/`）では外部CDNを参照しない。** 必要なライブラリは npm の依存として入れる。
- 公開する関数・型には、役割が分かる日本語のコメントを書く。
- 変更したコードには対応する単体テスト（Vitest、`src/**/*.test.ts`）を用意する。特に `src/core`・`src/music`・`src/share` はテストで仕様を固定する。
- 1コミット＝1つの意図（機能追加とリファクタリングを混ぜない）。

## 10. 機能追加の流れ

新しい機能を追加するときは、いきなりコードを書かず、次の順で進める。実装とテストは**テストファースト**で進める。設計を終えたらまずテストを書いて合格条件（ハーネス）を先に固定し、そのテストが全件成功するまで実装と修正を反復する（テスト側の運用詳細は [テスト方針](../04_テスト/01_テスト方針.md) 9章）。

1. **起票** — `テンプレート/機能追加シート.md` をコピーして、影響範囲を整理する。
2. **要件に追記** — `01_要件定義/01_機能要件.md` に機能を追加する。
3. **画面の設計** — 画面が増える・変わるなら `02_基本設計/画面設計/` と `モックアップ/` を追加し、`01_画面一覧・遷移図.md` を更新する。
4. **処理の設計** — `03_詳細設計/処理設計/` の機能単位ファイルに機能固有の設計判断を書く。記録や共有URLの形式が変わるなら共有の処理設計と本書7章（版番号）を、楽器や音の決め方が変わるなら [音の設計方針](../02_基本設計/設計方針/音の設計方針.md) を更新する。
5. **テストの作成（テストファースト）** — 実装より先に、設計書の仕様を合格条件として表す単体テストを書く（実装がない間は失敗してよい）。画面がある機能は、画面単位の観点表を `04_テスト/テスト仕様書/` に追加し、PlaywrightによるE2Eテスト（`e2e/tests/`）を実装する。
6. **実装（テストが通るまで反復）** — 本書のルール（層の役割・時刻の渡し方・同じ記録から同じ踊りと音）に沿って実装し、`npm run check`（型検査＋静的解析＋単体テスト）が成功するまで「実行 → 失敗の修正」を繰り返す。E2Eテスト（`npm run e2e`）も同様に全件成功させる。音は手で聞いて確かめる。
7. **設計書の更新** — コードとあわせて設計書・README を更新し、乖離させない。
