# Git運用手順

本プロジェクトの Git の使い方をまとめた文書。ブランチの構成と日々の作業の流れを、Git に慣れていない人でも迷わないように説明する。読者は開発メンバー（利用者）と AI エージェントを想定する。

個人統合ブランチの作成やClaudeレビューの設定など、案件の開始時に1回だけ行う管理者向けの作業は [README.md](../../README.md) の「管理者向けセットアップ」にまとめている。メンバーは通常読まなくてよい。

## Git操作の進め方

コミット、push、PRの作成は、原則として **AIエージェント（Claude Code / Codex）に依頼して行う**。VSCode の GUI で手動で行ってもよい。

AIに任せるのは、**コミットメッセージとPRの説明を、他の人が読んで分かる内容にするため**。差分を読んだうえで書けるAIに任せたほうが、「何を、なぜ変更したか」が揃いやすい。手動で行う場合も、メッセージに求める内容は同じ。

> **前提**: AIにGit操作を任せるには、事前に Claude Code または Codex に GitHub 連携（GitHubプラグイン）を設定しておく。

## 1. ブランチ構成

| ブランチ                | 役割                                                         | 直接編集してよい？                                             |
| ----------------------- | ------------------------------------------------------------ | -------------------------------------------------------------- |
| `master`                | 統合ブランチ。プルリクエスト経由でのみ取り込む               | ❌ 禁止（PR経由のみ。例外は下記「PRを経ない反映の例外」）     |
| `dev/自分の名前`        | **個人の統合ブランチ**。作業ブランチを集め、master へPRを出す | ❌ 直接編集しない                                              |
| `dev/自分の名前-作業名` | **作業ブランチ**。実際の編集はここで行う                     | ✅                                                             |

ブランチと作業ツリーは1対1で対応させる。

| 作業ツリー                                   | チェックアウトするブランチ | 役割                                                                    |
| -------------------------------------------- | -------------------------- | ----------------------------------------------------------------------- |
| **本体ツリー**（clone した場所）             | `dev/自分の名前` 固定      | master を取り込む・作業ブランチを集める・PRを出す。**ファイルは編集しない** |
| **作業ツリー**（`.claude/worktrees/<作業名>`） | `dev/自分の名前-作業名`    | 編集・コミット・テスト。作業1件につき1つ作り、終わったら消す              |

### なぜこの構成なのか

- **壊れた変更を混ぜないため**: `master` への取り込みをプルリクエスト（PR）経由にすることで、「テストが通っているか」「設計書を更新したか」をマージ前に確認できる。
- **マージ先が塞がらないようにするため**: `dev/自分の名前` を誰も編集しないことで、作業ブランチをいつでも取り込める。git は同じブランチを2つの作業ツリーで同時にチェックアウトできないため、**編集する場所と集める場所を分けておく**必要がある。
- **本体ツリーを編集しないため**: 編集を作業ツリーに閉じ込めると、本体ツリーの index は常にきれいなまま保たれ、いつでもマージと PR を受けられる。セッションが何本並んでも本体ツリーで取り合いにならない（→「4. 並行作業（複数セッション）」）。
- **同じコンフリクトを繰り返さないため**: 終わった作業を、PRの承認を待たずに `dev/自分の名前` へ入れる。次に切る作業ブランチはそれを含んだ状態から始まるので、完了済みの変更と再びぶつかることがない。
- **master は常に動く状態を保つため**: `master` はいつ誰が clone してもテストが通る状態にしておく。

> ⚠️ **`master` にはブランチ保護をかけていない**（プライベートリポジトリのプラン制約により、保護を設定しても強制されないため）。つまり、技術的には直接 push できてしまう。事故を防げるのは各自の確認だけなので、**作業前に必ず VSCode 左下のブランチ名を見て、自分の作業ブランチにいることを確かめる**。うっかり master にコミットしたときの対応は「5. うっかり master にコミット・push したとき」を参照する。

### ブランチ名のルール

- **個人の統合ブランチ**は `dev/自分の名前`（英小文字）とする。例: `dev/yamada`。**削除せず、ずっと使い続ける**。
- **作業ブランチ**は `dev/自分の名前-作業名`（英小文字とハイフン）とする。例: `dev/yamada-scr14-impl`。**master へ取り込まれたら消す**。
- 作業ブランチは **`dev/自分の名前` から切る**。`master` から切らない（完了済みで master 未反映の自分の変更を取りこぼす）。
- 1つの作業ブランチで複数の画面を跨がない（→「6. コンフリクトを減らす工夫」）。
- 他人のブランチには push しない。

最初に1回だけ、`master` の最新から `dev/自分の名前` を作って push する。AIに依頼するか、VSCode 左下のブランチ名 →「新しいブランチの作成」から行う。

### PRを経ない反映の例外

`master` へPRを経ずに反映してよいのは、次の2つだけ。いずれも**専用のスラッシュコマンド、または専用の GitHub Actions ワークフロー経由に限る**（対象パスが正しいことを機械的に検証するため）。手でmasterに直接pushするのは従来どおり禁止。

| 対象                                                                  | 手段                                                                                   | 理由                                                                       |
| --------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `WBS/` 配下だけの変更                                                 | `/wbs-push`                                                                            | 進捗管理の情報は共有情報で、masterに入って初めてダッシュボードが全員の最新になる |
| バグの**採番と転記**（`04_テスト/バグ/未採番/` → `02_バグ表.md` 3章の表） | GitHub Actions [bug-table-sync.yml](../../.github/workflows/bug-table-sync.yml)（毎朝9時に自動）、`/bug-sync`（kashiwagiだけが手動で実行） | バグIDは共有カウンタで、番号を付ける場所を master のこの処理に限れば取り合いが起きない |

#### WBS配下だけの変更

- **なぜ例外か**: タスクの `status`・`actual` をはじめ `WBS/` 配下は進捗管理の情報で、masterに反映されて初めてダッシュボードが全員の最新になる。ビルドにも影響しないため、コード変更のPRを待たせる理由がない。
- **なぜ `/wbs-push` 経由か**: コミットが `WBS/` 配下だけであることを検証してからpushするため。WBS以外の変更が紛れ込むのを機械的に防ぐ。
- **範囲は `WBS/` 配下すべて**: タスクファイルのほか、ダッシュボード・テンプレート・振り返り・決定事項・`WBS/AGENTS.md` などの運用ルールも含む。ダッシュボードやテンプレートは全員が触るため cherry-pick がコンフリクトすることがあり、その場合は `/wbs-push` が停止して報告する（最新を取り込んでから再実行する）。
- コード変更に伴うタスク更新は、従来どおりそのPRに同梱してもよい。

#### バグの採番と転記

- **なぜ例外か**: `BUG-nnn` はブランチをまたぐ共有カウンタで、各ブランチで番号を付けると並行ブランチと取り合いになり、マージ時に採番のやり直しになる（→「6. コンフリクトを減らす工夫」）。番号を付ける処理を master 上の1か所に限れば、取り合いは起きない。
- **起票は例外ではない**: `/bug-new` は番号を付けず、`バグ/未採番/<担当者>-<日時>.md` を**作業ブランチ**に1つ足してコミットするだけ。ファイルは通常のPRで master に入る。担当者と起票時刻で名前が一意なので、起票同士がぶつからない。
- **なぜ `/bug-sync` と Actions で採番するか**: master 上で `未採番/` のうち**対応の終わったもの**（`状態` が `修正済`・`確認済`・`取り下げ`）を検出日→ファイル名の順に並べ、バグ表3章の表にある最大＋1 から `BUG-nnn` を付けて表の末尾へ1行ずつ転記し、転記できたファイルを消す。手で実行するのはkashiwagiだけ、自動実行は毎朝9時（JST）の [bug-table-sync.yml](../../.github/workflows/bug-table-sync.yml)。実行者を1人と1ワークフローに限り、同時実行は Actions の concurrency と push の拒否で防ぐ。`バグ/` 配下と `02_バグ表.md` 以外を含むコミットは push しない。
- **なぜ対応が終わるまで転記しないか**: 転記は未採番ファイルの削除を伴う。まだ記入している最中のファイルを master 側で消すと、修正内容を書いた作業ブランチとの間で「片方が消し、片方が書き換えた」競合になり、取り込みのたびに全員がぶつかる（→「6. コンフリクトを減らす工夫」）。書き終わったものだけを移せば、削除と記入が同じ時期に重ならない。`未対応`・`対応中` のファイルはそのまま残る。
- **記録は表が正本**: 修正・確認の記入は、対応が終わるまで作業ブランチで `未採番/` のファイルへ書く。転記後に直す場合だけバグ表3章の該当行を書き換え、通常のPRに含める。**PRで表へ行を足すことだけはCIが落とす**（起票は必ず `未採番/` のファイルで行う）。
- **なぜ1日1回か**: 起票のたびに動かさず毎朝にまとめるのは、master への bot コミットを増やさないため。対応を終えた分をすぐ表へ載せたいとき（顧客提出・集計・リリース判定の前）と、自動実行が動かなかったときはkashiwagiが `/bug-sync` を手で呼ぶ。
- **番号が付く前の修正**: 番号は対応が終わってから付く。修正中のコミットメッセージや報告では未採番の名前で呼び、採番後は表の行の `修正コミット` 列で紐付ける。
- レビュー指摘表はこの例外の対象外。起票も更新も通常のPRで行い、採番と番号が重なったときの振り直しは `ドキュメント/管理表/AGENTS.md` を正本とする。

## 2. 日々の作業の流れ

作業を始めてから PR をマージするまでの流れ。

```
① 本体ツリー（dev/自分の名前）に master の最新を取り込む
      │
② /worktree-start <作業名> で作業ツリーと作業ブランチを作り、そこへ移る
      │
③ 作業ツリーで実装・コミット（こまめに）
      │
④ /worktree-end でテストし、dev/自分の名前 へマージして作業ツリーを消す（PRは出さない）
      │
⑤ /create-pr で dev/自分の名前 から master へPRを出す（1日1回以上。溜めない）
      │
⑥ レビュー → /merge-pr で master へマージ
```

本体ツリーで行うのは①④⑤（取り込む・集める・出す）だけで、ファイルの編集は②③の作業ツリーでしか行わない。本体ツリーでの Edit / Write は `worktree-guard` フックが拒否する（`WBS/` 配下は例外）。

### ① 本体ツリーに master を取り込む

本体ツリーは常に `dev/自分の名前` をチェックアウトしているので、そこで `master` の最新を取り込む（マージ）。

**本体ツリーにいるAIのセッションは、`git rev-list --count dev/自分の名前..origin/master` が1以上（＝master未取り込み）なら、人の指示を待たずに取り込む。** 人に毎回「プルして」と言わせない。`session-start` フックが開始時に未取り込みの件数を知らせるので、それを見て取り込む。人から明示的に頼む場合は `/pull` を呼ぶ。VSCode で手作業で行う場合はコマンドパレット（`Ctrl+Shift+P`）→「Git: ブランチをマージ」→ `origin/master` を選択する。

```powershell
git fetch origin
git merge origin/master
git push origin dev/自分の名前
```

**コンフリクトが出たら、どちらを採るかをAIが勝手に決めない。** 解消案とその理由を示してユーザーに決めてもらう（例外は「片側が起票直後の空欄・もう片側が記入済み」のように選択肢が1つしかない場合で、この場合も採った側を報告する）。コンフリクトを解消したコミットは index 全体を対象にするのが正しいため、`git commit --no-edit` で作る（`safe-commit-guard` はコンフリクト解消中のみこれを許可する）。**マージの途中のままセッションを終えない。** 続けられないときは `git merge --abort` で取り込み前へ戻す。

本体ツリーに未コミットの変更が残っていたら、それ自体が事故のサイン（本体ツリーは編集しない決まり）。誰の変更かを確かめ、判断がつかなければ有識者に相談する。

### ② 作業ツリーと作業ブランチを作る

**1件目の作業から、ファイルを1つ触るだけでも作る。** `/worktree-start <作業名>`（Claude Codeのスラッシュコマンド）が、`dev/自分の名前` から作業ブランチ `dev/自分の名前-作業名` を切り、専用の作業ツリー `.claude/worktrees/<作業名>` にチェックアウトして、セッションをそこへ移す。人が手で行う場合も同じ形にする。

```powershell
git worktree add ".claude\worktrees\<作業名>" -b dev/自分の名前-作業名 dev/自分の名前
```

**作業ツリーは `.claude/worktrees/` の中に作る。** Claude Code はこの場所の外へセッションを移すとき、作業ディレクトリ・書き込み権限・`CLAUDE.md` や設定の読み込み元ごと移ることになるため、移動のたびに確認を求める（`EnterWorktree` の許可設定では抑制できない）。リポジトリ配下だが `.gitignore` に入れてあるので、本体ツリーの未追跡ファイルとしては現れない。

- `WBS/` 配下だけを触る作業は例外で、本体ツリーのままでよい（`/wbs-push` がパス指定でmasterへ反映する）。
- 実装（`src/`・`e2e/`・`index.html`・`package.json`・`package-lock.json`・`tsconfig.json`・`vite.config.ts`・`eslint.config.js`）を触る作業では、`.env` の用意が要る（→「4. 並行作業（複数セッション）」の軽量版・フル版）。

### ③ 実装してコミットする

コミットはAIに依頼するか、VSCode 左側の「ソース管理」ビューから行う。

- コミット前に、作業ツリーにいること（`git worktree list` の1行目と違うパス）と、ブランチ名が `dev/自分の名前-作業名` であることを確認する。
- コミットはこまめに行う。
- コミットメッセージは日本語でよい。「何をしたか」が一目でわかるように書く。
- コードを変更したら、対応する設計書もあわせて更新する（[ドキュメント構成.md](../ドキュメント構成.md) 参照）。

### ④ テストして dev/自分の名前 へマージし、作業ツリーを消す

区切りがついたら `/worktree-end`（Claude Codeのスラッシュコマンド）で行う。**ここではPRを出さない。** レビューは⑤のPRで受ける。手で行う場合の中身は次のとおり。

```powershell
# 作業ツリー側
git fetch origin
git merge dev/自分の名前                  # 統合ブランチの最新を作業ブランチへ取り込む（rebase 禁止）
`npm run check`                          # マージしたら必ず通す
git push -u origin dev/自分の名前-作業名   # 本体ツリーへ戻る前に必ず push する

# 本体ツリー側（AIセッションは ExitWorktree で戻る。人は別のターミナルで）
git merge --no-ff dev/自分の名前-作業名
git push origin dev/自分の名前
git worktree remove ".claude\worktrees\<作業名>"
git branch -d dev/自分の名前-作業名
git push origin --delete dev/自分の名前-作業名
```

- 作業ブランチの削除は、`dev/自分の名前` に取り込み済みであれば `-d` で成功する。`-D` は使わない。
- Windowsでは `git worktree remove` が失敗することがある（パス長、そのディレクトリを使っているプロセス。Viteの開発サーバーやPlaywrightが動いたままなど）。原因の見分け方と対処は [worktree-end](../../.claude/commands/worktree-end.md) 手順5にまとめてある。
- AIセッションは作業ツリーから本体ツリーの git を操作できない（ハーネスが `git -C <本体ツリー>` を拒否する）。先に push しておけば、戻れなくなっても作業は失われない。
- 本体ツリーに未コミットの変更が残っているとマージできない。本体ツリーは編集しない決まりなので、**残っていたらそれ自体が事故のサイン**。誰の変更かを確かめてから進める。
- コンフリクトが出たら、**作業ツリー側**（`git merge dev/自分の名前` の段階）で解消する。VSCode の「ソース管理」ビューに現れた「マージ変更」のファイルを開き、**「マージ エディターで解決」** から解消する。2人が別々の行やメソッドを追加した場合は「両方の組み合わせを承認」を選ぶ。わからなくなったらコマンドパレット →「Git: マージを中止」で元に戻せるので、壊す前に相談する。
- マージは成功してもビルドが壊れることがあり、それはテストでしか検出できない。`npm run check` は必ず通す。

> 本体ツリーが塞がっているなど、ローカルでマージできない事情があるときは、`作業ブランチ` → `dev/自分の名前` のPRを立てて GitHub 上でマージしてよい。**このPRはレビューの対象外**で、approve も指摘への返信も要らない（AIの自動レビューも走らない）。レビューは⑤の master 向けPRで受ける。
>
> 誤って master 宛で立ててしまった場合は、GitHub 上で base を `dev/自分の名前` へ付け替えれば直る。向き先チェック（[pr-target.yml](../../.github/workflows/pr-target.yml)）は base の付け替えでも走り直すため、赤い表示は自動で消える（重い `npm run check` は走り直さないので、テスト結果は最後の push のものが残る）。

### ⑤ push して PR を作成する

`/create-pr`（Claude Codeのスラッシュコマンド）で行う。`/worktree-end` が最後に続けて実行する。PR は必ず本体ツリーの `dev/自分の名前` → `master` に向ける。作業ブランチからは出さない。

**1日1回以上出す。溜めない。** 差が育つほどコンフリクトもレビューの負担も跳ね上がる。すでにPRが開いていれば、push するだけで同じPRが更新される。

PRの説明には最低限つぎの2点を書く。

- [ ] 対応する設計書を更新した
- [ ] `npm run check` が通ることを確認した

アプリケーションコードを変更した場合は、上記に加えて**影響する画面のE2Eテストを回して通ったこと**（回したspec名）をPR本文へ記載する。対象specの選び方と実行手順は [影響調査ルール](影響調査ルール.md)「src/ を変更した場合のE2Eテスト」を正本とする。

デザインシステム（`ドキュメント/02_基本設計/画面設計/デザインシステム/`）を変更した場合は、上記に加えて**変更した節・影響成果物**をPR本文へ記載する。

### ⑥ レビューしてマージする

> **CIの検査・AIレビューはマージ直前に `/merge-pr` がローカルで回す。** Actions（CI・PR向き先チェック・AI自動レビュー・`@claude`）は補助で、止まっていても（課金・無料枠超過）マージの判断は変わらない。**PRのチェックが赤いことだけを見て判断しない。**

チームの誰か1人がレビューして approve したらマージしてよい。approve なしでマージしない。

approve は「読んで納得した」という表明であり、責任を伴う。レビュー担当者は、変更の中身を次のレベルまで理解したうえで approve する。

- **設計書の変更**: 何が修正されたか、どんな変更なのかに責任を持つ。内容を理解しないまま approve しない。
- **コード・テストコードの変更**: 細かい実装まで理解する必要はない。どのファイルが、何の目的で変更されたかを理解する。

**レビュー（人・AIとも）の対象は `master` 向けのPRだけ。** 作業ブランチ → `dev/自分の名前` のマージはレビューを通さない（④）。個人ブランチ宛にPRを立てた場合もAIの自動レビューは走らない（[claude-pr-review.yml](../../.github/workflows/claude-pr-review.yml) が base を `master` に絞っている）。

AIによるレビューについても、**指摘には必ずコメントを返す**。対応するのか、しないならなぜかを書く。指摘を放置したままマージしない。

**AIレビューは `/merge-pr` がマージ直前に1回だけローカルで実行し、結果をPRの行コメントとして投稿する**（Actions が使えるなら、PR作成時とドラフト解除時に [claude-pr-review.yml](../../.github/workflows/claude-pr-review.yml) も自動で走る）。指摘が出た時点で `/merge-pr` は停止するので、返信してから再実行する。head に新しいコミットが乗ると再レビューになるため、`@claude` での再レビュー依頼は要らない。**master向けPRは開いたままにして日々pushで更新するが、レビューはマージ直前の内容に対して行われる。**

返信は、**事実**と**判断**を分けて扱う。

| 返信の中身                                                     | 誰が書くか                                                                              |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **対応した事実**（何をどう直したか、どのコミットか）           | AIに書かせて投稿させてよい。差分を読んだうえで書けるほうが正確なため                    |
| **対応しない判断**（指摘が誤り／仕様どおり／今回は見送る）     | **人が決める。** AIに判断を代弁させない。人が決めた理由をAIが清書して投稿するのは構わない |

- AIが**自発的に**返信を投稿しない。投稿は人が指示したときだけ行う。
- 投稿する前に、返信の内容を人が読む。AIの書いた事実が差分と合っているかは、投稿者の責任で確かめる。
- 返信があること自体は `/merge-pr` が機械チェックする（`/merge-pr` は返信を投稿しない。判定だけを行う）。

> ⚠️ **`Claude PR Review` のチェックが赤いとき**: 本来は「レビューが途中で終了し、結果が投稿されていない」ことを表す（差分が大きすぎて読み切れなかった場合などに起きる）。Actions が動いていないときは中身と関係なく赤くなるので、この表示からは何も判断しない。差分が大きいとレビューを読み切れないこと自体は変わらないため、**PRを出す間隔は短く保つ**。

マージは `/merge-pr`（Claude Codeのスラッシュコマンド）で行う。PR番号を渡すと、CI相当のローカル検査・AIレビュー・レビュー指摘への**返信漏れ**・approveの有無を機械チェックし、問題なければマージする。未返信の指摘が残っていれば一覧が提示されるので、返信してから再実行する（ブランチ保護が使えないため、この運用が返信漏れマージを防ぐ唯一の砦になる）。

**マージ手段は `/merge-pr` に一本化する。**

- **GitHubのマージボタンは使わない。** 返信漏れ・ローカル検査を素通りし、押した瞬間に master が壊れうる。
- Claude Code から `/merge-pr <PR番号>` を実行する。`gh` を使うので、GitHubのAPIさえ生きていれば動く（Actions が止まっていても動く）。

マージ方法は **Create a merge commit（通常のマージ）** を使う。

- ※ Squash merge は使わない。個人の統合ブランチを削除せず使い続ける運用では、Squash を使うと履歴のずれが蓄積して次回以降のマージでコンフリクトが増えるため。

マージ後、`dev/自分の名前` はそのまま使い続ける。作業ブランチと作業ツリーは④の `/worktree-end` で既に消えている。残っていれば `/worktree-end <作業名>` で片付ける。

## 3. こまめに取り込む習慣

コンフリクトは「差が育つほど」大きくなる。取り込む向きは2つあり、どちらも放っておくと差が育つ。

| 取り込む向き                    | タイミング                                  |
| ------------------------------- | ------------------------------------------- |
| 作業ブランチ ← `dev/自分の名前` | 毎日の作業開始時（作業ツリーで `git merge dev/自分の名前`）。④の直前は `/worktree-end` が行う |
| `dev/自分の名前` ← `master`     | 毎朝1回（本体ツリーで①）。誰かのPRがマージされたと聞いたとき |

**作業ブランチは1日以内に `dev/自分の名前` へ入れる**ことを目安にする。数日開いたままにすると、ぶつかる量が跳ね上がる。作業ツリーも同じで、1件の作業が終わるごとに `/worktree-end` で消し、次の作業は新しいツリーで始める。

## 4. 並行作業（複数セッション）

セッション（AI・人を問わず）は1本につき1つの作業ツリーで動かす。本体ツリーでは誰も編集しない。**触っているファイルが重ならなくても、同じツリーを共有すると事故が起きる。**

### なぜ分けるのか

gitの index と作業ツリーはセッション間で1つしかない。そのため次が成立してしまう。

- 素の `git commit` は、`git add <パス>` の直後でも index 全体を拾う。他セッションがステージ済みの変更が自分のコミットへ入る
- `git commit --amend` にパス指定は存在せず、必ず index 全体を拾う
- `git merge` は index 全体が HEAD と一致することを要求するため、他セッションのステージ済み変更があるとマージできない

いずれもgitのエラーにならず、正常なコミットとして成立する。コンフリクトとして検知されないため、気づくのは事後（`git show --stat`）かPRレビューになる。

「他のセッションがいるときだけ分ける」運用では、2本目が本体ツリーで始まった時点で両方が編集できなくなり、どちらが移るかで止まる。**最初から全員が作業ツリーへ出る**ことで、本体ツリーは常にマージを受けられる状態に保たれる。

### 分け方

作業を始める前に `/worktree-start <作業名>` を実行する。専用の作業ツリーと作業ブランチが用意される。終わったら `/worktree-end` で `dev/自分の名前` へマージして片付ける（→「2. 日々の作業の流れ」②④）。

用意するものは、作業の中身によって2段階に分かれる。

| 作業の中身                                                                      | 用意するもの                                                                 |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| ドキュメント・設計書・モックアップ・WBSだけ                                     | 作業ツリーとブランチだけ（**軽量版。既定**）                                 |
| `src/`・`e2e/`・`index.html`・`package.json`・`package-lock.json`・`tsconfig.json`・`vite.config.ts`・`eslint.config.js` を触る（アプリを起動する／E2Eを回す） | 上記 ＋ `.env` の複製（**フル版**）。実装ツリーが2本以上並ぶときだけ `SERVER_PORT` を分ける |

**軽量版を既定とする。** アプリを動かさない作業では `.env` は使われないまま残る。途中で実装を触ることになったら、そのとき追加する。

**フル版で `.env` を複製するとき、実装を触る作業ツリーが自分1本だけなら、ポートは本体の既定値（`.env.example` の値）のまま使ってよい。** 本体ツリーは編集もアプリ起動もしないので、ぶつからない。実装ツリーを2本以上並べるときだけ、2本目以降の `SERVER_PORT` を分ける（空き番号の決め方は `/worktree-start` の手順）。

- **同じブランチを2つのツリーで同時にチェックアウトできない。** そのため作業ツリーごとに別の作業ブランチを切る
- `WBS/` 配下だけの作業は分離しなくてよい（`/wbs-push` がパス指定でmasterへ反映するため）
- ツリーを分けてもPCのポートは共有される。実装ツリーが2本以上並ぶときは `SERVER_PORT`（Vite の開発サーバーのポート）を必ず分ける。分けずにアプリやE2Eを回すと、相手のツリーで動いているサーバーを再利用して別のコードを検証してしまうか、起動に失敗して落ちる

### 片付け忘れの見つけ方

作業ツリーは `/worktree-end` を呼ばずにセッションが終わると残る。セッション開始時に `session-start` フックが次を点検して知らせるので、指摘されたら `/worktree-end <作業名>` で片付ける。

- `git worktree list` にあり、ブランチが `dev/自分の名前` に取り込み済みで、未コミットの変更もない作業ツリー（片付け候補）
- `.claude/worktrees/` にあるが `git worktree list` に載っていないディレクトリ（`git worktree remove` が途中で失敗した残骸。削除してよい）
- `git stash list` に残っている stash（この運用では stash を作らない。中身を確認して復元か破棄を決める）

### 本体ツリーで編集せざるを得ないとき

原則として無い。フックが壊れて `/worktree-start` が使えないなど、やむを得ず本体ツリーで編集する場合だけ、コミット対象を必ずパス指定する。`git add <パス>` だけでは足りない。

```powershell
git commit -- <path1> <path2> -m "<メッセージ>"
```

- **新規（未追跡）ファイルは、先に `git add <パス>` してから上記を実行する。** 未追跡のままパス指定だけで `git commit` すると `pathspec ... did not match any file(s)` で失敗する
- `git commit`（パス指定なし）、`git commit -a`、`git commit --amend` は使わない。Claude Codeでは `safe-commit-guard` フックが拒否する。Codex等フックの無い環境でも同じ制約を守る
- コミット後は `git show --stat` で、題目に書いていないファイルが入っていないかを必ず確認する
- 他セッションの未コミット変更を巻き込んだ場合は、`git reset --soft HEAD~1` でコミットを解いてから、パス指定でコミットし直す（相手のステージ済み状態はそのまま戻る）
- `git stash` は使わない。他セッションの未コミット変更まで巻き上げる。本体ツリーでの `git stash` は `safe-commit-guard` フックが拒否する

## 5. うっかり master にコミット・push したとき

**自分で戻そうとせず、有識者に連絡する。**

自己流で戻そうとすると、他の人の作業まで巻き込んで壊すことがある。気づいた時点で作業の手を止めて連絡する。

## 6. コンフリクトを減らす工夫

ブランチの切り方だけでは、全員が触る共有ファイルの衝突は減らない。次の3つを併せて行う。

### バグの起票は1件1ファイルにし、番号は master で付ける

バグの正本は `ドキュメント/04_テスト/02_バグ表.md` 3章の表で、1件が1行（バグ表2-0）。**起票のときだけ**番号なしのファイルを1件1つ `バグ/未採番/` に置く。各ブランチで `BUG-nnn` を採ると、並行ブランチとの取り合いで採番のやり直しが起きる（前案件で繰り返し発生した）。番号を付ける場所を master の1か所に限ることでこれを止める。

**バグの起票は `/bug-new`（Claude Codeのスラッシュコマンド）で行い、番号は付けない。** このコマンドは作業ブランチに `バグ/未採番/<担当者>-<日時>.md` を1つ足してコミットするだけで、ファイルは通常のPRで master に入る。**`BUG-nnn` を付けるのは master 上の `/bug-sync`（kashiwagiだけが実行）と毎朝9時の GitHub Actions だけ**（PRを経ない反映を認める2つ目の例外）。番号を付ける場所が1つなので取り合いが起きず、起票は既存ファイルを書き換えない純粋な追加なので他の起票・修正ともぶつからない。

- 起票時に埋めるのは `検出工程`・`検出日`・`検出者`・`対象`・`事象`・`重要度` と、状態 `未対応` まで。ファイル名・見出しに `BUG-` は書かない
- `対応内容`・`修正コミット`・`状態` の更新は、修正と同じ作業ブランチで、採番前なら `未採番/` のファイルを、採番後なら**バグ表3章の該当行**を編集し、通常のPRに含める。番号が付く前に修正へ着手してよく、その間は未採番の名前で呼ぶ
- 採番と表への転記は毎朝9時（JST）に GitHub Actions（[bug-table-sync.yml](../../.github/workflows/bug-table-sync.yml)）が master 上で行う。日中にすぐ確定したいとき（修正着手前、顧客提出・集計・リリース判定の前）と、自動実行が動かなかったときはkashiwagiが `/bug-sync` を手で呼ぶ
- 手で `BUG-nnn` を付けない。3章の表へ手で行を足さない（新規はすべて `未採番/` へ。バグ表2-1）
- ファイルの書式違反、表の書式違反・ID重複、PRで表へ足した行はCIが落とす（[ci.yml](../../.github/workflows/ci.yml) の「バグ表の検査」）

`ドキュメント/管理表/レビュー指摘表.md` は本節の対象外。表へ直接 `REV-nnn` で起票し、並行ブランチと番号が重なったときは後から取り込む側が振り直す（正本: `ドキュメント/管理表/AGENTS.md`）。

### 1つの作業ブランチで複数の画面を跨がない

同じ画面のシーン（`src/view/`）・E2Eを複数のブランチが同時に触ると衝突する。バグを何件かまとめて直すときは、**画面単位でまとめる**。

- よい: 「SCR11（画面ID）のバグ3件」
- よくない: 「モンキーテストで見つかった全部」

### git rerere を有効にする

一度手で解いたコンフリクトの解決を git が記録し、同じ衝突が再び現れたときに自動で当てる。長く生きたブランチで同じコンフリクトを繰り返し解く手間を減らすための、git 標準の機能。履歴は書き換えないので `rebase` 禁止とは両立する。

各自のマシンで1回だけ設定する。

```powershell
git config --global rerere.enabled true
```

## 7. やってはいけないこと

| 禁止事項                                                          | 理由                                                                                                                                                                                                                             |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `master` への直接push                                             | 保護をかけていないので技術的にはできてしまうが、運用上は禁止。PRを経由する。例外は `/wbs-push`（`WBS/` 配下）と、バグの採番と転記（GitHub Actions の `bug-table-sync.yml`、手動はkashiwagiだけが `/bug-sync`）の2つだけ（→「PRを経ない反映の例外」）                                     |
| `dev/自分の名前` を直接編集する                                   | 作業ブランチのマージ先が塞がる。編集は必ず作業ブランチで行う（→「1. ブランチ構成」）。`dev/自分の名前` へのマージ以外のコミットは `safe-commit-guard` フックが拒否する（`WBS/` 配下だけの `/wbs-push` は例外）              |
| 本体ツリーでファイルを編集する                                    | 本体ツリーは取り込み・マージ・PR専用。編集は `/worktree-start` で作った作業ツリーで行う（→「4. 並行作業（複数セッション）」）。`worktree-guard` フックが拒否する（`WBS/` 配下は例外）                                              |
| 作業ブランチを `master` から切る                                  | 完了済みで master 未反映の自分の変更を取りこぼし、同じコンフリクトを再び解くことになる（→「1. ブランチ構成」）                                                                                                                   |
| 作業ブランチから直接 `master` へPRを出す                          | `dev/自分の名前` が置き去りになり、次に切る作業ブランチが古い土台から始まる（→「2. 日々の作業の流れ」④）。CIが落とす（[pr-target.yml](../../.github/workflows/pr-target.yml)）。base を `dev/自分の名前` へ付け替えれば走り直す |
| `git push --force`（force push）                                  | 他人の作業を消してしまう危険がある。原則使わない                                                                                                                                                                                 |
| `git rebase`                                                      | 履歴を書き換える操作で force push が必要になる。取り込みは merge を使う                                                                                                                                                          |
| コンフリクトを `master` 側で解消する                              | 統合ブランチを直接いじることになる。自分のブランチ側で解消する                                                                                                                                                                   |
| 他人のブランチへの push                                           | ブランチは本人だけが更新する                                                                                                                                                                                                     |
| パス指定のない `git commit`・`git commit -a`・`git commit --amend` | index 全体を拾い、並行セッションの変更まで自分のコミットへ入る（→「並行作業（複数セッション）」）                                                                                                                                |
| `git stash`                                                       | 他セッションの未コミット変更まで巻き上げる。作業ツリーでも、退避はパス指定のコミットかパッチで行う（→「並行作業（複数セッション）」）                                                                                              |
| テストせずにPRをマージする                                        | 「見えないコンフリクト」でビルドが壊れたまま統合される                                                                                                                                                                           |
| レビュー指摘（AI・人とも）に返信しないままマージする              | 指摘の見落とし・握りつぶしにつながる。返信漏れは `/merge-pr` が機械チェックする                                                                                                                                                  |
