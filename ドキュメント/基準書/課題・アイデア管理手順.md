# 課題・アイデア管理手順

チームの中で見つけた課題やアイデアを、GitHub の Issue に集めて一元管理するための手順。読者は開発メンバー（利用者）と AI エージェントを想定する。

タスク管理は `WBS/` の運用手順、Git 操作は [Git運用手順](Git運用手順.md) が正本。ここに重複させない。

## 1. 目的

**「気づいたけれど、まだやると決まっていないこと」の置き場を作る。**

実装中や設計中に出てくる「この作りだと後で困りそう」「ここ、こうした方が使いやすい」といった気づきは、その場でタスクにするほど固まっていない。かといって口頭で流すと消える。これを Issue に置いて、チーム全員が見える形にする。

**ここはチームの気づきを置く場所であって、宿題の管理簿ではない。** 上から降ってくる指摘を混ぜると、書くこと自体が身構える行為になり、誰も書かなくなる。

## 2. 何を載せて、何を載せないか

| 載せる | 載せない | 載せないものの行き先 |
| --- | --- | --- |
| 実装中に気づいた懸念 | PMからの指摘 | 定例など従来どおり |
| 改善アイデア | 顧客からの指摘・要望 | QA表（共有フォルダのExcel） |
| 仕様の引っかかり・疑問 | プルリクエストの指摘 | PRのコメント |
| 技術的負債・気持ち悪さ | やると決まっている作業 | `WBS/タスク/` |

### WBSとの線引き

**「やると決まっているか」だけで分かれる。**

- **Issue** … まだやると決まっていないもの（気づき・アイデアの置き場）
- **WBS** … やると決まった作業（担当・見積・期日がある）

したがって **Issue のゴールは「対応して閉じる」「WBSタスクになって閉じる」「見送りとして閉じる」の三択**になる。Issue が open のまま作業だけ進んでいる状態を作らない。

### 対応するときに、WBSタスクを挟むかどうか

**1つの作業ブランチ・1つのPRで終わる規模なら、Issue から直接着手してよい。** その場合はWBSタスクを起票せず、PRがマージされた時点で Issue を閉じる。着手は `/issue-start <Issue番号>` で始める（Issueの要約と現状確認を経てから作業ツリーへ移る）。

**複数のPRにまたがる、または日をまたぐ規模なら、`/wbs-new` でタスクにして Issue を閉じる。** 担当・見積・期日で追う必要がある大きさだからで、この線を守る限り二重管理にはならない。

判断がつかないときはWBSタスクにする。小さいと思って始めた作業が伸びた場合も、その時点で `/wbs-new` に切り替える。

## 3. 起票する

**タイトル1行だけで起票してよい。本文は空でよい。**

思いついた瞬間に放り込めるかどうかが、この仕組みが生き残るかどうかを決める。整形は後からでもできるし、他の人が補ってもよい。

- 本文のテンプレートは用意するが、**全項目が任意**。埋まっていなくても起票してよい
- **Assignee は付けない。** 付けた瞬間に「その人の宿題」になり、気軽に投げられなくなる。担当が付くのは、やると決まって WBS タスクになるときだけ
- 期日・見積・優先度は書かない（WBS 側の役目）
- ID は振らない。Issue 番号がそのまま ID になる

### Claude Code から起票する

手を止めずに投げたいときは、リポジトリのルートで起動した Claude Code に雑に伝えるだけでよい。

```text
/issue-new 注文確定の在庫の減らし方、同時アクセスで壊れそう
```

重複の確認（閉じた Issue も含む）、種別の判定、`gh issue create` までを行う。**足りない項目を聞き返さない**のがこのスキルの方針で、読み取れない欄は空のまま起票される。あとから本人でも他の人でも書き足せる。

### ラベルは2つだけ

| ラベル | 意味 |
| --- | --- |
| `課題` | 困っている・このままだとまずい |
| `アイデア` | こうしたらもっと良くなる |

**工程区分・優先度・状態のラベルは作らない。** 状態は open / close の2つで足りる。「検討中」のような状態ラベルは誰も更新しなくなって嘘になる。ラベルを増やすのは、件数が増えて探しづらくなってからでよい。

### 賛同は 👍 で示す

「それ自分も思ってた」は、コメントでもリアクション（👍）でもよい。リアクションの数は 4. の選別で「何から見るか」の材料になる。議論しなくても優先順位が浮き上がる。

## 4. 週に1回、3択で選別する

**この場が無いと、ただ増え続けるだけの一覧になる。** 10〜15分で回す。

open の Issue を上から見て、必ず次の3つのどれかに振り分ける。

| 判定 | やること |
| --- | --- |
| **やる** | 1ブランチ1PRで終わるなら `/issue-start <Issue番号>` で着手し、PRのマージ後に **Close**。それより大きければ `/wbs-new` でタスクを起票する → Issue にタスク名を書いて **Close** |
| **見送り** | **理由を1行書いて Close** |
| **保留** | 「いつ見直すか」をコメントに書いて open のまま残す |

### 見送りを堂々と閉じる

**「見送り」を閉じられるかどうかが、この仕組みの成否を分ける。** 判断されないまま残り続けると、開いても意味がない一覧になり、そのうち誰も見なくなる。

捨てた記録が残ることは、起票した人にとって「読まれた」という証拠になる。理由を1行書いて閉じることは、無視することとは違う。

### 保留を溜めない

保留にするときは「いつ見直すか」を必ず書く。書けないなら、それは保留ではなく見送りである。

## 5. Close するときに書くこと

Close する前に、次の1〜2行をコメントする。

```
判定: 対応した / やる（WBSタスク化） / 見送り / （保留はCloseしない）
理由・反映先: PR #123 で対応 ／ WBSタスク「退会処理を実装する」を起票 ／ または見送りの理由を1行
```

**プルリクエストの本文に `Closes #12` は書かない。** 課題の解決とコードのマージは別の出来事で、自動で閉じると上のコメントが残らないまま消える。参照するときは `#12` と番号に言及するだけにする。

## 6. やってはいけないこと

| 禁止事項 | 理由 |
| --- | --- |
| PM・顧客からの指摘を Issue に載せる | 指摘簿と混ざると、気軽に書けなくなって起票が止まる |
| 起票時に Assignee を付ける | 「その人の宿題」になり、投げるハードルが上がる |
| Issue に見積・期日を書く | WBS と二重管理になる |
| 1PRで終わらない作業を Issue のまま進める | 担当・見積・期日で追えない。その大きさのものは WBS タスクにする |
| 対応が終わったのに Issue を開いたままにする | 何が残っているか分からない一覧になる。PRのマージ後に判定を書いて閉じる |
| ラベルを増やす | 埋めること自体が仕事になる。まず2つで運用する |
| 選別せずに放置する | 判断されない一覧は、そのうち誰も見なくなる |
| `Closes #N` で自動クローズする | 判定と理由が残らないまま閉じる |

## 7. 導入時にやること

1. GitHub にラベル `課題` と `アイデア` を作る（**これを先にやる**。ラベルが無いとテンプレートの自動付与が効かない）
2. 週1回の選別を、誰がいつ回すか決める（工程区分 `1_プロジェクト管理` に含まれる）

Issue のテンプレートは `.github/ISSUE_TEMPLATE/` に追加済み。種別ごとに1ファイルとし、選んだ時点でラベルが自動で付く。**空のIssue（テンプレートなし）も許可**してあるので、タイトルだけ書いて送ることもできる。

| ファイル | 付くラベル |
| --- | --- |
| `課題.yml` | `課題` |
| `アイデア.yml` | `アイデア` |
| `config.yml` | （空のIssueの許可と、本書へのリンク） |
