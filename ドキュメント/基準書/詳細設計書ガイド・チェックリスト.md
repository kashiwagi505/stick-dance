# 詳細設計書ガイド・チェックリスト

棒人間ダンシングの外部仕様を実装へ落とし込むときに必要な、機能固有の設計判断だけを記載する。コードや基本設計を再掲しない。

## 1. 正本の分担

| 成果物 | 正本とする情報 |
|---|---|
| 要件・基本設計 | 踊り・ループ・分身・鑑賞のルール、操作と音の対応、画面、メッセージ、画面の切り替え |
| 技術選定の設計方針 | 使う技術、層の分け方と読んでよい層、再現性（記録・物理の刻み・乱数）・時刻・共有URL・音の読み込みの決めごと |
| 音の設計方針 | テンポ・音階・伴奏・人ごとの楽器 |
| 処理設計 | 機能固有の判断、責務、重要な順序、時間の扱い、例外・制御 |
| インフラ要件 | 動作環境、配信、外部サービス、CI |
| コード | 関数、型、モジュールの実装詳細 |
| テストコード | 単体テストの仕様と結果 |

## 2. 作成単位

- 機能要件の1機能につき1ファイルを原則とする。
- 同じ目的とデータを扱う密接な機能群（例: ループ（F3）と分身（F4）、その場の音（F2）と楽器（F5））はまとめてよい。
- 共有URLの形式（記録の詰め方・版番号・版違いの扱い・長さの上限）は、共有の処理設計1か所に書く。

## 3. 記載する内容

- 採用した設計判断、理由、影響
- `src/core`・`src/music`・`src/share`・`src/audio`・`src/view`・`src/main.ts` のうち、その機能で各層が受け持つ責務（→ [アプリケーション実装方針](アプリケーション実装方針.md) 2章）
- 層の間で受け渡すもの（キー入力＋刻みの番号、記録、頭の高さ、鳴らす音の並び）
- ルールの分岐と、後続処理に影響する順序（ループの頭・分身が残るかの判定・最後の1人を消す・鑑賞の始まりと終わりなど）
- 時間の扱い（音の時計を基準に、何が何刻み・何拍・何秒で起きるか）と、同じ記録から同じ踊りと音になる理由（→ 実装方針6章）
- 仮の数値の名前と置き場所（値そのものは設定1か所が正本。→ 実装方針9章）
- 受け付けない操作、共有URLの不備、音の読み込みの失敗、ブラウザの制約の検出箇所と最終動作（→ 実装方針5章）
- 記録の詰め方・共有URLの形式・版番号など固有の制御（→ 実装方針7章）

## 4. 記載しない内容

- import、型定義の全文
- TypeScript風の擬似コード、HTML全文
- 全関数・全型・全項目の一覧
- 画面項目、入力文言、画面の切り替えの再掲
- Vite、Canvas 2D、Tone.js の一般説明
- テストケースやソース行番号

## 5. 作成・レビュー手順

1. 機能要件、関連画面、インフラ要件、技術選定の設計方針、実装方針、既存コードを確認する。
2. 複数の実装方法があり判断を誤りやすい事項を洗い出す。
3. 判断と理由、層ごとの責務、重要な処理順、エラー処理を書く。
4. 実装後にコードと一致するか確認する。
5. コードを読めば一意に分かる記載や他文書との重複を削る。

## 6. レビューチェックリスト

- [ ] 1機能または密接な機能群につき1ファイルである。
- [ ] 機能、画面、共有URLの形式、インフラが各正本と一致する。
- [ ] 設計判断に採用理由または影響がある。
- [ ] 各層の責務・受け渡しが分かり、依存の方向（実装方針2章）に反していない。
- [ ] ルールの分岐と時間の扱いが分かり、`src/core`・`src/music`・`src/share` の中で時計を読む設計になっていない。
- [ ] 仮の数値が設定1か所に名前付きで置かれる設計になっている。
- [ ] 受け付けない操作・共有URLの不備・音の読み込みの失敗・ブラウザの制約の最終動作が分かる。
- [ ] 同じ記録から必ず同じ踊りと音になる設計で、物理を決まった刻み（1/60秒）で進め、`Math.random()`・現在時刻・ブラウザで結果が変わりうる `Math` の関数を使わない（実装方針6章）。
- [ ] コード、画面仕様、一般説明の写経になっていない。
- [ ] 空欄、`TODO`、`TBD`がない。

AIレビューは「問題なし」「要修正」「要確認」を先に示し、対象、根拠、重要度、修正案または確認事項を報告する。
