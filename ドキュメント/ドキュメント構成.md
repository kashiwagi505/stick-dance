# ドキュメント構成

棒人間ダンシングの設計資料と開発基準の配置を定義する。編集ルールは [AGENTS.md](AGENTS.md) を参照する。

## 構成の考え方

- 連番フォルダは `要件定義 → 基本設計 → 詳細設計 → テスト` の工程順とする。
- `基準書/` と `テンプレート/` は工程をまたいで参照する。
- `管理表/` は工程をまたぐ進行管理の記録を置く。顧客とのやり取りで生まれた質問と回答（QA表）は、発注元が本人のため置かない。有識者の紙面レビュー指摘は `レビュー指摘表.md`、品質管理部門がテスト工程で挙げた指摘は `品質管理指摘表.md`（不良と判定したものだけバグ表へも起票）、結合テスト以降の不良は `04_テスト/02_バグ表.md`、チーム内の未決の気づきは GitHub の Issue と、記録先を重複させない。納品対象でない社内進行用の打ち合わせ資料（ヒアリングシート等）は `ドキュメント/` に置かず `WBS/10_Project/打ち合わせ/` に置く。顧客から受領した案件開始前の資料（提案依頼書・提案書・会社基礎情報等）も同様に `ドキュメント/` に置かず `WBS/10_Project/事前資料/` に置く。
- `01_要件定義/03_インフラ要件.md` は、配信（GitHub Pages の静的配信）、開発環境（PCのChrome・Node.js）、環境変数（無し）、外部サービス（GitHub・画像生成の Codex）をまとめる。サーバーは持たない。位置づけは「要件」であり、機能追加時はここを正本とする。
- `01_要件定義/判断ログ.md` は、なぜそう決めたかを却下案と覆す条件つきで残す。要件・設計を変えるときは、該当する判断の「覆す条件」を先に確かめる。
- `02_基本設計/設計方針/技術選定の設計方針.md` は、使う技術とコードの分け方（`src/core`・`music`・`share`・`audio`・`view` と `main.ts`）の正本。曲の雰囲気・伴奏・楽器の割り当ては `音の設計方針.md` が正本。実装のルールとしての書き下ろしは [アプリケーション実装方針](基準書/アプリケーション実装方針.md)。
- API・URL一覧は置かない。サーバーもAPIも無いため。共有URLの形式は、共有の処理設計と [アプリケーション実装方針](基準書/アプリケーション実装方針.md) 7章で扱う。
- 画面一覧・遷移図、画面設計、モックアップは利用者から見える外部仕様を担う。
- `02_基本設計/画面設計/デザインシステム/` が共通外観の正本。配色・書体・余白・形・影・動き・共通部品の規定はこのフォルダ配下だけに置き、他の設計書は [readme.md](02_基本設計/画面設計/デザインシステム/readme.md) へ相対リンクで参照して転記しない。規定の本文は `readme.md`、実数のトークンは `tokens/`、設計意図は `guidelines/`、部品仕様は `components/` に置く。
- 機能追加シートは、`テンプレート/機能追加シート.md` から起票し、合意後に機能要件・各設計へ反映する。シート自体は仕様の正本ではなく、実装するかどうかは機能要件を正本とする。納品対象外の経緯資料として残すシートは、`WBS/退避資料/機能追加/` に1機能1ファイルで置き、納品前にWBSとともに削除する。
- `設計方針/` は、特に重要な処理の全体像と方針（なぜこう作るか）を、関数名・モジュール名を書かずに残す。実装の詳細はコードと実装方針を正本とする。
- 詳細設計は実装を左右する機能固有の判断だけを残す。
- `02_基本設計/` と `03_詳細設計/` は設計の着手時に作る。それまでは各文書からのリンク先が存在しない。
- データベースは使わないため、データベース設計は置かない（→ [アプリケーション実装方針](基準書/アプリケーション実装方針.md)）。
- 未確定事項には担当と決定期限を明記する。設計完了時は確定内容を本文へ反映し、空欄・`TODO`・`TBD`を残さない（[AGENTS.md](AGENTS.md)「スコープ」）。
