起票内容: $ARGUMENTS

このスキルは [Git運用手順](../../ドキュメント/基準書/Git運用手順.md)「6. コンフリクトを減らす工夫」の「バグは1件1ファイルにし、番号は master で付ける」を実行する。

**起票では番号を付けない。** バグIDはブランチをまたぐ共有カウンタで、起票時に採ると並行しているブランチと取り合いになる（実績: 2026-09-01・09-02・09-04・09-07）。
このスキルは **担当者と起票時刻で一意な名前のファイル** `ドキュメント/04_テスト/バグ/未採番/<担当者>-<YYYYMMDD>-<HHmmss>.md` を**いま居る作業ブランチ**に1つ足してコミットするだけにする。master への直接 push はしない。ファイルは通常のPRで master へ入り、`BUG-nnn` は `/bug-sync`（kashiwagiだけが実行。毎朝9時の GitHub Actions も同じ処理）が master 上で付ける（バグ表2-1）。番号を付ける場所が1つなので取り合いが起きない。

## 対象と対象外

- **対象**: [バグ表](../../ドキュメント/04_テスト/02_バグ表.md) 1章の管理対象に当たる不良の**起票**（新しいバグを1件足すこと）。
- **対象外**: 既存バグの更新（`対応内容`・`修正コミット`・`状態`・`確認日`・`密度計上` の記入）。これは修正作業と同じ作業ブランチで、採番前なら `バグ/未採番/…md` を、採番後なら[バグ表](../../ドキュメント/04_テスト/02_バグ表.md) 3章の該当行を編集し、通常のPRに含める。採番は対応が終わってから行われるので、記入先は通常 `未採番/` のファイル。
- **対象外**: 採番と3章の表への転記。どちらも `/bug-sync` と GitHub Actions（[bug-table-sync.yml](../../.github/workflows/bug-table-sync.yml)）が master 上で行う。本スキルは番号にも表にも触らない。
- **対象外**: レビュー指摘表（`ドキュメント/管理表/レビュー指摘表.md`）。本スキルはバグ表専用。

## 1. 前提確認

1. 現在の場所とブランチを確認する。**作業ツリーの作業ブランチ（`dev/自分の名前-作業名`）に居ること。** `master` や `dev/自分の名前` に居たら停止し、`/worktree-start <作業名>` で作業ツリーを作ってから呼び直すよう報告する（本体ツリーの編集はフックが拒否する）。
2. [バグ表](../../ドキュメント/04_テスト/02_バグ表.md) の1章（管理対象）と2章（記入ルール）を読む。管理対象に当たらないものは起票せず、[課題・アイデア管理手順](../../ドキュメント/基準書/課題・アイデア管理手順.md) の Issue かレビュー指摘表へ案内して終了する。
3. 起票前に重複を確認する。`git fetch origin` のうえで、`origin/master` の `ドキュメント/04_テスト/02_バグ表.md` 3章の表と `ドキュメント/04_テスト/バグ/未採番/`、およびいま居るブランチの同じ2か所を `対象`・`事象` で検索し、同一または類似の不良が無いことを確認する。あれば新規起票せずユーザーに確認する。
4. 起票に必要な項目が揃っているか確認する。**起票時に埋める項目**は次の7つ。不足していたらユーザーに聞く。推測で埋めない。

   | 項目 | 内容 |
   | --- | --- |
   | 検出工程 | `結合テスト（人間）` / `結合テスト（AI）` / `システムテスト` / `リリース後`（人が気づいたか、AIの自動テスト・探索で見つけたかで分ける。バグ表1章） |
   | 検出日 | 実際に検出した日（YYYY-MM-DD） |
   | 検出者 | 氏名 |
   | 対象 | 画面ID・機能名（例: `SCR26 / ギフト登録・編集`） |
   | 事象 | 何がどう起きるか。期待結果と実際の結果がわかるように書く |
   | 重要度 | 2-2の判断基準で決める |
   | 状態 | `未対応` |

   残る項目（`混入工程`・`原因`・`対応内容`・`修正コミット`・`確認日`・`密度計上`・`備考`）は**空欄のまま行だけ置く**。修正時に同じ作業ブランチで埋める。**バグIDは付けない**（ファイル名にも見出しにも `BUG-` を書かない）。

## 2. 未採番ファイルを作ってコミットする

ファイル名は `<担当者ローマ字>-<YYYYMMDD>-<HHmmss>.md`。担当者は `検出者` の姓をローマ字小文字にしたもの（kashiwagi→`yamada`、鈴木→`suzuki`、佐藤→`sato`）、日時は起票を実行した現地時刻。例: `yamada-20260908-193012.md`。

```powershell
$stamp = Get-Date -Format "yyyyMMdd-HHmmss"
$stem = "yamada-$stamp"                       # 担当者は検出者に合わせる
$file = "ドキュメント/04_テスト/バグ/未採番/$stem.md"
```

内容は [未採番/README](../../ドキュメント/04_テスト/バグ/未採番/README.md)「書式」と同じで、見出しは `# <stem>`（ファイル名と同じ）になる。「項目 | 内容」の2列表に14項目すべての行を置く。

```markdown
# yamada-20260908-193012

| 項目 | 内容 |
|---|---|
| 検出工程 | 結合テスト（人間） |
| 検出日 | 2026-09-08 |
| 検出者 | kashiwagi |
| 対象 | SCR26 / ギフト登録・編集 |
| 事象 | … |
| 重要度 | 中 |
| 混入工程 |  |
| 原因 |  |
| 対応内容 |  |
| 修正コミット |  |
| 状態 | 未対応 |
| 確認日 |  |
| 密度計上 |  |
| 備考 |  |
```

作ったら書式を検査し、**そのファイル1つだけ**をパス指定でコミットする。push はしない（作業の区切りで `/worktree-end` → `/create-pr` が通常どおり流す）。

```powershell
node .github/scripts/bug-table.mjs check     # 書式・必須項目・ファイル名の検査（未採番も対象）
git add -- $file
git commit -m "バグを起票する（<対象> / <事象の要約>）" -- $file
```

コミット後に検証する: `git show --name-only --pretty=format: HEAD` がそのファイル**1つだけ**であること。他のパスがあれば `git reset --soft HEAD~1` で取り消して停止し、報告する。

- 同じ作業で複数件を起票するときは、1件ずつこの手順を繰り返す（1件1コミット）。秒単位の時刻で名前が分かれる。
- ファイルの読み書き以外で迷いが出たら、自己流で解消せず停止して報告する。

## 3. 番号が付くまでの扱い

- `BUG-nnn` は、**対応が終わってから**確定する。このファイルが master に入り、`状態` が `修正済`・`確認済`・`取り下げ` のいずれかになったあと、`/bug-sync`（毎朝9時の Actions を含む）が `バグ/未採番/` からバグ表3章の表へ転記するときに付く（転記できたファイルは消える）。番号の順は検出日→ファイル名（担当者・起票時刻）。
- 起票直後は `未対応` なので、**このファイルはしばらく `未採番/` に残る。**その間の修正・確認の記入先はこのファイルで、`混入工程`・`原因`・`対応内容`・`修正コミット`・`状態`・`確認日`・`密度計上` をここへ書き足す（バグ表2-0）。
- 修正中はコミットメッセージや報告で未採番の名前（例: `yamada-20260908-193012`）で呼ぶ。採番後の紐付けは、`修正コミット` 列に修正コミットのハッシュを書くことで行う（コミットメッセージは書き換えない）。
- 転記はファイルの削除を伴うので、**対応を終えたあとにこのファイルをさらに編集するときは、先に `git merge origin/master` で最新を取り込む。**取り込まずに書くと、master 側で消えたファイルを書き換える形になり、modify/delete のコンフリクトになる。

## 禁止事項

- ファイル名や見出しに `BUG-nnn` を書くこと（採番は `/bug-sync` の役割）
- `バグ/` 直下へ新しいファイルを置くこと（新規は `未採番/` へ）
- バグ表3章の表へ行を足すこと（転記は `/bug-sync` の役割）
- 起票以外の変更（既存バグの書き換え、他の項目の記入）を同じコミットに混ぜること
- master・`dev/自分の名前` への直接 push、`git push --force`・`git rebase`

## 報告と終了条件

次を1〜3行で報告して終了する。

- 作ったファイル名（未採番の名前）、対象と事象の要約、コミットのハッシュ
- 番号は**対応が終わってから**付くこと。master に入り `状態` が `修正済`・`確認済`・`取り下げ` になったあと、`/bug-sync`（毎朝9時の Actions を含む）が採番する。それまでは未採番の名前で呼び、修正の記入もこのファイルへ書く
- 修正はこのあと作業ブランチで同じファイルを更新し、通常のPRに含めること
