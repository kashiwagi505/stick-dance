作業内容: $ARGUMENTS

このスキルは [Git運用手順](../../ドキュメント/基準書/Git運用手順.md) の「2. 日々の作業の流れ」④⑤を実行し、PR作成までを自動で行う。

```
作業ブランチ ──④マージ（PRなし）──→ dev/自分の名前 ──⑤PR──→ master
```

通常は `/worktree-end` が④（マージと片付け）を行ったうえで、本コマンドの「4. push と PR 作成」以降を続けて実行する。本コマンド単独で呼ぶのは、本体ツリーの `dev/自分の名前` にマージ済みの成果があってPRだけを出したいときと、作業ツリーを使わない例外的な作業のとき。

## 対象と対象外

- **対象**: パイプライン（/run-impl-loop）を使わない作業のPR作成。ドキュメント・モックアップの修正、WBSの更新、小さな改修など。
- **対象外**: /run-impl-loop の実行中・完了時。そちらの手順4がPR作成まで含むので、このスキルは呼ばない。

## 1. 前提確認

1. [Git運用手順](../../ドキュメント/基準書/Git運用手順.md) を全文読む（未読の場合）。
2. 現在の場所とブランチを確認し、以下で分岐する。
   - **`master` にいたら即座に停止してユーザーに報告する。** 勝手に戻さない（Git運用手順5章）。
   - **作業ツリーの作業ブランチ（`dev/自分の名前-作業名`）にいる**: `/worktree-end` の経路が正。同コマンドの手順1〜5（マージと片付け）を実行してから手順4へ進む。
   - **本体ツリーの `dev/自分の名前` にいる**: 統合ブランチは直接編集しない決まり（Git運用手順1章）。未コミットの変更があれば、**なぜここに変更があるのかをユーザーに確認してから**進める。変更が無ければ手順2・3をとばして手順4へ。
3. 未コミットの変更があれば、内容を確認して日本語でコミットする。
   「何をしたか」が一目でわかるメッセージにする。無関係な変更が混ざっていたらコミットを分ける。
   並行セッションがいる場合は**必ずパス指定でコミットする**（`git commit -- <パス> -m "..."`）。
4. 差分（`git diff dev/自分の名前...HEAD`）を読み、今回の変更の全体像を把握する。

## 2. 連動更新の確認

[ドキュメント/AGENTS.md](../../ドキュメント/AGENTS.md) の「連動して更新するもの」の表と差分を照らし、
片側だけ更新されているもの（コードだけ直して設計書が古い、等）がないか確認する。

- 漏れがあれば、PRを作る前に同じ作業ブランチで更新してコミットする。
- 判断できないものは「要確認」としてPR説明に明記する。

## 3. 統合ブランチへマージする（PRは出さない）

1. 作業ブランチ側で `dev/自分の名前` を取り込む（**マージ。rebase 禁止**）。

   ```powershell
   git fetch origin
   git merge dev/自分の名前
   ```

2. コンフリクトが出たら**作業ブランチ側で**解消する。判断に迷う箇所は勝手に解消せず、ユーザーに状況を報告して指示を待つ。
3. 取り込み後に必ずテストと静的解析を実行する。

   ```powershell
   npm run check
   ```

   - アプリケーションのコード（`src/`・`index.html`）を触っていない変更（ドキュメントのみ等）でも、マージを行った場合は実行する。
   - 失敗したら原因を直してから先へ進む。**失敗したまま push・PR作成をしない。**

4. **アプリケーションコードを変更している場合は、影響する画面のE2Eテストも実行する。**

   対象specの選び方と実行手順は [影響調査ルール](../../ドキュメント/基準書/影響調査ルール.md)「検証コマンド」を正本とする（影響ありと判定した画面のspec全部。全件は要求しない）。ドキュメント・モックアップ・WBSだけの変更では実行しない。

   - 実行しなかった場合は、なぜ対象外なのかをPR本文の「確認事項」に書く。
   - 分離した作業ツリーでは `npm ci` と `npm --prefix e2e ci` から始める必要がある（`node_modules` が無い）。

5. `dev/自分の名前` へマージする。**ここではPRを出さない。**

   **同じツリーにいる場合:**

   ```powershell
   git switch dev/自分の名前
   git merge --no-ff dev/自分の名前-作業名
   ```

   **作業ツリーにいる場合**（`dev/自分の名前` は本体ツリーにチェックアウトされたまま）:

   ```powershell
   git push -u origin dev/自分の名前-作業名   # 戻る前に必ず push する
   ```

   push したうえで `ExitWorktree`（`action: "keep"`）で本体ツリーへ戻り、そこで `git merge --no-ff dev/自分の名前-作業名` を実行する。
   **作業ツリーから `git -C <本体ツリー>` は使えない**（ハーネスが拒否する）。先に push しておけば、戻れなくても作業は失われない。マージ後のツリー・ブランチの片付けは [worktree-end](worktree-end.md) の手順5。

   - 本体ツリーに未コミットの変更が残っているとマージできない。`dev/自分の名前` は編集しない決まりなので、**残っていたらそれ自体が事故のサイン**。誰の変更かを確かめ、判断がつかなければ停止して報告する。

## 4. push と PR 作成

1. `dev/自分の名前` を push する（`--force` 禁止）。
2. **既に `dev/自分の名前` → `master` のPRが開いていないか確認する**（`gh pr list --head dev/自分の名前`）。
   - 開いていれば、pushだけで同じPRが更新される。**新しいPRを作らない。** PR本文の「変更内容」に今回分を追記し、URLを報告して終了する。
   - 開いていなければ次へ。
3. PRのタイトルと説明を、**差分と引数（$ARGUMENTS）から自分で起案する**。ユーザーに文面を聞かない。
4. PR を `dev/自分の名前` → `master` に向けて作成する（`gh pr create`）。

### タイトルの書き方

- 変更内容が一目でわかる日本語1文。「何を」＋「どうしたか」を入れる（例: `共有URLを開くと種明かしの旋律が元のプレイとずれる不具合を修正`）。
- 変更の種類が明確なら `feat:` `fix:` `docs:` などの接頭辞を付けてよい（既存コミットの慣例に合わせる）。
- 複数の作業が混ざるPRでは、主目的をタイトルに、残りは説明の概要に書く。

### 説明のテンプレート

差分を読んだうえで、次の構成で書く。「何を、なぜ変更したか」を他の人が差分を開かずに理解できる粒度にする。

```markdown
## 概要

（何を、なぜ変更したか。1〜5行）

## 変更内容

- （主な変更点を箇条書き。ファイル名や画面ID・機能名を添える）

## 確認事項

- [ ] 対応する設計書を更新した（対象がない場合はその旨を書く）
- [ ] `npm run check` が通ることを確認した
- [ ] アプリケーションコードを変更した場合、影響する画面のE2Eテスト（回したspec名を書く）が通ることを確認した（変更していない場合はその旨を書く）

## デザインシステム変更

（`ドキュメント/02_基本設計/画面設計/デザインシステム/` を変更した場合だけ、変更した節・影響成果物を書く。変更していなければこの節ごと省略）

## 要確認

（手順2で「要確認」とした事項。なければこの節ごと省略）
```

## 5. 報告と終了条件

PRのURL・変更概要・`npm run check` の結果を1〜3行で報告して終了する。既存PRを更新した場合はその旨を明記する。
PR作成時に自動レビュー（codex-pr-reviewer＋実装方針レビュー）が走るので、**指摘には必ず返信する**運用であることを添える。対応した事実はAIが書いて投稿してよいが、対応しない判断は人が決める（Git運用手順⑥）。

作業ツリー・作業ブランチが残っていれば（`git worktree list`）、`/worktree-end <作業名>` で片付けることを添える。

## 禁止事項（Git運用手順7章）

- `master` への直接 push・`master` 側でのコンフリクト解消
- `dev/自分の名前` を直接編集する
- 作業ブランチから直接 `master` へPRを出す
- `git push --force`・`git rebase`
- テスト失敗を握りつぶしての push・PR作成
- 他人のブランチへの push
