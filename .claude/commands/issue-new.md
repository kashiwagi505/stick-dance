依頼: $ARGUMENTS

[課題・アイデア管理手順](../../ドキュメント/基準書/課題・アイデア管理手順.md) に従って
GitHub の Issue を起票する。ルールの正本はその手順書。ここには複製しない。

## 対象と対象外

- **対象**: チームの中で見つけた課題・アイデア（まだやると決まっていないもの）。
- **対象外**: 次に当たるものは**起票せず、行き先を伝えて止まる**。
  - PM・顧客からの指摘や要望 → 従来どおり定例で扱う
  - プルリクエストの指摘 → PRのコメント
  - すでにやると決まっている作業 → `/wbs-new` でタスクにする

依頼文が対象外に見えるが断定できない場合は、**起票する前に確認する**。

## 1. 重複を確認する

```powershell
gh issue list --state all --search "<キーワード>"
```

- `--state all` にする。**閉じた Issue も見る。** 過去に「見送り」で閉じたものが再度出てきた場合は、
  その理由をユーザーに示してから、新規に起票するか既存にコメントするかを聞く。
- 似た open の Issue があれば「既存の #N と重複しませんか」と聞いてから進める。

## 2. 種別を決める

ラベルは次の2つのどちらか1つだけ。

| ラベル | 意味 |
| --- | --- |
| `課題` | 困っている・このままだとまずい |
| `アイデア` | こうしたらもっと良くなる |

どちらか判断がつかない場合だけ聞く。**それ以外は聞かない**（下記）。

## 3. 本文は分かる範囲で書く

**このスキルはユーザーに聞き返さないことを優先する。** 起票の軽さがこの仕組みの前提で、
質問を挟むほど「あとで書く」になって消える。`/wbs-new` とは方針が逆であることに注意する。

- 依頼文から読み取れる範囲だけ書き、読み取れない項目は**空のままにする**。埋めるために質問しない。
- 推測で内容を足さない。ユーザーが言っていない懸念や効果を書かない。
- タイトルは内容が一目で分かる日本語1行にする。
- **Assignee を付けない。期日・見積・優先度を書かない。** 付けると「その人の宿題」になり、
  WBS と二重管理になる。

本文の見出しはIssueテンプレートに合わせる。

- `課題` … 気づいたこと / このままだとどうなりそうか / 関連する画面・機能・ファイル
- `アイデア` … やりたいこと / どう良くなるか / 関連する画面・機能・ファイル

## 4. 起票する

本文は一時ファイルに書いてから `--body-file` で渡す（PowerShell で日本語と改行を
コマンドラインに直接埋めると壊れやすいため）。作成後、一時ファイルは削除する。

```powershell
gh issue create --title "<タイトル>" --label "<課題 または アイデア>" --body-file <一時ファイル>
```

- ラベルが存在せずエラーになった場合は、**勝手にラベルを作らず**ユーザーに報告する
  （ラベルは `課題` と `アイデア` の2つだけ。増やさない）。

## 5. 報告と終了条件

作成した Issue の URL・タイトル・付けたラベルを1行で報告して終了する。

- 複数を頼まれた場合は1件ずつ別の Issue にする。まとめない。
- 起票しただけで作業は始めない。**やるかどうかは週1回の選別で決める**（手順書4章）。
  「これはすぐやる」と言われた場合は、Issue ではなく `/wbs-new` を案内する。
