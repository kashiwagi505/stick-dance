対象: $ARGUMENTS

このスキルは**テストファースト（テスト方針9-1）の前半だけ**を行う。設計書の仕様を失敗するテストとして
固定するのが目的であり、**実装本体は書かない**（実装は /run-impl-loop が行う）。
対象機能の処理設計が完成していることが前提（無ければ着手しない）。
以下の順で正本を**全文読んでから**作ること。要約や記憶で書き始めない。

## 1. 着手前に読む

1. [ドキュメント/04_テスト/01_テスト方針.md](../../ドキュメント/04_テスト/01_テスト方針.md) の 3章（単体テスト方針）・7章（テストデータ）・9章（テストファースト） ← 正本
2. 対象機能の処理設計 `ドキュメント/03_詳細設計/処理設計/○○機能.md` と `ドキュメント/01_要件定義/01_機能要件.md` の該当行
   - **処理設計が無い場合はテストを書かない。** 先に処理設計が必要だと報告して終了する。
3. [アプリケーション実装方針](../../ドキュメント/基準書/アプリケーション実装方針.md)（骨格も層の役割・時間の渡し方・strict・ESLintに従うため。特に2章・6章・9章）
4. 見本となる既存テスト `src/**/*.test.ts`（あれば、対象に近い層のものを選ぶ）
5. 仮の数値をまとめた設定（あれば。テストの期待値は数値の直書きではなく設定の名前から導く）
6. `git status --short` で開始時点の既存変更を記録する（完了時のコミット対象の切り分けに使う。既存の変更には触れない）

## 2. 作成手順

1. 処理設計から確認すべき仕様（ルールの分岐・境界値・異常系）を洗い出し、層ごとに振り分ける。
   - `src/core` … 街・移動・配達・記録。時刻を引数で渡し、移動・停止・配達完了・ステージの終わりと、記録の中身（通ったマス・速さ・止まった時間・操作）を確かめる（実装方針6章）
   - `src/music` … 記録 → 音符の並び。乱数の種を固定し、旋律が区画のコードに合う音だけであること（伴奏と旋律がぶつからない）、同じ記録から同じ並び、違う道順から違う並び、曲の長さを確かめる（テスト方針3章）
   - `src/share` … 共有URLの往復（記録 → URL → 記録で一致）、版番号、壊れた文字列で失敗を戻り値で返すこと、WAV のバイト列の組み立て（実装方針5・7章）
   - `src/audio`・`src/view` … 単体テストの対象にしない（Tone.js・Phaser に依存する。テスト方針1章）。画面操作の確認はE2E（/gen-e2e）の担当
2. テスト対象の関数・型が**まだ存在しない場合だけ**、骨格（シグネチャ）を `src/` に追加し、型検査（`tsc --noEmit`）を通す（9-1）。
   - 新規関数の中身は `throw new Error('未実装: /run-impl-loop で実装する');` とし、
     テストが「未実装だから失敗した」と判別できるようにする。
   - **既存の関数の実装は変更しない**（未実装例外への置き換え禁止。既存機能が壊れる）。
     既存機能への追加テストは、現在の実装のままで失敗する（仕様不一致）か成功するかをそのまま確認する。
   - 骨格も実装方針とESLintに従う（`src/` は静的解析の対象）。`any`・型アサーションで型検査を黙らせず、公開する関数・型には日本語のコメントを付ける。時刻・乱数の種・ステージのデータは引数で受け取る形にする（実装方針6章）。
3. テストごとの前提データ（小さな街・区画・マスの音・記録など）が必要なら、テストファイルの中で素のデータとして組み立てる。`src/data` の本番のステージに頼らない。テスト間で共有する場合の置き場所はテスト方針3章・7章に従う。
4. テストを `src/**/*.test.ts`（対象ファイルと同じ場所に `<対象>.test.ts`）として実装する。期待値は**処理設計・機能要件から導く**。意図は `describe`・`it` の名前と日本語のコメントで読めるようにする
   （テスト内容は設計書に残さない。テストコードが正本＝テスト方針1章）。
5. `npm test` を実行し、**新しいテストが「未実装」を理由に失敗し、既存テストは全件成功のまま**で
   あることを確認する。型エラーや設定ミスによる失敗は直す。あわせて `npx tsc --noEmit` と `npx eslint .` が通ることを確認する（失敗するのはテストだけにする）。

## 3. 禁止事項

- 実装本体を書かない。骨格（シグネチャ＋未実装例外）まで。テストを通し始めたらこのスキルの範囲を超えている。
- 期待値を実装の都合に合わせない・弱めない（9-1）。設計書に無い仕様が必要になったら、
  テストを止めて先に設計書の修正を提案する。
- 共有URLの形式（版番号）や層の読んでよい向きを変える必要があると分かったら手を止める（共有の処理設計・実装方針と連動ファイルの更新が先。ドキュメント/AGENTS.md の連動表を参照）。
- テストの中で実際の時計（`Date.now()`・`performance.now()`）・`Math.random()`・タイマーの実時間待ちに頼らない。時刻と乱数は引数で固定する（実装方針6章）。
- テストから外部へ通信しない（外部サービスは使わない）。
- テストを実行順に依存させない。実行後にファイルを残さない（3章）。

## 4. 完了時にやること・報告

1. セルフチェック: 処理設計の分岐・境界値・異常系がテストケースに対応しているか。層（`src/core`／`src/music`／`src/share`）の漏れがないか。
2. **Codexにレビューさせる**: codexプラグイン（/codex:rescue）でテストコードのレビューを依頼する（読み取りのみ・修正はさせない）。
   レビュー観点: 処理設計の分岐・境界値・異常系の抜け、期待値が設計書と一致しているか
   （実装の都合に寄っていないか）、実行順依存・時計や乱数への依存、モックの使いすぎ。
   指摘を反映したら手順5の失敗確認をやり直す。対応に迷う指摘はコミットメッセージと報告に持ち越す。
3. 開始時に `git status --short` で記録した既存の変更には触れず、**今回作成・変更したファイルだけ**
   （テストコード・新規の骨格。既存テストファイルへの追加分も含む）をパス指定でステージし、
   `git diff --cached` で無関係な変更やステージ済みファイルが混ざっていないことを確認してからコミットする
   （メッセージ例: `旋律の生成機能の単体テストを作成（テストファースト・実装前）`）。
   ブランチが作業ブランチ（`dev/自分の名前-作業名`）であることをコミット前に確認する。`master` または `dev/自分の名前`（統合ブランチ）にいたら停止し、`/worktree-start <作業名>` で作業ツリーを作るよう案内する（Git運用手順「1. ブランチ構成」）。
4. 報告: 層ごとのケース数、骨格として作った関数・型、失敗確認の結果（未実装による失敗のみか）、
   Codexの主な指摘と対応を1〜5行でまとめ、「実装は /run-impl-loop で進めてください」と案内して終了する。
