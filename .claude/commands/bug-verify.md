バグは `未対応` → `対応中` → `修正済` → `確認済` の順に進む（[バグ表](../../ドキュメント/04_テスト/02_バグ表.md) 2-3）。`修正済` は「修正をコミットしたが、まだ再確認していない」状態で、**修正した本人が直したつもりでも、事象が消えたことを見ていない**。リリース判定は「バグ表の不良がすべて `確認済` または `取り下げ`」（[テスト方針](../../ドキュメント/04_テスト/01_テスト方針.md) 2章）なので、`修正済` が残っているとリリースできない。このコマンドは、その残りを消化する。

`/bug-new` が起票、`/bug-sync` が採番と転記を担当するのに対し、本コマンドは**状態を `修正済` から `確認済` へ進める**ところを担当する。再テストで事象が再発した場合は、**その場で直して再テストが通るところまで**を含む（手順3-1）。`修正済` なのに事象が残っているのは修正が足りていないということなので、突き返さずにここで片づける。ただし直すのは再テストで落ちた件だけで、`未対応`・`対応中` のバグには手を出さない。

直した件も `確認済` にしてよい（自分で直して自分で確認する形になるが、その経緯を備考に残し、PRのレビューで人が見る）。**回数には上限がある**（同じバグにつき3回まで。手順3-1）。上限に達したものは直さずに残し、**最後にまとめて人の判断を仰ぐ**（手順3-2・報告4）。

## 対象と対象外

- **対象**: `状態` が `修正済` のバグ。バグ表3章の表の行と、`バグ/未採番/` のファイルの**両方**を見る（採番は対応が終わってから行われるため、`修正済` は表と未採番のどちらにもあり得る。バグ表2-0）。
- **対象外**:
  - `未対応`・`対応中`（まだ修正されていない。着手は別の依頼で行う。**このコマンドが直すのは、再テストで落ちた `修正済` だけ**）
  - `確認済`・`取り下げ`（済んでいる）
  - 採番と表への転記（→ `/bug-sync`）、起票（→ `/bug-new`）
  - 再テストで見つかった**別の**事象（→ `/bug-new` で新しく起票する。元のバグへ書き足さない）

## 手順

### 0. 作業ツリーを用意する

バグ票を書き換え、アプリを起動してE2Eを回し、再発したものはアプリケーションのコード（`src/`）を直すので、`/worktree-start bug-verify` の**フル版**（他にも実装を触る作業ツリーがあれば `.env` の `SERVER_PORT` を分ける）で始める。本体ツリーで実行しない。軽量版に落とさない（手順3-1で実装を触る）。

### 1. `修正済` を洗い出す

```powershell
# 未採番ファイル
Select-String -Path "ドキュメント\04_テスト\バグ\未採番\*.md" -Pattern '^\| 状態\s*\|\s*修正済\s*\|' | ForEach-Object { $_.Path }
# バグ表3章（状態は後ろから4列目）
node -e "const fs=require('fs');for(const l of fs.readFileSync('ドキュメント/04_テスト/02_バグ表.md','utf8').split(/\r?\n/)){if(!l.startsWith('| BUG-'))continue;const c=l.split('|');if(c[c.length-5].trim()==='修正済')console.log(c[1].trim())}"
```

0件なら「`修正済` は無し」と報告して終了する。**件数を報告に必ず入れる**（リリース判定の材料になる）。

### 2. 1件ずつ「何をもって解消と言えるか」を決める

バグ票の `事象`（**期待結果がここに書いてある**）・`対応内容`・`修正コミット` を読み、合格条件を1文で決める。`対応内容` をなぞるのではなく、`事象` に書かれた期待結果に戻って決める（対応内容どおりに直っていても、事象が消えていなければ `確認済` にしない）。

そのうえで3つに仕分ける。

| 仕分け | 条件 | 進め方 |
|---|---|---|
| **自動** | 事象そのものを検証するE2E spec・単体テストが**ある**（テスト観点番号と一致するテスト名、または該当の検査メソッド） | 手順3で実行する |
| **目視** | 自動テストが無い、または**あっても事象を検知できない**（例: 並び順の不良に対してE2Eが `getByRole('button', { name: ... })` で名前から取っており、左右の並びを見ていない） | 手順4で一覧にする |
| **環境待ち** | 耳で聞くこと・公開先の GitHub Pages・別のブラウザが要り、E2Eでも単体テストでも成立しない（例: 伴奏と旋律がぶつかって聞こえる、共有URLを別のブラウザで開くと違う曲に聞こえる、書き出したWAVが種明かしと違って聞こえる） | 手順5で据え置く |

**「テストがあるはず」で自動に入れない。** 該当するテストのファイル名・テスト名・行番号を実際に見て、そのテストが**この事象を落とせるか**を確かめてから振り分ける。

### 3. 自動分を実行する

```powershell
npm run check                              # 型検査＋静的解析＋単体テスト
npm --prefix e2e ci                        # 作業ツリーは e2e/node_modules が無いので初回だけ
npm --prefix e2e test -- -g "SCRxx-nn"     # 観点番号で1件ずつ
npm run e2e -- scrxx                       # 画面まるごと回すとき（ファイルパスの部分一致）
```

- `npm run check` と E2E は**同時に走らせない**（ゲームは音の時刻で進むため、負荷で移動・配達の時刻がぶれる。`e2e/playwright.config.ts` が `workers: 1` で直列に流すのと同じ理由）。
- **全件の完走は求めない。**変更範囲のspec・観点だけを回す。
- 実行したコマンドと結果（成功件数・失敗件数）を控える。報告と備考に書く。

**失敗したら `確認済` にしない。**まず、落ちた原因がテスト側の不整合（負荷による時間判定のぶれ・並行実行による時間切れ・他の作業ツリーとのポートの重なり）かどうかを見る。テスト側が原因なら、そう判断した根拠を報告に書いてから再実行する。**事象そのものが再発している**なら手順3-1へ進む。

### 3-1. 再発したものは直す（同じバグにつき3回まで）

1. 該当機能の処理設計書（`ドキュメント/03_詳細設計/処理設計/*.md`）と [アプリケーション実装方針](../../ドキュメント/基準書/アプリケーション実装方針.md) を読む。
2. バグ票の `修正コミット` の差分（`git show <SHA>`）を見て、**前の修正で何が足りなかったか**を1文で言う。原因を言えないまま直さない（テストが通る形にコードを寄せることになる）。
3. 直して、落ちたテストと `npm run check` を再実行する。実装を触ったので [AGENTS.md](../../AGENTS.md) の連動更新（設計書・README）も同じ変更で行う。
4. 通れば手順6へ進み、`確認済` にする。通らなければ1へ戻る。

**1〜4の往復は同じバグにつき3回まで。** 3回とも通らなければそこで打ち切り、手順3-2へ移る。時間をかければ直ると考えて4回目に進まない。

次のものは**回数に関係なく直さない**。1回目で当たったらそこで手を止める。

- 設計書の記載と実装が食い違っていて、**どちらを直すのが正しいか決まらない**もの → 手順3-2（人の判断待ち）
- 直すと他機能の仕様が変わるもの（画面の項目を増やす・操作と音の対応を変える・共有URLの形式（版番号）を変える） → 手順3-2（人の判断待ち）
- 原因が環境側にある可能性が残っているもの（音を聞く機材・ブラウザの音の機能・公開先の GitHub Pages） → 手順5（環境待ち。`修正済` のまま据え置く）

### 3-2. 直せなかったものは残して、次のバグへ進む

3回で直らなかった件と、上の「直さない」2つに当たる件は、次のようにして**次の `修正済` の処理へ進む**。1件のために全体を止めない。

- `状態` を `対応中` へ戻す（`確認日` は空のまま）
- 備考に、再テストで再発したこと・試した修正の要点（3回ぶんを並べず、分かったことだけ）・どこで行き詰まったかを書く
- **途中までの修正コードはコミットしない**（`git checkout -- <パス>` で戻す）。中途半端な修正が次の人に渡らないようにする。分かったことは備考に残っているので失われない
- 報告4の「人の判断待ち」へ積む

**ここで人に聞きに行かない。**残りの `修正済` を最後まで処理してから、手順7の報告でまとめて判断を仰ぐ。

### 4. 目視分を一覧にして人へ渡す

**AIのスクリーンショット判断で `確認済` にしない。**`確認済` は「再テスト実施者が事象の解消を確認した状態」（バグ表2-3）で、自動テストが検知できないから目視に回している以上、見るのは人。

1件につき次を書いて渡す。**「画面を見てください」で終わらせない。**

- バグID（未採番ならファイル名）と対象画面
- 開くURL（作業ツリーの `SERVER_PORT` を入れた実URL。画面は1ページなので例: `http://localhost:5001/`）
- そこへ至る前提（遊ぶステージ、キーボードで出す操作とその順番、再現に使う共有URL（記録と乱数の種が入っているので同じ曲を再現できる））
- 見る場所（要素・領域を名指しする）
- 期待（バグ票の `事象` に書かれた期待結果をそのまま引く）
- ウィンドウの大きさの条件（バグ票が大きさに触れていれば、その大きさも）

人から「解消を確認した」と返ってきてから手順6へ進む。返事が無いものは `修正済` のまま残し、報告に「目視待ち」として載せる。

### 5. 環境待ちは据え置く

`修正済` のまま、`確認日` は空のままにする。備考の「残る確認」を**今の状況に合わせて書き直す**（何を・どの環境で・いつ確認するか）。ローカルで代わりになる確認をしても `確認済` にしない。

### 6. 記入する

書き込み先は、そのバグが `バグ/未採番/` にあるならそのファイル、3章の表にあるならその行（バグ表2-0）。

| 項目 | 書く内容 |
|---|---|
| `状態` | `確認済` |
| `確認日` | 再テストを実施した日（`YYYY-MM-DD`） |
| `備考` | 既存の記述の末尾へ、**確認方法と確認者**を足す。例: `SCRxx-nn・SCRyy-nn のE2E再実行で確認（kashiwagi）` / `種明かし画面を1440×900で開き、軌跡と灯った窓が音に合って光ることを目視と耳で確認（kashiwagi）` |

手順3-1で直した件は、備考に**再発したことと追加修正**も書く。例: `再テストでSCRxx-nnが再発。<原因>のため追加修正（コミット <SHA>）、同specの再実行で解消を確認（kashiwagi）`。直した事実を隠して `確認済` にしない（PRのレビューで人が見る材料になる）。

`対応内容` は、追加修正で中身が変わったなら追記する（前の記述を消さない）。`修正コミット` には追加修正のSHAを足す。

`密度計上` が空なら、アプリケーションのコード（`src/` の `*.test.ts` 以外と `index.html`）を変更したかどうかで `○` / `—` を埋める（バグ表2-5）。**手順3-1でアプリケーションのコードを触ったなら `○`。**項目は増やさない。

### 7. コミットして閉じる

```powershell
# 手順3-1で直した分（バグ1件ごとに分ける。まとめて1コミットにしない）
git commit -- src/music/... src/music/....test.ts ドキュメント/03_詳細設計/処理設計/....md -m "fix: ...（BUG-nnn 再発分）"
# 状態の更新
git commit -- "ドキュメント/04_テスト/バグ/未採番" "ドキュメント/04_テスト/02_バグ表.md" -m "バグを確認済にする（...）"
```

パス指定でコミットする（同じ作業ツリーの他セッションの変更を巻き込まないため）。手順3-2で打ち切った件の**修正コードは含まれていないこと**を `git status --short` で確かめてからコミットする。そのあと `/worktree-end` → `/create-pr`。未採番ファイルは master に入ったあと `/bug-sync` が採番して表へ転記する。

## 禁止事項

- 自動テストも人の目視もせずに `確認済` にする
- 該当するテストの中身を見ずに「テストがあるから自動」と仕分ける
- 環境待ちのものをローカルの代替確認で `確認済` にする
- 再テストで見つかった別の事象を、元のバグ票へ書き足す（`/bug-new` で別に起票する）
- `修正済` 以外（`未対応`・`対応中`）のバグを、ついでに直す
- 前の修正で何が足りなかったかを言えないまま直す（落ちたテストが通る形にコードを寄せる）
- 3回直しても通らないものを、4回目・5回目と続ける
- 直せなかった件を1件ずつ人に聞きに行く（最後の報告でまとめる）
- 打ち切った件の途中までの修正をコミットする、または直っていないのに `修正済` のまま残す
- 手で `BUG-nnn` を付ける、3章の表へ行を足す（→ `/bug-sync`）

## 報告と終了条件

次の5つを報告して終了する。

1. `確認済` にした件数と、1件ずつの根拠（実行したテストと結果）。**再発して直した件は、原因・追加修正のコミット・再々テストの結果**も添える
2. **目視待ちの一覧**（人が見る場所。手順4の形式のまま）
3. **環境待ちの件数と、確認できる条件**（いつ・どの環境で）
4. **人の判断待ちの一覧**（手順3-2で打ち切った件）。ここが人に決めてもらう場所なので、1件につき次を書く。「直せませんでした」だけで渡さない
   - バグID（未採番ならファイル名）と、再テストで再発した事象
   - 前の修正で足りなかったと分かった点（分かった範囲まで）
   - 試したことと、行き詰まった点（なぜ3回で通らなかったか）
   - **考えられる進め方を2つ以上**（例: 設計書の記載どおりに実装を直す／実装に合わせて設計書を直す。どちらを採るかは人が決める）
5. 別に起票した新しいバグ

最後に、残った `修正済` の件数を1行で添える（リリース判定はここが0になるまで進まない）。
