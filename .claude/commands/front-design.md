**前提:** 公式プラグイン `frontend-design` を使う。未導入の環境では手順2で失敗するので、
その場合は作業を止めて「プラグイン `frontend-design` の導入が必要」とユーザーへ報告する。

## 1. 着手前に読む（要約で進めない）

1. [ドキュメント/02_基本設計/画面設計/デザインシステム/readme.md](../../ドキュメント/02_基本設計/画面設計/デザインシステム/readme.md) と同フォルダ配下（`tokens/`・`guidelines/`・`components/`） ← **共通の見た目の正本**
2. [ドキュメント/基準書/画面設計書ガイド・チェックリスト.md](../../ドキュメント/基準書/画面設計書ガイド・チェックリスト.md)
3. 対象画面の設計書 `ドキュメント/02_基本設計/画面設計/SCRXX_○○画面.md` と**同名モックアップ**
4. [ドキュメント/AGENTS.md](../../ドキュメント/AGENTS.md) の「画面設計とモックアップ」「連動して更新するもの」
5. [ドキュメント/02_基本設計/モックアップ/README.md](../../ドキュメント/02_基本設計/モックアップ/README.md) の「利用してよい外部リソース一覧」

## 2. 手順

1. `Skill` ツールで `frontend-design:frontend-design` を呼び、スキルの指示を読み込む。
2. **`ドキュメント/02_基本設計/画面設計/デザインシステム/` が正本。** 既存のトークン・部品・規則を先に読み、勝手な新体系を持ち込まない。
   全画面共通の判断が不足している場合はデザインシステム側で規定を確定してから実装する。画面設計書やモックアップへ共通規定を転記せず、相対リンクで参照する。画面固有の判断は対象画面の画面設計書へ記載する。
3. ブリーフが曖昧でも確認で止まらず、**対象・読者・その画面の唯一の仕事**を自分で仮決めして明言する。
4. スキルの二段構え（design plan → 自己批評 → 実装）に従う。色4〜6値・書体・レイアウト案・
   signature（その画面が記憶される一点）をトークンとして先に出す。
5. 生成AIの既定の見た目（クリーム地＋高コントラストserif＋テラコッタ／黒地＋アシッドグリーン／新聞風hairline）に
   落ちていないか点検し、落ちていたら理由を添えて直す。
6. `.claude/skills/` の `accessibility` の数値基準を満たす（→ [.claude/skills/README.md](../skills/README.md)）。中身は canvas に描くゲームで検索向けの要件が無いため、`seo` は当てない。
   ただし寸法系はプロジェクト正本（[デザインシステム](../../ドキュメント/02_基本設計/画面設計/デザインシステム/readme.md)「決めごと」）が優先する。
   - クリック対象は44px以上、本文フォント 16px 以上
   - `<h1>` はページに1つ、見出しレベルを飛ばさない
   - キーボードフォーカスが見える、`prefers-reduced-motion` に対応する

## 3. このプロジェクトの制約

- **1画面 = 設計書1ファイル ＋ 同名モックアップ1ファイル。片方だけ変更しない。**
  実装（`src/view/`・`index.html`）を直した場合も、同じ変更でモックアップを追従させる。
- モックアップは**ビルド不要**で、HTMLを直接開いて確認できる状態にする。
- 外部CDNは `モックアップ/README.md` の「利用してよい外部リソース一覧」にあるものだけ使う。実装（`src/`）では外部CDNを参照しない（→ [アプリケーション実装方針](../../ドキュメント/基準書/アプリケーション実装方針.md) 9章）。
- 配置は HTML が `モックアップ/` 直下、CSS は `css/`、JavaScript は `js/`、画像は `img/`。
- 対象はPCのChromeだけ（→ [非機能要件](../../ドキュメント/01_要件定義/02_非機能要件.md) N1）。スマートフォン・タブレット向けのレスポンシブ対応はしない。
- 実装側は `index.html` と `src/view/`（棒人間と舞台は Canvas 2D、トップページ・ボタン・案内は HTML と CSS）。画面はブラウザ1枚で動かし、ページ遷移ではなく HTML の表示切り替えで画面を変える（→ 実装方針3章、技術選定の設計方針 1章）。
  利用者向けの文言は `src/view/` の文言定義へ置き、描画処理に直接書かない（→ 実装方針4章）。
  新規デザイン仕様（色・書体等の共通規定）は実装のCSSへ直接追記せず、まずデザインシステムを更新してから反映する。
- 実装側のCSSの置き場所と分け方は [デザインシステム](../../ドキュメント/02_基本設計/画面設計/デザインシステム/readme.md)「3. 実装への写し方」に従う（`src/view/styles/` に共通の `tokens.css`・`components.css` と画面ごとの1ファイル、書体は `public/fonts/`）。

## 4. 完了時の報告

- 何をどう変えたか（トークン・レイアウト・signature）を数行で説明し、デザインシステム側を変更した場合は変更した節・影響成果物も明示する。
- **設計書とモックアップの両方を更新したこと**を明示する。片方だけ触った場合はその理由を書く。
- 実装画面とモックアップを比較して差分が残っている場合は、残差分を列挙する。
- コミットはしない。
