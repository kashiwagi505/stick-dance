依頼: $ARGUMENTS

[課題・アイデア管理手順](../../ドキュメント/基準書/課題・アイデア管理手順.md)「4. 週に1回、3択で選別する」と
[Git運用手順](../../ドキュメント/基準書/Git運用手順.md)「2. 日々の作業の流れ」に従って、Issueへの着手を始める。
ルールの正本はその2つ。ここには複製しない。

## 対象と対象外

- **対象**: open の Issue に着手するとき（「issue#N に対応したい」「#N について教えて」を含む）。
- **対象外**: 次に当たるものは**着手せず、行き先を伝えて止まる**。
  - 起票 → `/issue-new`
  - 複数のPRにまたがる・日をまたぐ規模 → `/wbs-new` でタスクにする（手順3で判定する）
  - システムテストで見つけた不良 → `/bug-new`、`harness-resolution`
  - PRのレビュー指摘 → `pr-review-resolution`

## 手順

### 1. Issueを読む

```powershell
gh issue view <番号> --comments
```

閉じている Issue だった場合は、**閉じた理由をユーザーに示してから**、続けるかどうかを聞く。

### 2. 内容を平易に報告する

**先に日本語で要点を書く。** パス・行番号の羅列から始めない。

- 何に困っているか / どうなれば解決したと言えるか
- ラベル（`課題` / `アイデア`）と、コメントで出ている論点
- 関連しそうな他のIssue・バグ・WBSタスクがあれば番号だけ

### 3. 現状を調べて報告する

**ここまでファイルを変更しない。** Issueは起票から時間が経っていることがあり、書かれた前提がすでに変わっている（直っている・仕様が変わった）ことがある。

- 該当する実装・設計書・テストの**現在の姿**を確認する。分類と順序は [影響調査ルール](../../ドキュメント/基準書/影響調査ルール.md) に従う
- Issueに書かれた事象が今も再現するかを確認する。再現しないなら、その事実を報告して着手可否を聞く
- 読む量が多い調査は `Explore` へ委譲し、生ログをメイン会話へ持ち込まない（[AGENTS.md](../../AGENTS.md)）

あわせて規模を判定する。**1つの作業ブランチ・1つのPRで終わらない**と判断したら、`/wbs-new` を案内してここで止まる。

### 4. 判断が分かれる点は、選択肢にして人に決めてもらう

**AIが決めない。** 直し方が2つ以上あるとき、どちらでもよさそうに見えるものも含めて、案と違いを示して聞く。

- 各案について「何が変わるか」「他への影響」「戻しやすさ」を1行ずつ
- **着手前に決まっていないと手戻りする判断だけを先に聞く。** 細かい判断は着手後にまとめて聞いてよい
- 判断材料が足りないなら、足りないものを言う。推測で案を作らない

### 5. 承認を得てから着手する

ユーザーが着手を認めたら `/worktree-start <作業名>` で作業ツリーへ移り、作業を始める。

対応が終わったら `/worktree-end` → `/create-pr`。**PRがマージされたら、Issueに判定と反映先（`対応した` / PR番号）を書いて閉じる**（課題・アイデア管理手順5章）。

## 終わり方

手順2〜3の報告と手順4の選択肢を提示し、**着手してよいかを確認して終了する**。承認なしに手順5へ進まない。

対象外と判定した場合は、行き先（`/wbs-new` など）を伝えて終了する。
