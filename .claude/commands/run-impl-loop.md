対象: $ARGUMENTS

このスキルはテストファースト（テスト方針9章）の後半を行う。**完了判定は人の目視ではなくテストの全件成功**。
最初に完了条件を宣言し、達成するまで自律的に反復すること。途中で「たぶん動く」で止めない。

## 1. 着手前に読む・前提確認

1. [アプリケーション実装方針](../../ドキュメント/基準書/アプリケーション実装方針.md) ← 実装の正本
2. 対象機能の処理設計 `ドキュメント/03_詳細設計/処理設計/○○機能.md`
   - **無い場合は実装を始めない。** 先に処理設計が必要だと報告して終了する。
3. [ドキュメント/04_テスト/01_テスト方針.md](../../ドキュメント/04_テスト/01_テスト方針.md) の 4章（E2Eの運用ルール・実行方法）と 9章（反復ループの正本）
4. [Git運用手順](../../ドキュメント/基準書/Git運用手順.md) の 2章（PRまでの流れ）
5. **ハーネスの存在確認**: 対象機能の単体テスト（未実装で失敗する状態）と、対象画面の観点表・specがあるか。
   - 単体テストが無い → /gen-unit-test を先に実行するよう案内して終了する。
   - 観点表・specが無い → /gen-e2e-scenario → /gen-e2e を先に実行するよう案内して終了する。
     （画面変更を伴わない内部機能なら、E2Eは既存specの全件成功をもって確認とする）
6. **作業ブランチ（`dev/自分の名前-作業名`）にいることを確認する**（Git運用手順「1. ブランチ構成」）。
   - `master` にいたら即座に停止して報告する。
   - `dev/自分の名前`（個人の統合ブランチ）にいたら、そこは本体ツリーで直接編集しない決まりなので停止し、
     `/worktree-start <作業名>`（フル版。`.env` を複製する）で作業ツリーを作るよう案内する。作らずに進めると `worktree-guard` フックが編集を拒否する。
   - 実装作業も作業ツリーで行う。実装ツリーが自分1本だけなら既定のポート（`SERVER_PORT=5000`）のまま使える。
7. `git status --short` で開始時点の既存変更を記録する。既存の変更はユーザーの作業として触らない。
8. `git fetch origin` → `git merge dev/自分の名前` で個人の統合ブランチの最新を取り込む（Git運用手順③の直前取り込み。rebase禁止）。
   コンフリクトは作業ブランチ側で解消し、判断に迷うものは解消せずユーザーに報告して指示を待つ。
9. **E2Eの実行前提を確認する**: `.env`（ポートを分けた作業ツリーだけ）、Node.js 22以上と `node_modules`・`e2e/node_modules`
   （無ければ `npm ci`・`npm --prefix e2e ci`）、Playwrightブラウザ（テスト方針4-5）。
   E2EはPlaywrightが `npm run dev` でアプリを自分で起動する。同じ `SERVER_PORT` で別のアプリ（他の作業ツリーや手動起動）が動いていると `strictPort` で起動に失敗するので、そのときはポートを分ける（`/worktree-start` 手順4）。
   DBは無いため、E2Eでデータが消える心配はない。

## 2. 実装の担当モデル

- **実装本体**（複数ファイル・設計判断あり）: **Codex Terra** への委譲を第一候補とする。Claudeメインセッションで実装してもよい。
- **定型実装**（テストが仕様を完全に規定した小粒なタスク・同型修正の量産）: **Codex Luna** に委譲してよい。
- Codexへ委譲する場合は、本スキルの「完了条件とループ」「安全装置」を依頼内容に必ず含める。
  委譲後もテスト実行による検証（3〜4章）・連動更新・PR作成（5章）は本スキル（Claude側）が責任を持つ。

## 3. 完了条件の宣言とループ

開始時に完了条件を明示する（/goal が使える環境では /goal にも設定する）。対象によって分岐する:

- **画面を伴う機能**: `npm run check` 全件成功 かつ 対象画面のE2E（`npm run e2e -- scrXX`）全件成功
  かつ E2E全件（`npm run e2e`）成功
- **画面を伴わない内部機能**: `npm run check` 全件成功 かつ 既存E2E全件（`npm run e2e`）成功（デグレ確認）

1. **単体ループ**: 実装 → **単体テストを実行**（反復中は `npm test`、区切りでは `npm run check`＝
   型検査＋ESLint＋単体テスト全件）→ 失敗の原因を直す、を全件成功まで繰り返す。
   - /gen-unit-test が作った失敗する単体テスト（`src/core`・`src/music`・`src/share` など）をすべて成功させるのがこの段の完了条件。
   - 骨格の `throw new Error('未実装: ...')` を処理設計どおりの実装に置き換えていく。
   - 型エラー・ESLintの違反もこのループで解消する。`any`・型アサーション・無効化コメントで黙らせない（実装方針9章）。
2. **E2Eループ**: 単体が通ったら `npm run e2e -- scrXX` → 失敗の修正、を対象specの全件成功まで繰り返す
   （画面を伴わない機能ではこの段は省略する）。
   - E2Eの失敗でアプリケーションのコード（`src/` の `*.test.ts` 以外と `index.html`）の修正に至ったものは、修正コミット確定後に
     [バグ表](../../ドキュメント/04_テスト/02_バグ表.md) へ起票する（検出工程「結合テスト（AI）」、テスト方針9-2）。
     テストコード側だけの修正は起票しない。
3. **全件で締める**: `npm run e2e` で他画面との相互作用を確認する（gen-e2eと同じ締め方）。
4. 意味のある区切り（単体全件成功、E2E成功など）でこまめにコミットする。**今回変更したパスだけを明示して
   ステージし、`git diff --cached` で無関係な変更（開始時に記録した既存変更）が混ざっていないことを
   確認してからコミットする**（Git運用手順）。

## 4. 安全装置（テスト方針9-2の厳守事項）

- **テストの期待値を書き換えて通すことは禁止。** 仕様の方が違うと判断したら、先に設計書を直し、
  次にテスト（観点表→spec、単体テスト）、最後に実装の順で直す。
- テストコード自体の不良（型ミス・ロケーター誤りなど）を直した場合は、**アプリの修正とコミットを分ける**。
- **同じ失敗を3回繰り返したら機械的な修正をやめる。** 設計とテストのどちらに問題があるかを判断し、
  状況と見立てをユーザーに報告して指示を待つ。
- `e2e/fixtures/`・`e2e/helpers/`・`playwright.config.ts` 等のテスト基盤を書き換えない（gen-e2eの禁止事項と同じ）。
- エラーを握りつぶして通さない。根本原因を直す（入力とエラーの役割分担は実装方針5章に従う）。
- テストを通すために、`src/core`・`src/music` で時計を読む・`src/music` で `Math.random()` を使う・仮の数値を処理の途中に直書きする・層の依存方向を崩す、をしない（実装方針2・6・9章）。

## 5. 完了時にやること: 連動更新とPR作成

1. **連動更新の確認**（ドキュメント/AGENTS.md の連動表）: 処理設計・画面設計・モックアップ・
   README のうち、今回の変更に対応するものを同じ変更で更新する。
   観点表の「自動化」欄など、テスト側の記録も最新にする。
2. `dev/自分の名前` を作業ブランチへ取り込み（マージ。rebase禁止）、コンフリクトがあれば作業ブランチ側で解消し、
   取り込み後にもう一度 `npm run check` を実行する（Git運用手順④）。
3. `dev/自分の名前` へマージする（**PRは出さない**）。作業ブランチを push してから `ExitWorktree` で本体ツリーへ戻り、
   `git merge --no-ff` でマージして push し、作業ツリー・作業ブランチを片付ける（[worktree-end](worktree-end.md) の手順3〜5。Git運用手順④）。
4. `dev/自分の名前` を push して PR を作成する（本体ツリーの `dev/自分の名前` → `master`）。
   既にPRが開いていれば新しく作らず、pushで更新して本文の「変更内容」に今回分を追記する。PR説明には次を必ず書く:
   - [ ] 対応する設計書を更新した
   - [ ] `npm run check` が通ることを確認した
   - 実装した機能・画面、テスト結果（単体○件・E2E○件成功）
   - デザインシステムを変更した場合は、変更した節・影響成果物
5. 報告: PRのURL、テスト結果、連動更新したファイルを1〜3行でまとめる。
   PR作成時に自動レビューが走るので、**指摘には必ず返信する**運用であることを添える。対応した事実はAIが書いて投稿してよいが、対応しない判断は人が決める（Git運用手順⑥）。
   作業ツリー・作業ブランチが残っていれば `/worktree-end <作業名>` で片付けることを添える。
