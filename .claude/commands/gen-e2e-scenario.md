対象: $ARGUMENTS

観点表は観点・確認内容・ケースIDの正本（手順・期待値の正本はテストコード＝テスト方針1章）。
ケースIDとspecの `test()` は1対1になる（テスト方針8-1）。
観点の抜けはコード化後に見つかると手戻りが大きいため、以下の順で正本を**全文読んでから**作ること。
要約や記憶で書き始めない。

## 1. 着手前に読む

1. [ドキュメント/AGENTS.md](../../ドキュメント/AGENTS.md)（`ドキュメント/` 配下に新規文書を作るときのルールの正本）
2. [ドキュメント/04_テスト/01_テスト方針.md](../../ドキュメント/04_テスト/01_テスト方針.md) の 4章（結合テストの運用ルール）・5章（結合テストの観点）・7章（テストデータ） ← 正本
3. 対象画面の画面設計書 `ドキュメント/02_基本設計/画面設計/SCRXX_○○画面.md`
   - **画面設計書が無い場合は観点表を作らない。** 先に画面設計書が必要だと報告して終了する（画面設計の完成がこのスキルの前提）。
   - 同名モックアップは**あれば**読む。無くても観点表は作ってよい（モックアップは後工程で作られる。
     その場合の扱いは手順8）。
4. 対象画面に関わる処理設計 `ドキュメント/03_詳細設計/処理設計/*.md`（ゲームのルール・判定・失敗時の扱いの根拠）
5. 既存の観点表 `ドキュメント/04_テスト/テスト仕様書/`（あれば書きぶり・粒度の見本にする）
6. 対象画面と切り替えでつながる画面の観点表（4-2「遷移確認は遷移元に書く」の責務重複を避けるため）

## 2. 作成手順

1. `ドキュメント/テンプレート/テスト仕様書テンプレート.md` をコピーし、
   `ドキュメント/04_テスト/テスト仕様書/SCRXX_○○画面テスト観点表.md` として保存する。
2. テスト方針5章の観点一覧を上から順に当ててケースを洗い出す。
   該当しない観点は省略してよいが、省略した観点と理由を完了報告に含める。
3. 入力・境界値（分身が現れる周の切れ目、分身の最大人数、受け付けるキーなど）の期待値は**機能要件・画面設計書・処理設計から導く**。実装コードから逆算しない。
   設計書に書かれていない仕様が必要になったら、観点表を止めて先に設計書の修正を提案する。
   数値は仮で遊んで決めるため（要件定義7章）、確認内容には数値そのものより「どの設定値を境にどう変わるか」を書く。
4. 画面の切り替えのケースは、切り替え先の画面が正しい状態（表示項目・引き継いだ選択）で
   表示されるところまで確認内容に書く。この観点表に載せるのは**この画面を起点とする切り替えだけ**（4-2）。
5. 各ケースの前提を書く。DBも番号付きのテストデータセットも無いため、前提は次の3つで表す。
   - 使う楽器と残す分身の人数（または共有URLを開くケースなら開く共有URL）
   - キーボード（左手＝WASD・右手＝矢印キー・楽器を選ぶ数字キー）で出す操作とその順番
   - 時間を固定するかどうか
   E2Eで時間を固定する方法、音の扱い、共有URLを開くケースで開くURLの作り方はまだ決まっていない（テスト方針4-3・4-8。詳細設計で決める）。
   決まるまでは前提欄に「時間固定が必要」のように要求だけを書き、方法は書かない。
6. 全ケースに `SCRXX-NN` 形式のケースIDを明記する。
   自動化欄は**全ケース `未`** とする（`済` への更新はspecをコード化した /gen-e2e が行う）。
7. 表示幅の観点は付けない。動作環境はPCのChromeだけで（[非機能要件](../../ドキュメント/01_要件定義/02_非機能要件.md) N1）、E2Eも Desktop Chrome の1プロジェクトだけで回す。
8. **モックアップが未作成の場合**: 画面設計書だけでケースを作る。見た目に依存する観点
   （初期表示のレイアウト、長いクレジット表記の表示崩れ）は確認内容を仮置きとし、
   観点表の冒頭に「モックアップ作成後に見た目系の観点を追補する」と明記する。
   モックアップ完成後にこのスキルを同じ画面IDで再実行すると、既存の観点表を壊さず
   見た目系の観点だけを追補・確定する（ケースIDは既存の続き番号を使う）。

## 3. 禁止事項

- 機能単位の観点表を作らない。**画面単位**で、`02_基本設計/01_画面一覧・遷移図.md` の画面一覧と1対1にする（4-1）。
- 他画面の観点表と切り替え確認の責務を重複させない（「他画面から切り替わってきた場合」のケースを書かない）。
- 音の聞こえ方（曲として聞ける・濁らない・同じ曲に聞こえる）をE2Eの観点として書かない（E2Eは音を聞けない。テスト方針2-1。耳で確かめるものは観点表の備考に分けて書く）。
- canvas の中身の確かめ方が未決のうちは（テスト方針4-1）、確かめ方を独自に決めて書かない。要求だけを書く。
- テスト方針2-1の明示的な除外対象のケースを書かない。

## 4. 完了時にやること・報告

1. セルフチェック: 全ケースにケースID・前提（楽器・分身の人数・操作・固定の要否）があるか。5章の観点の網羅を再確認する。
2. **Codexにレビューさせる**: codexプラグイン（/codex:rescue）で観点表のレビューを依頼する（読み取りのみ・修正はさせない）。
   レビュー観点: テスト方針5章の観点の抜け、確認内容と画面設計書・処理設計の整合、
   切り替え責務（4-2）の重複、前提の妥当性。
   指摘があれば観点表へ反映し、対応に迷う指摘は人レビューへ持ち越す（勝手に捨てない）。
3. 観点表ファイル**だけ**を対象に指定してコミットする（メッセージ例: `SCR02 テスト観点表を作成`）。
   ブランチが作業ブランチ（`dev/自分の名前-作業名`）であることをコミット前に確認する。`master` または `dev/自分の名前`（統合ブランチ）にいたら停止し、`/worktree-start <作業名>` で作業ツリーを作るよう案内する（Git運用手順「1. ブランチ構成」）。
4. **人のレビューを依頼して終了する。** ケース数・前提に使った組み合わせと判定・
   省略した観点と理由・モックアップ未作成により仮置きした観点の有無・**Codexの主な指摘と対応**を1〜5行で報告し、
   「レビュー承認後に /gen-e2e SCRXX でコード化に進んでください」と案内する。
   承認前に自分で /gen-e2e へ進まない。仮置きの観点は、モックアップ完成後に本スキルを
   再実行して追補してからコード化するよう案内する。
