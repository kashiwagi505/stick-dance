対象: $ARGUMENTS

`e2e/` には `test`・`expect` の供給元（fixture）、証跡保存、アプリの自動起動の仕組みがある。素のPlaywrightの書き方では崩れるため、
以下の順で必ず正本と既存specを**全文読んでから**specを書くこと。要約や記憶で書き始めない。

## 1. 着手前に読む

1. [ドキュメント/04_テスト/01_テスト方針.md](../../ドキュメント/04_テスト/01_テスト方針.md) の 4章（結合テストの運用ルール）と 5章（結合テストの観点） ← 正本
2. 対象画面のテスト観点表 `ドキュメント/04_テスト/テスト仕様書/SCRXX_○○画面テスト観点表.md`
   - **無い場合はspecを書かない。** `/gen-e2e-scenario <画面ID>` で観点表を先に作るよう案内して終了する。
     観点表が人のレビュー承認済みであることも確認する（未承認なら承認後に再実行してもらう）。
   - 観点表は観点・確認内容・ケースIDの正本。手順・期待値の正本はテストコード（テスト方針1章）。
     ケースIDと `test()` は1対1（テスト方針8-1）。
3. 既存spec `e2e/tests/*.spec.ts`（あれば、対象に近いものを見本にする。無ければ下の骨格に従う）
4. 使う仕組みの実装
   - `e2e/fixtures/test.ts` … `test` / `expect` の供給元。全ケース共通の前提が必要になったらここで強制する（テスト方針4-3）
   - `e2e/helpers/evidence.ts` … `saveEvidence(page, 画面ID, ケースID, 連番)`
   - `e2e/helpers/paths.ts` … `e2eRoot` / `repoRoot`
   - `e2e/playwright.config.ts` … Desktop Chrome の1プロジェクトだけ、`workers: 1`（直列）、`npm run dev` でアプリを自動起動、接続先は `.env` の `SERVER_PORT`
5. 対象画面に関わる処理設計 `ドキュメント/03_詳細設計/処理設計/*.md` のうち、E2Eでの判定の差し替え・時間の固定を定めた箇所

## 2. specの骨格（この形を崩さない）

`e2e/tests/scrXX-<英小文字の画面名>.spec.ts` に置く。

```ts
import { test, expect } from '../fixtures/test';   // ← @playwright/test から import しない
import { saveEvidence } from '../helpers/evidence';

const SCREEN = 'SCR02';

test.describe('SCR02 踊る画面', () => {
  test('SCR02-01 観点表の確認内容をそのまま書く', async ({ page }) => {
    await page.goto('/');
    // トップページから始め、踊る画面へ進む（前のケースの状態を使わない。テスト方針4-3）
    // 手を引く操作（WASD・矢印キー）と楽器の選択（数字キー）はキーボードから出す（例: await page.keyboard.down('ArrowUp')）
    await expect(page.getByRole('heading', { level: 1 })).toBeVisible();
    await saveEvidence(page, SCREEN, 'SCR02-01', 1);   // ← 全ケースで必須
  });
});
```

- `test()` のタイトルは `ケースID + 半角スペース + 観点表の確認内容` にする。
- 各ケースは新しいページで `page.goto('/')` から始め、観点表の前提（楽器・操作の順番・残す分身の人数・固定の要否）をそのケースの中で作る。共有URLを開くケースは `page.goto('/#…')` から始める。前のケースの結果を前提にしない。DBもテストデータセットも無い。
- 操作は**キーボードから出す**（`page.keyboard`）。音の聞こえ方は判定しない（テスト方針2-1）。
- 棒人間と舞台は Canvas 2D で描くため、canvas の中身の確かめ方は未決（テスト方針4-1）。時間を固定する方法と、E2Eでの音の扱いも未決（同4-3・4-8。詳細設計で決める）。決まっていない状態でspecが必要になったら、specの中で独自の差し替えを作らず「何が足りないか」を報告して指示を仰ぐ。
- 時間で進む表示（ループの周の切り替わり・鑑賞の再生）を待つときは、固定の待ち時間（`page.waitForTimeout`）ではなく、`expect(...).toBeVisible()` などの自動待機で状態の変化を待つ。
- 証跡は全ケースで最低1枚。1ケース内で複数撮るときは連番を `1, 2, 3…` と増やす。
- ロケーターは `getByRole` / `getByLabel` を優先する。`#id` は `<label for="id">` があるフォーム部品に限り可（テスト方針4-1）。
- 対象はPCのChromeだけ。スマートフォン・タブレット向けのspec（`*.mobile.spec.ts` など）は作らない。
- 機能系とレイアウト系を1つのspecに混ぜない（テスト方針4-7）。
- 接続先は相対パスで書く（`page.goto('/')`）。`browser.newContext()` で自分で開いた文脈も `use.baseURL` を継承する。

## 3. 禁止事項

- `e2e/fixtures/`・`e2e/helpers/`・`global-setup.ts`・`playwright.config.ts` を**書き換えない**。
  足りない仕組みがあれば、specを無理に通さず「何が足りないか」を報告して指示を仰ぐ。
- `@playwright/test` から `test` を import しない（`Page` などの型だけは可）。fixtureを迂回すると、全ケース共通の前提を強制できなくなる。
- 前のケースの結果を前提にしない（テスト方針4-3）。
- `data-testid` を使わない。
- スクリーンショットを `page.screenshot()` で直接保存しない。パスを自作せず `saveEvidence` を通す。
- アプリ側に「テスト中かどうか」の分岐を求めない（テスト方針4-8）。
- **接続先のホスト・ポート（`http://localhost:5000`）をspecに直書きしない。** ポートは `.env` の `SERVER_PORT` で変わるため、直書きしたケースは既定以外で必ず落ちるか、中身を見ずに通ってしまう。
- **テストを通すために期待値を弱めない**（テスト方針9-2）。仕様の方が違うと判断したら、設計書→観点表→specの順に直す。

## 4. 実行して確認する

実行前の前提確認（テスト方針4-5）: `.env`（ポートを分けた作業ツリーだけ。秘密値は無い）、`e2e/node_modules`（無ければ `npm --prefix e2e ci`）、Playwrightブラウザ。
未セットアップの項目があれば**実行せず**、READMEとテスト方針4-5の手順を案内する。
アプリはPlaywrightが `npm run dev` で自分で起動するので、事前に起動しておく必要はない（同じポートで別に起動していると衝突する）。

対象specだけ回す（引数はファイルパスに対する部分一致）:

```powershell
npm run e2e -- scr02
```

結果の判定は、対象機能が実装済みかどうかで分ける:

- **テストファースト（実装が無い・未完成）の場合**: specが**未実装の仕様を理由に失敗する**こと、
  構文エラー・fixture設定ミス・ロケーター誤りによる失敗ではないことを確認して終了する（テスト方針9-1）。
  **アプリケーションのコード（`src/`・`index.html`）は変更しない。** E2Eを成功させる責務は /run-impl-loop にある。
- **既存機能へのテスト追加の場合**: 対象specの全件成功まで直し、最後に全件で締める（他specとの相互作用の確認）:

```powershell
npm run e2e
```

- 失敗したら、期待値ではなく実装かspecの側を疑う。同じ失敗を3回繰り返したら機械的な修正をやめ、
  設計とテストのどちらに問題があるかを判断してユーザーに相談する（テスト方針9-2）。

## 5. 完了時にやること・報告

- 観点表の「自動化」欄を `済` にする。ケースIDと `test()` の対応がずれていないか確認する。
- 開始時に `git status --short` で既存の変更を確認しておき、**今回作成・変更したファイルだけ**
  （spec・観点表）をパス指定でステージし、`git diff --cached` で無関係な変更が
  混ざっていないことを確認してからコミットする（ブランチが作業ブランチ `dev/自分の名前-作業名` であることも確認。`master` または `dev/自分の名前`（統合ブランチ）にいたら停止し、`/worktree-start <作業名>` で作業ツリーを作るよう案内する。Git運用手順「1. ブランチ構成」）。
- 追加・変更したケースIDの一覧、実行結果（全件成功か、未実装による失敗確認か）、
  `e2e/evidence/<画面ID>/` に証跡が生成されたことを1〜2行で報告する。
