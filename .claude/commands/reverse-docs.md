対象: $ARGUMENTS

このスキルは、実装済みのコード・設定に対して設計書が古い、または存在しないとき、
**設計書側を実装へ追従させる**（リバース反映）。コードは変更しない。
乖離の検出は `doc-sync-checker` に委譲し、このスキルは仕分け・承認・反映だけを担う
（レビュー専用と自動修正を混ぜない＝エージェント・スキル設計基準書）。

## 対象と対象外

- **対象**: 実装が確定しているのに設計書が未更新・未作成の状態の解消。処理設計・画面設計・機能要件・インフラ要件・実装方針7章（記録の形式・共有URL・素材）・README などへの書き戻し。
- **対象外**:
  - これから作る機能の設計（→ 実装方針「10. 機能追加の流れ」の順方向で行う）
  - 実装バグの修正（→ バグ表へ起票し `harness-resolution` の手順で対応する。このスキルはコードを直さない）
  - 未確定の仕様の確定（→ 要件定義の未決事項・判断ログへ。発注元が本人のためQA表は置かない）
  - 要件・実装方針で未決とされている事項（共有URLの版違いの扱い・再読み込みの扱いなど）を、実装されているからといって決定済みとして書くこと（→ 「要確認」として担当者に確認する）

## 1. 範囲確定と着手前に読む

1. `$ARGUMENTS` から対象範囲を特定する（機能名／画面ID／ファイルパス）。省略時は `git diff origin/master...HEAD --name-status` の差分を対象とする。
2. `git status --short` で開始時点の既存変更を記録する（完了時のコミット対象の切り分けに使う。既存の変更には触れない）。
3. [ドキュメント/AGENTS.md](../../ドキュメント/AGENTS.md) を全文読む（「連動して更新するもの」の表が書き込み先の正本。このスキルへ転記しない）。

## 2. 乖離の検出（doc-sync-checker へ委譲）

1. 対象範囲を指定して `doc-sync-checker` サブエージェントに乖離検出を依頼する。
2. 対象がコミット済みで差分に現れない乖離（過去に実装だけ進んだもの）は、対象コードと該当設計書を読み比べて乖離を列挙する。どの設計書が該当するかは ドキュメント/AGENTS.md の連動表と [ドキュメント構成.md](../../ドキュメント/ドキュメント構成.md) で決める。
3. 乖離ゼロならその旨を報告して終了する。

## 3. 正誤判定と承認（承認前に書き換えない）

1. 乖離ごとに、上流の正本（機能要件・画面設計・処理設計・判断ログ）まで遡って次の3つに仕分ける。
   - **実装が正**: 設計書側を更新する候補。判断根拠（どの正本・どのコードから言えるか）を添える。
   - **実装バグ疑い**: 設計書・要件と矛盾する実装。**設計書には反映しない。** バグ表（`ドキュメント/04_テスト/02_バグ表.md`）への起票を案内する。
   - **要確認**: 上流に根拠がなく、コードだけでは正誤を断定できないもの。実装が正と推定しない。
2. 仕分け結果を一覧（乖離の内容／判定／根拠／反映先ファイル／変更概要）で提示し、**ユーザーの承認を待って停止する**。
3. 承認された「実装が正」の項目だけを手順4へ進める。「要確認」はユーザーの回答（または Issue への起票）で確定してから扱う。

## 4. 反映

1. 反映先の種類ごとに、該当ガイドを**全文読んでから**書く。要約や記憶で書き始めない。
   - 処理設計: [詳細設計書ガイド・チェックリスト](../../ドキュメント/基準書/詳細設計書ガイド・チェックリスト.md)
   - 画面設計・モックアップ: [画面設計書ガイド・チェックリスト](../../ドキュメント/基準書/画面設計書ガイド・チェックリスト.md) と [デザインシステム](../../ドキュメント/02_基本設計/画面設計/デザインシステム/readme.md)
2. 設計書が存在しない場合は `ドキュメント/テンプレート/` の該当テンプレートをコピーして作る。ゼロから書式を作らない。
3. 書き込み先の注意:
   - 機能追加シート（`ドキュメント/テンプレート/機能追加シート.md` から作ったもの）は経緯記録であり、**反映先にしない**。仕様は機能要件・各設計書へ書く。
   - 全画面共通の見た目はデザインシステム側へ書き、個別の画面設計へ転記しない。
   - 画面設計を更新したら同名モックアップも同じ変更で追従させる。
4. 設計書には**最終決定内容だけ**を書く。経緯・日付のナレーションは書かない（経緯はGit履歴と機能追加シート）。

## 5. 自己検証

1. 各ガイド末尾のレビューチェックリストで更新後の設計書を自己レビューし、通るまで直す。
2. コードと更新後の設計書で、共有URLの版番号・操作と音の対応・名称・仮の数値の名前・文言などの具体値が一致することを突き合わせて確認する。
3. 直せない・判断できない指摘が残ったら「要確認」として報告に含める。

## 6. コミット・報告と終了条件

1. 手順1で記録した既存の変更には触れず、**今回更新・作成したファイルだけ**をパス指定でステージし、`git diff --cached` で無関係な変更が混ざっていないことを確認してからコミットする（メッセージ例: `SCR02踊る画面: 実装内容を画面設計・処理設計へリバース反映`）。ブランチが作業ブランチ（`dev/自分の名前-作業名`）であることをコミット前に確認する。`master` または `dev/自分の名前`（統合ブランチ）にいたら停止し、`/worktree-start <作業名>` で作業ツリーを作るよう案内する（Git運用手順「1. ブランチ構成」）。
2. 報告: 反映した設計書の一覧、バグ疑いとして除外した項目（起票先の案内付き）、残った要確認事項を1〜5行でまとめる。PRは `/create-pr` で作るよう案内して終了する。

## 禁止事項

- 手順3の承認を得る前に設計書を書き換える。
- `src/`・`index.html`・`e2e/` のコードを変更する（バグはバグ表→修正の工程へ）。
- コード・HTML・全項目一覧の転記（各ガイドの「記載しない内容」。設計書に書くのは機能固有の判断・責務・重要な順序だけ）。
- 実装バグ疑い・要確認の項目を「実装が正」として反映する。
- 空欄・`TODO`・`TBD`・経緯ナレーションを設計書に残す。
