# impl-policy-reviewer — 実装方針レビュー手順書

変更されたコードを [アプリケーション実装方針](../ドキュメント/基準書/アプリケーション実装方針.md) に照らしてレビューする。

## 対象

- 原則は `git status` と `git diff HEAD` で確認できる未コミット変更（ステージ済みを含む）。
- ブランチが指定された場合は、指定ブランチとの三点差分（例: `git diff master...HEAD`）。
- `src/**/*.ts`（単体テスト `src/**/*.test.ts` を含む）、`index.html`、`package.json`、設定ファイル（`tsconfig.json`・`vite.config.ts`・`eslint.config.js`）、`.env.example` を対象とする。
- 対象変更がなければ「レビュー対象の変更なし」と報告して終了する。

## 手順

1. `git status --short` と適切な `git diff` で変更範囲を把握する。
2. `ドキュメント/基準書/アプリケーション実装方針.md` を全文読む。
3. 変更ファイルの全文と、影響を受ける呼び出し元・呼び出し先（import している側・されている側）を確認する。
4. 下記チェック項目を検査し、指定形式で報告する。

## チェック項目

### 層と依存（1・2章）

- [ ] 各層が自分の仕事だけをしているか。`src/view`・`src/audio`・`src/share` に踊りや音の決め方の規則（体の引き方・分身になる条件・どの拍にどの高さを鳴らすか）を書いていないか
- [ ] `src/core`・`src/music`・`src/share` が Tone.js・Canvas・DOM・時計（`Date.now()`・`performance.now()`）・`Math.random()` に触れていないか（ESLint が止めるが、無効化コメントで外していないかも見る）
- [ ] import の向きが実装方針2章と `eslint.config.js` の層の境界に収まっているか（core→なし、music→core、share→core・music、audio→core・music、view→すべて）。Tone.js を `src/audio` 以外が import していないか。`view` 以外の層が `view` を import していないか
- [ ] 踊りと音を「記録（キー入力と楽器の選択）→ 姿勢の列 → 鳴らす音の並び」の1つの流れで作り、踊っている最中・分身・鑑賞・共有URLからの再生が同じ関数の結果を使っているか。呼び出し元ごとに別の計算をしていないか

### 画面の切り替え（3章）

- [ ] 画面の切り替えをページ遷移ではなく、1ページの中の HTML の表示切り替えで行っているか（Phaser などの画面ライブラリを持ち込んでいないか。技術選定 1章）
- [ ] URL の `#` 以降に記録があるとき、遊ばずに鑑賞を開くか（F8）
- [ ] 踊っている途中の状態をブラウザ（`localStorage` 等）に保存していないか（再読み込みの扱いは未決。決定前に既成事実として実装していれば「要確認」）

### 文言・入力とエラー（4・5章）

- [ ] 利用者向けの文言（ボタン・案内・エラー表示）を `src/view/` の文言定義1か所にまとめ、描画処理や HTML の組み立てに直接書いていないか
- [ ] 受け付けるキー（左手＝WASD・右手＝矢印キー・楽器を選ぶ数字キー）以外を `src/core` に渡していないか。キーをどう引くかの扱いを `src/core` の規則に置いているか
- [ ] 共有URLの不備（壊れている・版が違う）と楽器の音の読み込みの失敗を、`src/share`・`src/audio` が戻り値で返しているか。例外を握りつぶして黙って続けていないか
- [ ] 利用者の操作より前に音を始めていないか（ブラウザの自動再生の制限）。共有URLを開いたときも同じか
- [ ] 内部の詳細（スタックトレース等）を画面へ出していないか

### 依存の渡し方・時間・同じ入力から同じ結果（6章）

- [ ] 差し替えたいもの（時刻・キー入力）を、引数またはコンストラクタで渡しているか。モジュール内で直接生成・グローバル変数で共有していないか
- [ ] 時刻の基準が音の時計（`AudioContext.currentTime`）になっているか。**Tone.js の Transport を使っていないか**（技術選定 3.2）。拍を音の時計から先読みして予約しているか
- [ ] 物理を決まった刻み（1/60秒）で進め、何刻み進めるかを音の時計の進みから決めているか。`requestAnimationFrame` の回数や描画の間隔で刻みを変えていないか（技術選定 3.1・3.2）
- [ ] `src/core`・`src/music`・`src/share` の中で時計を読まず、呼び出し側が読んだ時刻を数値で渡しているか
- [ ] `src/core`・`src/music`・`src/share` で、ブラウザによって結果が変わりうる計算（`Math.hypot`・`Math.sin` など）を使っていないか。平方根を `Math.sqrt(dx * dx + dy * dy)` で書いているか（技術選定 3.1）
- [ ] 乱数を使っていないか。使うなら、種を記録に入れた自作の乱数になっているか（技術選定 3.1）
- [ ] 同じ記録から必ず同じ踊り・同じ音になるか（N3・AC3）
- [ ] 画面が隠れたら（`visibilitychange`）音と物理を止め、戻ったら続きから進めるか（N5・技術選定 3.3）

### データと記録の形式（7章）

- [ ] 記録に入れるのがキー入力（何刻み目に、どのキーが押された・離された）と楽器の選択だけか。姿勢を記録していないか（技術選定 3.1）
- [ ] 共有URLの先頭に形式の版番号を入れているか。記録の詰め方・物理・音の決め方を、同じ記録から違う踊りや音になる形で変えたのに版番号を上げていない変更がないか
- [ ] 共有URLの圧縮に `CompressionStream` を使い、`#` 以降に入れているか。追加のライブラリを入れていないか
- [ ] 実行時に読む楽器の音のファイル・画像を `.gitignore` に入れていないか（インフラ要件 I4）
- [ ] 版違いの扱い・URLの長さの上限・記録の形式（詳細設計で未決）を、決定前に既成事実として実装していないか（判断できなければ「要確認」）

### サーバーと秘密値を持たない・公開範囲（8章）

- [ ] サーバー側の処理・外部API・`fetch` での外部通信・鍵を持ち込んでいないか。共有の記録を `#` 以降以外（クエリ文字列・外部送信）に入れていないか
- [ ] 楽器の音のファイルを同じサイト（GitHub Pages）から読んでいるか。外のサイトから直接読んでいないか（技術選定 3.4）
- [ ] `.env` を秘密値の置き場として使っていないか（`SERVER_PORT` だけ）。`import.meta.env` から秘密値を読む前提のコードがないか
- [ ] Vite の `base` が GitHub Pages のパス（`/stick-dance/`）に合っているか
- [ ] 出所と権利確認の記録が無い素材（絵・音）を配信物に加えていないか。CC BY の素材を足したのにゲーム内のクレジットに載せていない変更がないか（N7・F10・AC5）

### 実装の共通ルール（9章）

- [ ] 互換レイヤー・フォールバック・「念のため」残した使われない関数・設定・ファイルがないか（共有URLの古い版の扱いは詳細設計の決定に従う）
- [ ] 現在の要件に対して過剰な抽象化・設定項目・間接化をしていないか（インターフェースは実装が複数必要になってから）
- [ ] 仮の数値（引く強さ・揺れ戻りの強さ・分身になるのに要る音の数・頭の高さの段の境目・音量など）を設定1か所に名前付きでまとめているか。処理の途中に数値を直書きしていないか
- [ ] 操作から音が鳴るまでの遅れ（N2）を試作で測れる形になっているか
- [ ] `tsconfig.json` の `strict` を緩めていないか。`any` と型アサーション（`as`）で型検査を黙らせていないか。ESLintの無効化コメントで違反を隠していないか
- [ ] 外から来るデータ（共有URLから読み戻した記録）を、受け取った場所で形を確かめてから使っているか
- [ ] 実装（`src/`・`index.html`）で外部CDNを参照していないか。ライブラリを npm の依存として入れているか
- [ ] 公開する関数・型に、役割が分かる日本語のコメントがあるか
- [ ] 変更したコードに対応する単体テスト（Vitest、`src/**/*.test.ts`）があるか。特に `src/core`・`src/music`・`src/share` の仕様をテストで固定しているか

## 出力形式

```text
### 指摘N: <一言サマリ>
- ファイル: <パス>:<行番号>
- 違反規約: アプリケーション実装方針 <章番号と要旨>
- 重要度: 要修正 | 推奨 | 要確認
- 内容: <問題と影響>
- 修正案: <具体的な修正方法>
```

- 指摘ゼロなら「**規約違反なし**」と明言する。
- 差分だけで断定できない事項は「要確認」とする。
- レビューのみを行い、依頼されていないコード修正はしない。
