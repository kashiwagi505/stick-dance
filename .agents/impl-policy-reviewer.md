# impl-policy-reviewer — 実装方針レビュー手順書

変更されたコードを [アプリケーション実装方針](../ドキュメント/基準書/アプリケーション実装方針.md) に照らしてレビューする。

## 対象

- 原則は `git status` と `git diff HEAD` で確認できる未コミット変更（ステージ済みを含む）。
- ブランチが指定された場合は、指定ブランチとの三点差分（例: `git diff master...HEAD`）。
- `src/**/*.ts`（単体テスト `src/**/*.test.ts` を含む）、`index.html`、`package.json`、設定ファイル（`tsconfig.json`・`vite.config.ts`・`eslint.config.js`）、`.env.example` を対象とする。
- 対象変更がなければ「レビュー対象の変更なし」と報告して終了する。

## 手順

1. `git status --short` と適切な `git diff` で変更範囲を把握する。
2. `ドキュメント/基準書/アプリケーション実装方針.md` を全文読む。
3. 変更ファイルの全文と、影響を受ける呼び出し元・呼び出し先（import している側・されている側）を確認する。
4. 下記チェック項目を検査し、指定形式で報告する。

## チェック項目

### 層と依存（1・2章）

- [ ] 各層が自分の仕事だけをしているか。`src/view`・`src/audio`・`src/share` にゲームや曲作りの規則（配達のルール・どの音を鳴らすか）を書いていないか。`src/data` に処理を書いていないか
- [ ] `src/core`・`src/music` が Phaser・Tone.js・DOM・時計（`Date.now()`・`performance.now()`）に触れていないか
- [ ] import の向きが実装方針2章の「読んでよい層」の表に収まっているか（core→data、music→core・data、share→core・music、audio→music、view→すべて、data→なし）。`view` 以外の層が `view` を import していないか
- [ ] 曲を「記録（種を含む）→ 音符の並び」の1つの関数で作り、プレイ中・種明かし・共有再生・書き出しが同じ関数の結果を使っているか。呼び出し元ごとに別の曲作りをしていないか

### 画面の切り替え（3章）

- [ ] 画面の切り替えをページ遷移ではなく Phaser のシーンの切り替えで行っているか
- [ ] URL の `#` 以降に記録があるとき、遊ばずに共有再生を開くか（F8）
- [ ] ステージの途中の状態をブラウザ（`localStorage` 等）に保存していないか（再読み込みの扱いは未決。決定前に既成事実として実装していれば「要確認」）

### 文言・入力とエラー（4・5章）

- [ ] 利用者向けの文言（ボタン・案内・エラー表示）を `src/view/` の文言定義1か所にまとめ、シーンの描画処理に直接書いていないか
- [ ] ステージ名など `src/data` が持つ名前を文言定義に重複して書いていないか
- [ ] 受け付けるキー以外を `src/core` に渡していないか。操作の扱いを `src/core` の規則に置いているか
- [ ] 共有URLの不備（壊れている・版が違う）と書き出しの失敗を、`src/share`・`src/audio` が戻り値で返しているか。例外を握りつぶして黙って続けていないか
- [ ] 利用者の操作より前に音を始めていないか（ブラウザの自動再生の制限）
- [ ] 内部の詳細（スタックトレース等）を画面へ出していないか

### 依存の渡し方・時間・乱数（6章）

- [ ] 差し替えたいもの（時刻・乱数の種・ステージのデータ）を、引数またはコンストラクタで渡しているか。モジュール内で直接生成・グローバル変数で共有していないか
- [ ] 時刻の基準が音（Tone.js の Transport）になっているか。画面のフレーム数から時刻を数えていないか
- [ ] `src/core`・`src/music` の中で時計を読まず、`src/view` が読んだ音の時刻を数値で渡しているか
- [ ] `src/music` で `Math.random()` と現在時刻を直接使っていないか。乱数がすべて記録に入った種から動く乱数（seed付きの擬似乱数）から取られているか
- [ ] 種がゲーム開始時に1つ作られて記録と共有URLに入り、同じ記録から必ず同じ曲になるか（AC4・AC5）
- [ ] 乱数で走り（道・速さ・操作）が曲に効く部分を変えていないか（乱数は脇役）

### データと記録の形式（7章）

- [ ] ステージのデータを `src/data` に置き、外部から取得していないか
- [ ] 共有URLの先頭に形式の版番号を入れているか。記録の詰め方・ステージのデータ・曲作りの規則を、同じ記録から違う曲になる形で変えたのに版番号を上げていない変更がないか
- [ ] 共有URLの圧縮に `CompressionStream`、WAV の組み立てに自前の処理を使い、追加のライブラリを入れていないか
- [ ] 実行時に読む画像・データを `.gitignore` に入れていないか（インフラ要件 I4）
- [ ] 版違いの扱い・URLの長さの上限（詳細設計で未決）を、決定前に既成事実として実装していないか（判断できなければ「要確認」）

### サーバーと秘密値を持たない・公開範囲（8章）

- [ ] サーバー側の処理・外部API・`fetch` での外部通信・鍵を持ち込んでいないか。共有の記録を `#` 以降以外（クエリ文字列・外部送信）に入れていないか
- [ ] `.env` を秘密値の置き場として使っていないか（`SERVER_PORT` だけ）。`import.meta.env` から秘密値を読む前提のコードがないか
- [ ] Vite の `base` が GitHub Pages のパス（`/stick-dance/`）に合っているか
- [ ] 生成元と規約確認の記録が無い画像を配信物に加えていないか（N3・AC6）
- [ ] 外部の音源ファイルを使っていないか（音はブラウザの中で合成する）

### 実装の共通ルール（9章）

- [ ] 互換レイヤー・フォールバック・「念のため」残した使われない関数・設定・ファイルがないか（共有URLの古い版の扱いは詳細設計の決定に従う）
- [ ] 現在の要件に対して過剰な抽象化・設定項目・間接化をしていないか（インターフェースは実装が複数必要になってから）
- [ ] 仮の数値（制限時間・速さとリズムの対応・休符を縮める長さ・音量など）を設定1か所に名前付きでまとめているか。処理の途中に数値を直書きしていないか
- [ ] 操作から音が鳴るまでの遅れ（N2）を試作で測れる形になっているか
- [ ] `tsconfig.json` の `strict` を緩めていないか。`any` と型アサーション（`as`）で型検査を黙らせていないか。ESLintの無効化コメントで違反を隠していないか
- [ ] 外から来るデータ（共有URLから読み戻した記録）を、受け取った場所で形を確かめてから使っているか
- [ ] Phaser 3 の API を Phaser 4 で使っていないか（4 の型定義で確かめる）
- [ ] 実装（`src/`・`index.html`）で外部CDNを参照していないか。ライブラリを npm の依存として入れているか
- [ ] 公開する関数・型に、役割が分かる日本語のコメントがあるか
- [ ] 変更したコードに対応する単体テスト（Vitest、`src/**/*.test.ts`）があるか。特に `src/core`・`src/music`・`src/share` の仕様をテストで固定しているか

## 出力形式

```text
### 指摘N: <一言サマリ>
- ファイル: <パス>:<行番号>
- 違反規約: アプリケーション実装方針 <章番号と要旨>
- 重要度: 要修正 | 推奨 | 要確認
- 内容: <問題と影響>
- 修正案: <具体的な修正方法>
```

- 指摘ゼロなら「**規約違反なし**」と明言する。
- 差分だけで断定できない事項は「要確認」とする。
- レビューのみを行い、依頼されていないコード修正はしない。
