# pr-review-resolution --- PRレビュー指摘への対応

`master` 向けプルリクエストに付いたレビュー指摘（AI・人とも）を、取りこぼさず仕分け、対応し、**全件に返信する**までの共通手順。

ルールの正本は [Git運用手順](../ドキュメント/基準書/Git運用手順.md)「⑥ レビューしてマージする」。ここには複製しない。本手順は、その⑥を確実に実行するための順序と停止条件を定める。

最優先するのは、指摘を1件も落とさないこと、**対応しない判断を人が決めること**、そして返信漏れのままマージへ進まないことである。

## 対象と対象外

- **対象**: `master` 向けPRのレビューコメント。自動レビュー（`codex-pr-reviewer`、[claude-pr-review.yml](../.github/workflows/claude-pr-review.yml)）と人のレビューの両方を含む。レビューコメントの本文を貼り付けられた場合も対象とする。
- **対象外**: 次は本手順では扱わず、行き先を伝えて停止する。
  - 有識者の紙面レビュー指摘・システムテストで見つけた不良 → [harness-resolution](harness-resolution.md)（レビュー指摘表・バグ表へ起票する別の流れ）
  - 顧客からの指摘・要望 → 人へ確認する（発注元が本人のためQA表は置かない）
  - 作業ブランチ → `dev/自分の名前` のPR（レビュー対象外。Git運用手順④）
  - **対応するかしないかの判断そのもの**。AIは案を出すだけで、決めるのは人（Git運用手順⑥）
- 本依頼と無関係な既存問題、生成物、ローカル環境固有ファイルは変更対象外とする。

## 起動方法

**この手順は自然文で起動する。** 決まった書式を人に覚えさせない。次のような依頼はすべてこの手順に当たる。

- 「PRのレビューを見て対応して」「レビューが返ってきました、修正して」
- 「#123のレビュー指摘に対応して」「PRのコメント直して」
- レビューコメントの本文（`[要修正]` などを含むもの）を貼り付けられたとき

PR番号が分からない場合は `gh pr list --state open` の結果を示して人に選ばせる。**推測で別のPRを触らない。**

## 実行手順

### 1. 指摘を全部集める

インラインコメントとPR全体へのコメントは別のAPIに分かれている。**両方見る。**

```powershell
gh pr view <PR番号> --json title,url,reviews,comments
gh api repos/kashiwagi505/stick-dance/pulls/<PR番号>/comments
```

- `Claude PR Review` のチェックが赤い場合は、レビューが途中で終了して結果が投稿されていない。**未実施のまま先へ進まない。** `@claude` で再レビューを依頼する（Git運用手順⑥）。
- 既に返信済みのスレッドと未返信のスレッドを分ける。

### 2. 1件ずつ表にして提示する

まとめて「対応しました」と書かない。指摘ごとに次を出す。

| 列 | 内容 |
|---|---|
| 指摘 | どのファイル・行への指摘か（インラインでなければ「PR全体」） |
| 要旨 | 指摘の内容を1〜2行で |
| 判断案 | `対応する` / `対応しない` / `要確認` と、その理由を1行 |

**先に日本語で要点を書く。** パスと行番号の羅列から始めない。

### 3. 対応するかどうかを人に決めてもらう

**AIが決めない。** 判断案は出すが、`対応しない` は人の承認を得るまで確定させない（Git運用手順⑥）。

`要確認` にしたものは、何が分かれば決まるのかを書く。

### 4. 対応する

- 修正は**作業ブランチ側**で行う。`master`・`dev/自分の名前` へ直接コミットしない（Git運用手順1章）。
- 本体ツリーにいる場合は `/worktree-start` で作業ツリーへ移ってから直す。
- コミットは**パス指定**で行う（`git commit -- <パス> -m "..."`）。
- 設計書・README・`.env.example` の連動更新は [ドキュメント/AGENTS.md](../ドキュメント/AGENTS.md) に従う。
- `npm run check` の成功を確認する。
- **アプリケーションのコード（`src/` の `*.test.ts` 以外と `index.html`）を変更した場合は、影響する画面のE2Eテストもあわせて実行し、全件成功を確認する。** 対象specの選び方と実行手順は [影響調査ルール](../ドキュメント/基準書/影響調査ルール.md) の「検証コマンド」を正本とする。設計書・コメント・テストコードだけの修正では不要。

### 5. 全件に返信する

**対応した／しないにかかわらず、指摘には必ずコメントを返す。** 対応した事実はAIが書いて投稿してよい。対応しない場合は、人が決めた理由をそのまま書く。

```powershell
gh api repos/kashiwagi505/stick-dance/pulls/<PR番号>/comments/<コメントID>/replies -f body="<返信>"
```

### 6. push して再レビューを依頼する

内容を足した場合は自動レビューの対象にならないため、PRコメントで `@claude` にメンションして再レビューを依頼する（Git運用手順⑥）。

### 7. マージ

マージは `/merge-pr` で行う。返信漏れとapproveを機械チェックする。**GitHubのマージボタンは使わない。**

## チェック項目と根拠

- [ ] インラインコメント（`pulls/comments`）とPR全体のコメント（`reviews`・`comments`）の**両方**を集めたか。片方だけ見ると指摘を落とす
- [ ] 未返信の指摘がゼロか。返信漏れマージを防ぐ砦は `/merge-pr` の機械チェックだけで、ブランチ保護は使えない（Git運用手順⑥）
- [ ] `対応しない` を人が決めたか。AIが握りつぶしていないか
- [ ] 修正が作業ブランチ側で行われているか（`master` 側でのコンフリクト解消・直コミットは禁止）
- [ ] 実装済み画面の見た目を変える修正なら、バグ表のバグIDへ紐付いているか（[02_バグ表](../ドキュメント/04_テスト/02_バグ表.md) 1章。実装完了後のUI変更はバグとして扱う）
- [ ] `npm run check` が通るか
- [ ] アプリケーションのコードを変更したなら、影響する画面のspecを回して全件成功したか。**修正が1画面で済んだつもりでも、共通の描画部品・共通CSS・文言定義・`src/core`・`src/music`・`src/share`・`src/audio`・`src/data` を触っていれば対象は1画面では終わらない**（[影響調査ルール](../ドキュメント/基準書/影響調査ルール.md)「検証コマンド」）

## 出力形式と終了条件

- 手順2の表と、手順3で人が決めた結果を提示する
- 対応した指摘・対応しない指摘・要確認の件数を明示する。**指摘ゼロの場合はゼロと明言する**
- 返信した件数と、未返信が残っている場合はその一覧
- 終了条件は「全件に返信済みで、`/merge-pr` を実行できる状態」。**未返信が残ったまま終了しない**
