# codex-pr-reviewer — PR自動レビュー観点

GitHub のプルリクエストを Codex が自動レビューするときに従う観点の正本。

このレビューで最優先するのは、**設計書間、設計書と実装、設計書とテストの不整合**の検出である。
個々の規約の詳細は既存の手順書・基準書を正本とし、この文書ではPRでの照合順序と判定ルールを定める。

## 対象

- PR の差分（ベースブランチと PR ブランチの三点差分。通常は `dev/<名前>` → `master`）に含まれるファイル。
- 差分と対応関係にある既存の要件、画面設計、詳細設計、実装、テスト。差分に現れていないファイルも、変更内容との不整合や更新漏れを判断するために読む。
- 指摘はPRの変更によって発生・顕在化した問題に限る。PRと無関係な既存問題は指摘しない。
- 生成物・ローカル環境固有ファイル（`node_modules/`、`dist/`、`e2e/evidence/`、`e2e/test-results/`、`e2e/playwright-report/`、`.env`）は対象外。ただしこれらがコミットされていること自体は「PR固有のチェック項目」で指摘する。

## 判定の原則

- 要件定義・基本設計・詳細設計などの**上流工程だけを先に追加・変更し、実装やテストを後続PRで行うことは許容する**。設計書だけが存在すること、または設計書の方が実装より先行していることだけを理由に指摘しない。
- 実装を追加・変更した場合は、対応する設計書とテストが同じ仕様を示している必要がある。実装だけが先行し、必要な設計書・テストが未更新であれば指摘する。
- 同じPRで複数の成果物を変更している場合は、変更された成果物同士の矛盾を指摘する。上流工程の先行を許容する場合でも、同じPR内の設計書同士の不整合は許容しない。
- 将来仕様として先行記載されたのか、実装済み仕様の更新漏れなのかを差分から断定できない場合は、違反と決めつけず「要確認」とする。
- 記載の詳しさや表現の好みではなく、利用者から見える振る舞い・聞こえる曲、踊り（物理）と音の決め方の規則、責務、エラー処理、テスト期待値に実質的な差があるものを優先する。
- 初期雛形として未策定の画面・詳細設計の文書がある。PRの対象機能に関係する箇所が未記載であれば指摘するが、無関係な未記載箇所は指摘しない（→ [ドキュメント構成.md](../ドキュメント/ドキュメント構成.md)）。
- 要件・実装方針で未決とされている事項（共有URLの版違いの扱い・長さの上限、記録の形式、E2Eでの時間・音・canvas の中身の扱い、再読み込みの扱い、画面の構成、仮の数値の置き場所など）を、PRが決定済みとして実装・記載している場合は「要確認」とする。

## 手順

1. **差分を読む**: PR の全差分を読み、変更の意図（どの機能・どの画面の対応か）を把握する。
2. **対応関係を作る**: 変更された機能・画面ごとに、要件、画面設計、詳細設計、実装、単体テスト、E2Eテストコードと画面単位のテスト観点表を対応付ける。対応が分からない場合は、そのこと自体を「要確認」とする。
   - 機能 → `ドキュメント/01_要件定義/01_機能要件.md`、`ドキュメント/03_詳細設計/処理設計/○○機能.md`、`src/core/**`・`src/music/**`・`src/share/**`・`src/audio/**`
   - 画面 → `ドキュメント/02_基本設計/01_画面一覧・遷移図.md`、`ドキュメント/02_基本設計/画面設計/SCRXX_○○画面.md`、同名モックアップ `ドキュメント/02_基本設計/モックアップ/SCRXX_○○画面.html`、`ドキュメント/02_基本設計/画面設計/デザインシステム/readme.md` と同フォルダ配下、`src/view/**`、`index.html`、`e2e/tests/scrXX-*.spec.ts`、`ドキュメント/04_テスト/テスト仕様書/SCRXX_○○画面テスト観点表.md`
   - 共有URL → 共有の処理設計（`ドキュメント/03_詳細設計/処理設計/`）、`ドキュメント/基準書/アプリケーション実装方針.md` 7章、`ドキュメント/02_基本設計/設計方針/技術選定の設計方針.md` 3.1、`src/share/**`
   - 音（楽器・伴奏・テンポ）→ `ドキュメント/02_基本設計/設計方針/音の設計方針.md`、`ドキュメント/素材/音の記録.md`、`src/music/**`・`src/audio/**`
   - 層の分け方・同じ入力から同じ結果・時刻 → `ドキュメント/02_基本設計/設計方針/技術選定の設計方針.md` 2・3章、`ドキュメント/基準書/アプリケーション実装方針.md` 2・6章
   - 配信・起動方法 → `ドキュメント/01_要件定義/03_インフラ要件.md`、`README.md`、`package.json`、`vite.config.ts`、`.github/workflows/`
   - 文言・操作キー → 機能要件または画面設計、`src/view/` の文言定義
3. **基準書を読む**: 変更内容に関係する箇所だけでなく、次の文書のチェック項目・責務分担・連動更新表を確認する。
   - [アプリケーション実装方針.md](../ドキュメント/基準書/アプリケーション実装方針.md)
   - [画面設計書ガイド・チェックリスト.md](../ドキュメント/基準書/画面設計書ガイド・チェックリスト.md)
   - [詳細設計書ガイド・チェックリスト.md](../ドキュメント/基準書/詳細設計書ガイド・チェックリスト.md)
   - [01_テスト方針.md](../ドキュメント/04_テスト/01_テスト方針.md)
   - [ドキュメント/AGENTS.md](../ドキュメント/AGENTS.md) の「連動して更新するもの」
   - 画面の見た目を変更している場合は、[デザインシステム/readme.md](../ドキュメント/02_基本設計/画面設計/デザインシステム/readme.md) と同フォルダ配下の該当規定を開く。
4. **整合性を照合する**: 下記「最優先のチェック項目」に従い、各成果物の内容を項目単位で突き合わせる。
5. **既存観点を適用する**: [impl-policy-reviewer.md](impl-policy-reviewer.md) の「チェック項目」と [doc-sync-checker.md](doc-sync-checker.md) の「チェックする連動ペア」を適用する。ただし、設計書側だけの先行更新は本書の「判定の原則」を優先し、実装漏れとして指摘しない。
6. **PR固有観点を確認する**: 下記「PR固有のチェック項目」を確認する。
7. **報告する**: 下記の出力形式でレビューコメントを投稿する。

## 最優先のチェック項目

### 設計書間の整合

- [ ] 機能ID、画面ID、画面の切り替え条件、共有URLの形式が、要件・画面一覧・画面設計・処理設計で一致しているか
- [ ] 踊りのルール（キーと引く体の部分・向き、分身になる条件、最大5人）、動きと音の対応（頭の高さ→音階の段、頭が動いた8分音符の拍だけ鳴る、楽器ごとの段の使い方）、ループの長さ・テンポ、表示項目、文言、正常時・異常時の動作が関連設計書間で一致しているか
- [ ] 画面設計書とモックアップが1対1で揃っており、内容が一致しているか。共通の見た目が確認時点の[デザインシステム](../ドキュメント/02_基本設計/画面設計/デザインシステム/readme.md)と矛盾していないか
- [ ] 処理設計書が要件・基本設計にない仕様を追加していないか。基本設計の再掲やコード全文でコード側の正本を二重化していないか
- [ ] 関連画面、層ごとの責務、例外処理の記載が各正本と矛盾していないか

### 設計書と実装の整合

- [ ] `src/view` の画面の切り替え・表示項目・操作・文言が、画面一覧・画面設計書・モックアップに一致しているか
- [ ] `src/core` の踊り（物理）・ループ・分身のルールと記録の項目（キー入力と楽器の選択だけ）が、機能要件（F1・F3・F4）・技術選定 3.1・処理設計書に一致しているか。仮の数値が設定1か所にまとまっているか（実装方針9章）
- [ ] `src/music` の音の決め方（頭の高さを A マイナーペンタトニックの11段に丸める、動いた拍だけ鳴る、楽器ごとの段の使い方）が、機能要件（F2・F5）・音の設計方針・処理設計書に一致しているか
- [ ] `src/share` の共有URLの形式（版番号・圧縮・`#` 以降）が、実装方針7章・技術選定 3.1・共有の処理設計に一致しているか。同じ記録から違う踊りや音になる変更で版番号を上げているか
- [ ] 利用者向け文言が `src/view/` の文言定義にまとめられ、設計書に書かれた文言と一致しているか
- [ ] 起動方法・配信（Vite の `base`、GitHub Actions での公開）を変更した場合、`README.md`・インフラ要件が揃っているか
- [ ] 実装された振る舞いに対応する設計書が更新されているか

### 設計書・実装とテストの整合

- [ ] `src/core`・`src/music`・`src/share` の振る舞いを変更した場合、対応する単体テスト（`src/**/*.test.ts`）が追加・更新されているか
- [ ] 時間に依存する振る舞い（物理の刻み・ループの位置・鳴る拍・分身になる周）のテストが、時刻とキー入力を引数で渡して確認しているか。同じ記録から同じ姿勢の列・同じ音の並びになることを確かめているか（実装方針6章・テスト方針3章）
- [ ] テストの入力、事前条件、期待値、失敗時の戻り値が、設計書と実装の仕様に一致しているか
- [ ] テストの意図がテスト名とコメントから読み取れるか（テスト内容を設計書側へ書き写していないか）
- [ ] 画面の表示・入力・操作・切り替えを実装変更した場合、対応する画面単位のE2Eテスト（`e2e/tests/`）とテスト観点表が追加・更新されているか
- [ ] テスト観点表・E2Eテストが、テスト方針5節の観点のうち該当するものを確認しているか
- [ ] 画面の切り替えの確認が切り替え元画面のテスト観点表・E2Eテストにあり、切り替え先の表示状態・引継ぎデータまで確認しているか（切り替え先の観点表に重複させていないか）
- [ ] E2Eテストが操作をキーボードから出し、音の聞こえ方を判定の対象にしていないか（テスト方針2-1・4-8）
- [ ] spec が `@playwright/test` を直接 import せず、`e2e/fixtures/test` から `test`・`expect` を取っているか
- [ ] テスト方針が対象としていないテストがないことだけを理由に指摘していないか。テスト方針2-1の明示的な除外対象を未確認として指摘していないか

## PR固有のチェック項目

上記でカバーされない、PRの単位でしか見えないものだけを挙げる。

- [ ] テストが「通ること」ではなく「仕様どおりであること」を確認しているか（アサーションのない・自明なだけのテストは指摘する）
- [ ] PR が `dev/<名前>` → `master` になっているか（`master` から `master` 以外へ向けていないか、原本リポジトリへ向けていないか。→ [Git運用手順](../ドキュメント/基準書/Git運用手順.md)）
- [ ] PR の説明に「対応する設計書を更新した」「`npm run check` が通ることを確認した」が示されているか
- [ ] デザインシステム（`ドキュメント/02_基本設計/画面設計/デザインシステム/`）を変更したPRでは、説明に変更した節・影響成果物が記載されているか。記載内容とPRの差分が一致しているかを照合する
- [ ] PR に無関係な変更が混ざっていないか（別機能の修正、大量のフォーマット変更、生成物・ローカル設定のコミット）
- [ ] `.env`、`node_modules/`、`dist/`、`e2e/evidence/` など、`.gitignore` 対象のファイルがコミットされていないか
- [ ] サーバー・外部API・鍵を持ち込む変更になっていないか（実装方針8章）。出所と権利確認の記録が無い素材（絵・音）をコミットしていないか（N7・AC5）
- [ ] 文言定義、仮の数値の設定、素材の記録・クレジットなどの全員が触る共通ファイルへの追記が、他の変更の行を消していないか（マージ事故の検出）
- [ ] 記録から踊りと音を作る関数や共通の描画部品・共通CSSで、マージ時に他の変更の追加分が失われていないか
- [ ] 共通CSS・共通の描画部品の変更が、意図した画面以外へ影響していないか
- [ ] 実装済み画面（対応するE2E specが `e2e/tests/` に既存）の `src/view` の描画・CSSの見た目を変更しているPRで、PR本文またはコミットメッセージがバグ表のバグID（`BUG-XXX`）またはレビュー指摘表の指摘ID（`REV-XXX`）へ紐付いているか（実装完了後のUI変更はバグとして管理する。→ [02_バグ表](../ドキュメント/04_テスト/02_バグ表.md) 1章。紐付きが無ければ「要確認」として起票漏れを確認する）

## 出力形式

レビューコメントのタイトル・本文・サマリは、すべて日本語で記述する。
コード、識別子、ファイル名、コマンド、GitHub の固定表記は原文のままでよい。

指摘ごとに、該当行への**行コメント**として次の形式で書く。

```
**[要修正|推奨|要確認]** <一言サマリ>

- 根拠: <規約名と章番号、または設計書のファイル名と該当箇所>
- 内容: <何が問題か>
- 修正案: <どう直すか。コード例は最小限>
```

重要度の定義は impl-policy-reviewer と揃える。

| 重要度 | 意味 |
|---|---|
| **要修正** | 実装方針・設計書に明確に違反している。マージ前に直す |
| **推奨** | 違反とまでは言えないが、方針の意図から外れている・改善が望ましい |
| **要確認** | 差分だけでは断定できない。作成者に判断を委ねる |

- サマリコメントの冒頭に、**要修正／推奨／要確認の件数**を書く。
- サマリには、確認した対応関係（設計書間／設計と実装／設計・実装とテスト）と、上流工程のみの先行として許容したものがあればその旨を簡潔に書く。
- 指摘がゼロの場合は「**指摘なし（設計書間・設計と実装・設計とテストの整合を確認）**」と明言する。無言で終わらない。
- **コードは修正しない**。修正は PR 作成者が行う（`@codex fix ...` で明示的に依頼された場合を除く）。
- 設計書を正本とする運用のため、指摘は「なぜそう直すのか」が分かるように書く。規約名・文書名を挙げるだけで終わらせない。
- 好みの範囲の書き換え（命名の言い換え、等価なリファクタリング）は指摘しない。ノイズになる。
