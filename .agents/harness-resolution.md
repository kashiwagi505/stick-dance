# harness-resolution --- レビュー指摘・不良対応

有識者の紙面レビュー指摘と、システムテストで発見した不良について、顧客提出用の2表への起票、影響調査、修正、検証、コミット、プルリクエスト作成までをAIが連続して行う共通手順。人間の承認はプルリクエストのレビューで受ける。

最優先するのは、要件・設計・実装・テストの修正漏れを防ぐこと、調査と判断の証跡を失わないこと、そして人間がPRの段階で変更内容を全て検証できる状態にすることである。影響調査の分類、順序、チャット出力形式は`ドキュメント/基準書/影響調査ルール.md`を正本とする。案件ごとの管理ファイルは作成しない。

## 対象と対象外

- 有識者が紙面で行ったレビューの指摘。`ドキュメント/管理表/レビュー指摘表.md`の3章へ`REV-nnn`形式（3章の最大番号＋1）で起票する。採番規則と番号が重なったときの振り直しは`ドキュメント/管理表/AGENTS.md`が正本。
- 開発者がシステムテストで発見した不良。`BUG-001`形式の連番で、`ドキュメント/04_テスト/02_バグ表.md` 3章の表に1件1行で記録する（記入ルールは同2章）。起票は番号を付けずに `バグ/未採番/` へ1ファイル置き、採番と表への転記は master 上の `/bug-sync` と毎朝の Actions が行う。
- 複数件をまとめて受け取った場合も、1件ずつに分解して起票し、対応をID単位で管理する。
- 顧客から受けたレビュー指摘は対象外とし、本手順を停止して人間へ確認する（発注元が本人のためQA表は置かない）。
- AIレビューとPRレビューの指摘は対象外とし、[pr-review-resolution](pr-review-resolution.md) で扱う。
- 本依頼と無関係な既存問題、生成物、ローカル環境固有ファイルは変更対象外とする。

## 起動方法

この手順は、依頼プロンプトの1行目が`レビュー指摘`または`バグ`であることをトリガーとする。AIは自動委譲に依存せず、次のいずれかで確実に起動する。

- 人間が`レビュー指摘`／`バグ`で始まるプロンプトを送る。メインセッションはルート`AGENTS.md`の表からこの手順を特定し、全文を読んでから着手する。
- 人間が明示的に`harness-resolution`を指定する。
- 自動委譲された場合も、本ファイルと`ドキュメント/基準書/影響調査ルール.md`を全文読んでから着手する。要約や記憶で進めない。

1行目が`レビュー指摘`／`バグ`のいずれでもない場合は、起票せず人間へ確認する。`レビュー指摘`で始まる場合も、`種別`を確認するまで起票しない。

## 人間からの依頼プロンプト

人間は次の形式で依頼する。ここに書かれていない情報（ID、検出日、検出工程、混入工程、原因、密度計上、影響範囲）は、AIが調査して補う。

### レビュー指摘の場合

```text
レビュー指摘
種別: <有識者紙面レビューまたは顧客レビュー>
対象: <指摘を受けた文書のパスまたは名称>
内容: <指摘された内容。期待する状態がわかるように書く>
```

- `種別`が`有識者紙面レビュー`の場合だけ、レビュー指摘表へ起票して本手順を続行する。
- `種別`が`顧客レビュー`の場合は起票せず、停止して人間へ確認する（発注元が本人のためQA表は置かない）。
- `種別`がない、または上記のどちらかに判定できない場合は、推測せず人間へ確認する。
- `指摘者`は`ドキュメント/管理表/レビュー指摘表.md`の「固定値で記入する項目」に定められた値を使う。記入例や過去行から推定しない。依頼プロンプトに別の氏名が明記されている場合だけそれに従う。対象表に固定値の定めがなく依頼にも氏名がない場合は、起票せず`確認待ち`として停止する。
- `指摘日`は依頼日とする。
- `重要度`（要修正／要検討／提案）は、AIが対象表の判断基準に照らして案を決め、起票時に記入する。人間が指定した場合はそれに従う。
- `要検討`と判定した場合は、`未対応`として起票した時点で停止する。影響調査・修正には進まず、人間が「対応」または「見送り」を決めた後に再開する。
- スクリーンショット、該当箇所の引用は任意で添える。

### バグ表へ起票する場合

```text
バグ
対象: <画面IDまたは機能名>
期待結果: <本来どうなるべきか>
実際の結果: <実際に何が起きたか>
```

- 再現手順は入力しない。システムテストは観点表どおりに実施するため、AIが`対象`の画面IDから`ドキュメント/04_テスト/テスト仕様書/`の該当テスト観点表を読み、手順を特定する。観点表から該当ケースを一意に絞れない場合だけ、テストケースIDを人間へ確認する。観点表にない操作で発見した不良の場合は、人間が`実際の結果`に操作内容を含めて書く。
- `検出者`は依頼者、`検出日`は依頼日、`検出工程`は`結合テスト（人間）`として記入する（人が画面を見て気づいた不良のため。バグ表1章）。
- `重要度`（致命的／重大／中／軽微）、`混入工程`、`原因`、`密度計上`は、AIが調査結果に基づいて記入する。
- ログ、スクリーンショット、テストケースIDは任意で添える。

### 複数件をまとめて依頼する場合

上記のブロックを空行で区切って並べる。AIは1件ずつに分解して順に処理する。

## 人間確認と再開

- サブエージェントの実行中に人間の確認が必要になった場合は、推測で続行せず、`確認待ち`としてメインセッションへ停止報告を返す。`確認待ち`はチャット上の一時停止であり、対象表の状態列には記入しない。停止報告は`ドキュメント/基準書/影響調査ルール.md`の定型に従い、`停止理由`を`人間への確認待ち`として`確認事項`と`再開地点`を記入する。起票前で対象IDがない場合は`停止したID`を`なし（起票前）`とし、対象と内容を併記する。
- 人間の回答後は、新しいサブエージェントを起動せず、同じエージェントまたはセッションを再開する。再開時は対象表、停止報告、`git status --short`、`git diff`を確認し、重複起票せず再開地点から処理を続ける。
- 同じ実行コンテキストを再開できない場合は、別エージェントへ暗黙に引き継がず、再開に必要な情報を報告して人間の判断を待つ。

## 実行手順

### 1. 実行前の前提確認

1. ルートの`AGENTS.md`、`ドキュメント/基準書/影響調査ルール.md`、目的・決定事項・未解決事項に相当する文書を読む。
2. この手順、影響調査ルール、対象表、要件・設計・実装・テスト資料の実在パスを確認する。
3. 対象表、ID体系、状態値、標準の検証コマンド、作業ブランチ、PRのベースブランチを特定する。
4. 必須資料や標準コマンドが見つからない場合は推測せず、欠けているものを人間へ提示して停止する。
5. プロジェクトごとの継続チャットを1つ使い、案件ごとにバッチIDと対象IDを付けて区切る。

### 2. 判定の原則

- AIは入力種別を判定し、選択した表の見出し・記入規則・直近の記入例を確認する。依頼プロンプトの必須項目が欠けている場合だけ、人間へ追加確認する。
- 起票時だけは入力の種類で分岐する。有識者紙面レビューはレビュー指摘表、システムテスト不良はバグ表へ起票する。顧客レビューは停止して人間へ確認し、種別を判定できない場合は起票前に人間へ確認する。
- 分岐後は対象表の見出し、記入規則、直近の記入例を必ず読む。2表に共通する項目名を仮定しない。
- ID、検出日、検出者、再現手順、重要度は、その表に存在する既存項目の範囲で補う。検出者の取得規則は既存のプロジェクト方針に従い、変更しない。
- 入力や既存文書から断定できない内容は、事実として埋めず`要確認`とする。
- 顧客提出用の2表には影響調査用の列・項目を追加しない。
- `要検討`以外は、**起票から修正、検証、コミット、PR作成までを、人間の事前承認を待たずに連続して実行する。** 人間の承認はPRのレビューで受ける。AIはPRをマージしない。
- `要検討`は`未対応`として起票した時点で停止し、対応方針を人間へ確認する。GitHub Issueは起票しない。人間が「対応」と判断した場合は`未対応`の行から再開し、影響調査後に`対応中`へ進める。「見送り」と判断した場合は、AIが`対応不要`へ変更せず、人間による状態と理由の記録を待つ。
- 状態は`未対応` → `対応中` → （レビュー指摘表は`対応済`、バグ表は`修正済`） → `確認済`の順とする。AIは`確認済`へ変更しない。表ごとの正式な状態名は対象表の記入規則を必ず確認する。
- `未対応`は起票直後、`対応中`はAIが影響調査を終えて修正に着手した状態とする。
- レビュー指摘表の`対応済`とバグ表の`修正済`は、修正・検証を終えて修正内容をコミットし、そのコミットハッシュを対象表へ記録した状態とする。PR作成成功は状態の条件ではなく、本手順全体の完了条件とする。
- レビュー指摘表の`確認済`は元の指摘者、バグ表の`確認済`は再テスト実施者が設定する。PRレビュアーのapproveは変更内容への承認であり、対象表の`確認済`とは別に扱う。AIは`確認済`へ変更しない。
- 修正しないと判断すべき案件（指摘が誤り、仕様どおりで不良でない等）については、AIは`対応不要`／`取り下げ`へ変更せず、`未対応`のまま理由と根拠をチャットへ報告して停止する。この判断は人間が行う。

### 3. 起票・採番・重複確認

1. 入力を1件ずつに分解し、有識者紙面レビュー、顧客レビュー、システムテスト不良のいずれかを判定する。顧客レビューは停止して人間へ確認する。
2. 判定した対象表の見出し、記入規則、直近の記入例を読む。
3. 起票前に対象表の全行を検索し、同一または類似案件がないか確認する。検索する列は表ごとに異なる。レビュー指摘表は`対象`と`指摘内容`、バグ表は`対象`と`事象`を見る。2表に共通の列名を仮定しない。同一または類似案件がある場合は新規起票せず、人間へ確認する。
4. 対象表の見出し・記入規則からID形式を確認する。形式が不明な場合は推測せず停止する。**レビュー指摘表は起票直前に表を再読み込みし、3章の最大番号＋1で採番する。バグ表は起票時に採番しない**（各ブランチで通し番号を採ると並行ブランチと取り合い、マージ時に採番のやり直しになる。実績: 2026-09-01・09-02・09-04・09-07・09-09）。
   - **バグ表への起票は `/bug-new` で行う。** 番号を付けず、バグ1件のファイル `ドキュメント/04_テスト/バグ/未採番/<担当者ローマ字>-<YYYYMMDD>-<HHmmss>.md` を作業ブランチに1つ足してコミットするコマンド。手順の正本は `.claude/commands/bug-new.md`。`/bug-new` を使えない環境でも同じ名前・書式でファイルを作り、その旨を報告する。`BUG-nnn` は master に入ったあと `/bug-sync`（kashiwagiだけが実行）と毎朝9時の GitHub Actions が付ける。手で `BUG-nnn` を付けない。起票でバグ表3章の表へ行を足さない（転記は `/bug-sync` の役割）。
   - バグの`対応内容`・`修正コミット`・`状態`などの更新は、作業ブランチで、採番前なら `バグ/未採番/…md` を、採番後ならバグ表3章の該当行を編集する。以下で「バグ表を更新する」とあるのは、この更新を指す。番号が付く前の修正では、コミットメッセージや報告に未採番の名前を使い、採番後は表の行の `修正コミット` 列で紐付ける。
   - レビュー指摘表は `/bug-new` の対象外。`ドキュメント/管理表/AGENTS.md` の採番手順に従い、表へ直接 `REV-nnn` で起票する。並行ブランチと番号が重なった場合は、後から取り込む側が最大番号＋1へ振り直し、`備考` に旧IDを残す。**起票前の重複確認（`対象`・`指摘内容`の検索）は表の全行に対して行う**（同じ指摘を二重に起票しないため）。
5. 同一表への起票は同時に行わず、1件ずつ処理する。既存項目だけで`未対応`として起票する。レビュー指摘表は`レビュー種別`を`設計レビュー`、`レビュー観点`を`有識者紙面レビュー`とし、対象に応じた`区分`を記入する。`PR`・`対応内容`・`修正コミット`・`確認日`・`確認者`は、起票時点で値がなければ空欄とする。バグ表は`混入工程`・`密度計上`・`修正コミット`のうち判明している範囲だけ埋め、調査後でないと分からない項目は空欄とする。
6. 起票後に表を再読み込みし、ID重複、意図しない変更、採番形式の不一致がないことを確認する。
7. 異常があれば修正作業を開始せず、状態と差分をチャットへ報告して停止する。
8. レビュー指摘の重要度が`要検討`の場合は、異常がなくても`未対応`のまま停止する。GitHub Issueは起票せず、人間へ「対応」または「見送り」の判断を求め、回答後に同じ実行コンテキストで再開する。

### 4. 影響調査

`ドキュメント/基準書/影響調査ルール.md`に従い、最初に`機能単位`、`横断`、`両方`、`要確認`のいずれかへ分類する。複数条件に該当する場合は`両方`とする。

- 機能単位：1機能固有の要件・画面・処理・テストだけに閉じる。
- 横断：共通部品、共通CSS、文言定義、仮の数値の設定、曲を作る関数（`src/music`）、共有URLの形式、ステージのデータ、非機能、インフラ（配信・GitHub Pages）、テスト方針、開発基準に関係する。
- 両方：機能固有と横断の双方に関係する。
- 要確認：下記の代替経路をたどっても対象を特定できない、または分類できない。

機能単位では、機能要件、画面一覧、画面設計、処理設計、テスト観点表の順に、**実在するものだけを**必要な箇所だけ読む。機能ID、画面ID、画面名、ステージ名、関数名・型名を検索語として実装とテストを調べる。横断では対象の基準書と、実在する`AGENTS.md`の連動更新規則を起点にする。

**設計書が存在しないことだけを理由に`要確認`として停止しない。** 設計書は工程の進行に応じて順次作成されるため、次のとおり扱う。詳細は`ドキュメント/基準書/影響調査ルール.md`の「設計書が未整備な場合の代替経路」を正本とする。

- ファイルが存在しない、または表が見出し行だけで中身が空の場合は、その段を飛ばす。飛ばした文書名と理由を着手報告の「参照できなかった文書」に必ず記載する。
- 設計書から対象を特定できない場合は、`要確認`とする前に次の順で特定を試みる。
  1. テスト観点表（`ドキュメント/04_テスト/テスト仕様書/SCRxx_*.md`）
  2. E2Eテスト（`e2e/tests/`、`e2e/helpers/`）
  3. 実装（`src/view` のシーンと文言定義、`src/core`・`src/music`・`src/share`・`src/audio` のモジュール名、`src/data` のステージのデータ）
- 代替経路で特定できた場合は、その根拠（ファイルパスと該当箇所）を着手報告に記載して修正へ進む。
- 3つの経路をすべてたどっても特定できない場合だけ`要確認`とし、修正へ進まず、たどった経路と見つからなかった内容をチャットへ提示して停止する。
- 対象の設計書が存在しないまま実装を修正した場合、設計書を新規作成するかどうかは本手順では判断しない。未解決事項としてPR本文とチャットに記載する。

### 5. 修正

1. 影響調査ルールの定型で、影響調査ルート、確認範囲、変更予定、検証方法をチャットの今回のバッチ欄へ提示する。これは着手報告であり、承認を待たない。
2. 状態を変更する前に、作業ブランチが`dev/<自分の名前>`、ベースブランチが`master`であることを確認する。`git status --short`を記録してこれを開始時ベースラインとし、着手報告に含める。修正対象ファイルと競合する未コミット変更がある場合だけ停止する。対象と無関係な未コミット・未追跡ファイルは、そのまま残して作業を続ける。ブランチが判定できない場合は停止する。
3. 対象行を`対応中`へ変更する。
4. 影響調査で特定した範囲だけを修正する。`ドキュメント/AGENTS.md`の「連動して更新するもの」に該当する変更は、同じ修正で設計書・テストまで揃える。コミットは対象ファイルだけを明示的にステージし、開始時ベースラインにあった変更を巻き込まない。
5. 次のいずれかに該当する変更が必要になった場合は、修正を中断し、内容と理由をチャットへ提示して人間の判断を待つ。
   - 層の分け方・読んでよい層の変更（アプリケーション実装方針2章）、または共有URLの形式（版番号）の変更（同7章）
   - サーバー・外部API・秘密値を持ち込む変更、公開範囲・配信の変更（同8章）
   - 要件定義そのものの変更
   - 影響が5ファイルを大きく超え、当初の影響調査結果と食い違う場合
6. 影響調査を終えても原因を特定できず、修正方針を決められない場合は、推測で修正に着手しない。調べた範囲、絞り込めた原因の候補、それぞれを確定できない理由をチャットへ提示して停止する。

### 6. 検証・自己修正

- ルート`AGENTS.md`に定められた標準コマンド（`npm run check`）を実行する。
- **アプリケーションのコード（`src/` の `*.test.ts` 以外と `index.html`）を変更した場合は、影響ありと判定した画面のE2Eテストもあわせて実行し、全件成功を確認する。** 対象specの選び方、実行手順、全件（`npm run e2e`）を要求しない理由は`ドキュメント/基準書/影響調査ルール.md`の「検証コマンド」を正本とする。設計書・管理表だけの修正では不要。
- E2EテストはPlaywrightがアプリ（`npm run dev`）を自分で起動する。DBを使わないため、データの初期化・復元は無い。他の作業ツリーでもアプリを起動している場合は`.env`の`SERVER_PORT`が重なっていないことを確認する。
- 標準コマンドが実行できない、または対象変更に別の検証が必要と判断した場合は、推測で実行せず人間へ確認する。
- 対象機能の再現手順、関連テスト、画面変更時のスクリーンショット、実際の`git diff`を確認する。
- 検証コマンドが成功しても、依頼された期待結果を満たしていない場合は成功として扱わない。再現手順をたどり、指摘・不良が実際に解消したことを確認する。解消していない場合は自己修正の対象とする。
- 検証に失敗した場合は、原因を`仕様`、`実装`、`データ`、`環境`、`テスト`に分類し、影響調査で特定した範囲内で修正して再検証する。**この自己修正は最大2回までとする。**
- 2回の自己修正でも検証が通らない場合、または検証環境・資料不足で進められない場合は、そこで停止する。PRは作成せず、対象表は`対応中`に留め、チャットへ次を報告する。
  - 失敗した検証コマンドと出力の該当箇所
  - 2回の試行それぞれで何を変更し、なぜ失敗したか
  - 原因分類（`仕様`／`実装`／`データ`／`環境`／`テスト`）と、そう判断した根拠
  - 現在の作業ツリーの状態（変更を残したか、戻したか）
  - 次に必要な人間の判断

### 7. 完了処理

- 全検証成功後、次の順序で修正、管理表、PRを対応付ける。PR作成はGit運用手順②〜④に従い、`/create-pr`スキルが利用できる場合はmaster取り込み・push・PR作成に使う。詳細は`ドキュメント/基準書/影響調査ルール.md`の「PR作成の手順」を正本とする。
  1. 作業ブランチが`dev/<自分の名前>`であることを確認し、修正・設計・テストの変更をコミットする（修正コミット）。`master`へ直接コミット・pushしない。
  2. 対象表の`対応内容`、`修正コミット`、必要な原因・集計項目を更新し、レビュー指摘表は`対応済`、バグ表は`修正済`へ変更して、管理表更新を別コミットにする。
  3. `master`の最新を自分のブランチへ取り込み、`npm run check`を再実行してからpushし、`dev/<自分の名前>` → `master`のPRを作成する。
  4. レビュー指摘表を更新した場合は、作成したPR番号を`PR`へ記入して別コミットにし、`npm run check`を再実行して同じPRへpushする。バグ表だけを更新した場合はこの手順を省略する。
  5. PRの最終差分に修正コミット、管理表の状態・修正コミット、レビュー指摘表のPR番号が含まれ、作業ツリーに開始時ベースライン以外の未コミット差分がないことを確認する。
  6. PR説明にはGit運用手順で必須とされている「対応する設計書を更新した」「`npm run check`が通ることを確認した」の2点を必ず含める。
- 1バッチにつきPRは1つとする。個人ブランチは1人1本の固定運用のため、バッチ内の複数IDを1つのPRにまとめ、PR本文には対応IDごとに節を設ける。
- レビュー指摘表を`対応済`へ更新するときは、`対応内容`と`修正コミット`を記入する。`PR`はPR作成後の最終メタデータ更新で記入する。
- バグ表を`修正済`へ更新するときは、`修正コミット`に修正コミットのハッシュを、`密度計上`に`○`（アプリケーションのコード（`src/` の `*.test.ts` 以外と `index.html`）を変更した場合）または`—`（アプリケーションのコードを変更していないすべての場合。要件・設計・テスト設計・テストコード・テストデータ・環境設定だけの修正、仕様どおりでの取り下げを含む）を、`混入工程`に判明した工程を記入する。
- PR本文には対応ID、バッチID、変更内容、最終影響範囲、調査根拠、実行コマンドと環境、検証証拠、未解決事項、プロジェクトの継続チャット識別子を記載する。バグ表を更新した場合は、`混入工程`と`密度計上`をその値にした判断根拠も書く。これらは不良密度の集計元であり、レビュー担当者が検証できる必要があるため。
- **AIはPRをマージしない。** PRレビュアーは変更内容を確認してapproveする。レビュー指摘表の`確認済`は元の指摘者、バグ表の`確認済`は再テスト実施者が設定する。
- PR作成に失敗した場合、修正コミットと管理表更新は残し、対象表の状態を戻さない。PRが未作成であること、レビュー指摘表の`PR`が空欄であること、再開地点を停止報告へ記載する。

## チェック項目と根拠

- [ ] 依頼プロンプトの必須項目がそろっている
- [ ] 起票先と対象表の既存項目を確認した
- [ ] `指摘者`は対象表の固定値、または依頼で明示された氏名を使った（推定していない）
- [ ] 重複確認、ID形式確認、起票後の差分確認を行った
- [ ] `要検討`の場合は`未対応`として起票後に停止し、人間が対応方針を決めるまで影響調査・修正へ進んでいない
- [ ] 影響調査ルートと選択理由を提示した
- [ ] 確認ファイル、該当箇所、検索語、根拠、未確認事項を提示した
- [ ] 参照できなかった文書と、代わりにたどった代替経路を着手報告に記載した
- [ ] 連動して更新すべき設計書・テストを同じ修正に含めた
- [ ] 状態を`対応中`にする前に、作業ブランチと開始時ベースラインを確認した
- [ ] コミットに開始時ベースラインの対象外ファイルが含まれていない
- [ ] 人間確認で停止した場合、状態・質問・変更状況・再開地点を報告し、同じ実行コンテキストで再開した
- [ ] リポジトリで定義された検証コマンドと対象機能の再現確認を実行した
- [ ] アプリケーションのコード（`src/` の `*.test.ts` 以外と `index.html`）を変更した場合、影響ありと判定した画面のspecを回して全件成功を確認した（実行しなかった場合は理由を記載した）
- [ ] 自己修正は2回以内に収まっている
- [ ] `git diff`に影響調査結果にない変更がない
- [ ] PR作成前に`master`を取り込み直し、`npm run check`を再実行した
- [ ] PR説明にGit運用手順の必須2項目（設計書の更新、`npm run check`の通過）を含めた
- [ ] 修正コミットのハッシュと該当の状態（レビュー指摘表は`対応済`、バグ表は`修正済`）を管理表更新コミットに含めた
- [ ] レビュー指摘表を更新した場合、PR番号の追記を同じPRへpushし、PRの最終差分と作業ツリーを確認した
- [ ] PR本文に、人間がレビューで判断するために必要な影響範囲・調査根拠・検証証拠・未解決事項がある

## 出力形式と終了条件

- チャットでの着手報告、完了報告、停止報告の形式は`ドキュメント/基準書/影響調査ルール.md`の「チャットで提示する着手報告の形式」「完了報告とPR」を正本とする。
- 終了条件は、全検証成功後に修正コミットと管理表更新コミットを作成し、PR作成と必要なPR番号追記を同じPRへ反映し、作業ツリーに未コミット差分がないことを確認して、PRのレビュー待ちを人間へ報告した時点とする。
- 次のいずれかに該当する場合は完了とせず停止し、状態・原因・証拠・実施済みと未実施の変更・次に必要な人間の判断をチャットの今回のバッチ欄へ報告する。
  - 人間への確認事項があり、回答待ちとなった場合
  - レビュー指摘を`要検討`と判定し、対応または見送りの判断待ちとなった場合
  - 起票先を判定できない、重複の疑いがある、ID形式が不明な場合
  - 起票後の差分確認で異常が見つかった場合
  - 影響調査ルートが`要確認`となった場合
  - 原因を特定できず、修正方針を決められない場合
  - 修正が「5. 修正」の中断条件に該当した場合
  - 自己修正2回でも検証が通らない、または期待結果を満たせない場合
  - PR作成に失敗した場合
  - 修正すべきでないと判断した場合（`対応不要`／`取り下げ`の判断は人間が行う）
