# WBS/ 配下の編集ルール

`WBS/` はタスク管理だけを置く。作業別の入口はルートの [AGENTS.md](../AGENTS.md)、
Git操作は [Git運用手順](../ドキュメント/基準書/Git運用手順.md)、設計資料は
[ドキュメント/AGENTS.md](../ドキュメント/AGENTS.md) が正本。ここに重複させない。

## スコープ

- `WBS/タスク/` に **1タスク＝1ファイル**。複数タスクを1ファイルにまとめない。
- 要件・設計・テスト・開発基準は `ドキュメント/` が正本。共通外観は `ドキュメント/02_基本設計/画面設計/デザインシステム/` を正本とする。**`WBS/` に写しを作らない。**
  タスクから参照するときは `../../ドキュメント/...` の相対リンクを張る。

### 退避資料

- `WBS/退避資料/` は、納品前に `WBS/` とともにリポジトリから削除する、仕様の正本ではない検討経緯資料だけを一時保管する例外とする。要件・設計・テスト・開発基準をここへ新規作成したり、納品対象の文書からここへリンクしたりしない。
- 納品対象外にした機能追加シートは `WBS/退避資料/機能追加/` に1機能1ファイルで置く。仕様として必要な内容は、移動前に `ドキュメント/` の正本へ反映する。

### 検討

- `WBS/検討/` は、設計を決めるために見た目を並べて比較した検討用HTMLを置く。納品前に `WBS/` とともに削除する仕様の正本ではない資料という扱いは `退避資料/` と同じで、**納品対象の文書からここへリンクしない。** 画面設計書と1対1で対応するモックアップは `ドキュメント/02_基本設計/モックアップ/` が正本。
- CSS・JS・画像は複製せず、`../../ドキュメント/02_基本設計/モックアップ/` の実体を相対パスで参照する。何をどう検討したかは [検討/README.md](検討/README.md) を正本とする。

## タスクのプロパティ

**この7つだけ。増やさない。** 管理項目を増やすと、埋めること自体が仕事になる。

```yaml
owner: yamada        # 担当1人。個人ブランチ名（dev/<owner>）と同じ文字列
status: 未着手          # 未着手 / 対応中 / 完了 の3つだけ
start: 2026-08-18       # 着手予定日。ガントの棒の左端になる
due: 2026-08-20         # 期日。ガントの棒の右端になる
estimate: 6             # 見積(h)
actual: 0               # 実績(h)
category: 3_要件定義    # 下の9工程のどれか。頭の番号ごと書く
```

### `category` に入れる値（この9つだけ）

工程表の8区分に `9_改善` を足したもの。**頭の番号ごと入力する**（一覧が工程順に並ぶため）。

| 値 | 含む作業 |
| --- | --- |
| `1_プロジェクト管理` | 進捗管理、報告、課題・リスク管理、顧客調整 |
| `2_AI管理` | 憲章・規約の整備、エージェント設定、利用状況の記録 |
| `3_要件定義` | 要件の洗い出しとスコープ確定 |
| `4_基本設計` | アーキテクチャ・データ・API・画面の設計 |
| `5_詳細設計・実装・テスト` | タスク分解、実装、単体テスト、レビューと手戻り |
| `6_結合テスト観点` | 結合時の確認観点とテストデータの整理 |
| `7_インフラ連携` | 環境構築、CI/CD、外部システム接続 |
| `8_システムテスト＋検収` | 結合・システムテスト実施、不具合対応、検収 |
| `9_改善` | 既存の成果物・進め方の改善（リファクタリング、手順・ドキュメント・ツールの改善、KPTのTry対応） |

`start` が空だと、ガントで棒が描けず期日の点だけになる。**必ず入れる。**
1日で終わるタスクは `start` と `due` を同じ日にする。

ファイル名がタスク名になる。IDは振らない。

### マイルストーン

**ファイル名の頭を `【MS】` にする**とマイルストーン扱いになる（プロパティは増やさない）。

- `estimate` は `0`。**作業ではなく判定ポイント**だから
- `start` と `due` は同じ日にする
- 本文は「この日までに揃っていること」のチェックリストにする
- ガントでは◆と黄色い破線、ダッシュボードでは専用の表に出る
- 各種タスク一覧からは自動で除外される（件数や工数を汚さないため）

## 守ること

1. **他人が `owner` のタスクの `status` / `actual` を書き換えない。**
   代理入力を頼まれたときだけ可。その場合はメモ欄に誰の申告か書く。
2. **実績工数を推測で埋めない。** 聞いていない工数は `0` のままにして、未記入だと伝える。
3. `status` を `完了` にするときは `actual` も必ず埋める。空のまま完了にしない。
4. `master` に手で直接コミットしない。コード変更に伴うタスク更新はそのPRに同梱する。
   WBSだけを先に反映したいときは `/wbs-push` を使う
   （`WBS/` 配下限定でmasterへ直接反映できる。正本は [Git運用手順](../ドキュメント/基準書/Git運用手順.md) の「PRを経ない反映の例外」）。

## タスクを起票するとき

1. `WBS/タスク/` を検索して重複がないか確認する。
2. 担当・開始日・期日・見積のどれかが分からなければ**聞く**。勝手に決めない。
   ただし「◯日まで」だけ言われた場合、`start` は見積時間から妥当な日を提案してよい。
3. [テンプレート/タスク.md](テンプレート/タスク.md) の書式でファイルを作る。ファイル名がタスク名になる。
4. 「やること・終わったと言える条件」を最低1つ具体的に書く。空のまま作らない。
5. その担当者のその期間の見積合計が1日7hを超えるなら警告する。
6. 実装・設計に関わるタスクなら、`ドキュメント/` 側の**着手前に読む正本**への相対リンクを
   メモ欄に張る。どれを読むべきかはルート [AGENTS.md](../AGENTS.md) の表で引く。
