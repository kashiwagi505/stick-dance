# タスク管理・運用手順

タスクを1件1ファイルで置くだけの仕組み。**この1枚を読めば運用できます。**
AIに作業させるときのルールは [AGENTS.md](AGENTS.md)。

```
WBS/
├── ダッシュボード.md   ← 全員でここを見る
├── テンプレート/       ← タスクの雛形
└── タスク/            ← 1タスク1ファイル。ここに増やす
```

---

## 1. 最初の1回だけ（セットアップ）

**vaultは `stick-dance` フォルダを開く。** `WBS/` ではなく親を開くこと。
そうしないと `ドキュメント/` の設計書へのリンクが切れます。

1. 設定 → コミュニティプラグイン → **制限モードをOFF**
2. 「閲覧」→ `Dataview` を検索 → インストール → 有効化
3. 設定 → **Dataview** → **Enable JavaScript Queries を ON**（ガントの描画に必要）

`.obsidian/` はGitで共有しているので、テンプレートの場所も `Alt+T` の割り当ても設定済みです。

## 2. 1日の流れ

| いつ | やること |
| --- | --- |
| 朝 | `master` を自分のブランチに取り込む → [ダッシュボード.md](ダッシュボード.md) を見る → 朝会（下記） |
| 着手時 | タスクを開いて `status` を `対応中` に。関連ドキュメントを読んでから始める |
| 作業中 | 詰まったらメモ欄に書いてチームに共有する。抱え込まない |
| 完了時 | DoDを全部チェック → `actual` を書く → `status` を `完了` に |
| 夕方 | タスクの `status`・`actual` を反映してから夕会（下記） |
| PR時 | コード変更に伴うタスク更新は**同じPRに混ぜて**出す |
| WBSだけ反映したいとき | `/wbs-push` でmasterへ直接反映する（PR不要。`WBS/` 配下限定） |

### 朝会（15分・時間厳守）

**目的: 今日の計画を全員で確認し、詰まりを早く外に出す場。** 個人の作業報告会にしない。

[ダッシュボード.md](ダッシュボード.md) の上のカード3枚（遅れ／全体の進み／次のマイルストーン）を映しながら進める。

| 順番 | 話すこと | 目安 |
| --- | --- | --- |
| 1 | kashiwagiがマイルストーンとの差分を共有（カード3枚を見るだけ） | 1分 |
| 2 | 各自、今日やることの確認 | 3分 × 人数 |
| 3 | 不明点の洗い出し | 残り時間 |

- 不明点は**その場で3分で決着しなければ課題管理表（GitHub Issue）へ**。議論で15分を溢れさせない
- 解消できる不明点は当事者間で朝会後に話す。全員を巻き込まない

### 夕会（30分）

**目的: 進捗と学びを共有し、今日の前進を確認して終える場。**

| 順番  | 話すこと                                  |
| --- | ------------------------------------- |
| 1   | 今日の進捗（`status`・`actual` を反映した状態で）     |
| 2   | 新たに出た疑問・アイデア・不安点                      |
| 3   | 今日自分が頑張ったこと・個人的に良かったこと（1人1つ、小さな前進でよい） |

- 「頑張ったこと」には**全員で拍手**し、kashiwagiがコメントを返す。**kashiwagiの分は他のメンバーが返す**
- コメントは能力ではなく**工夫・プロセスに向ける**（「すごい」より「その調べ方が良かった」）
- **10日に一回、夕会の後半15分をKPTふりかえりに置き換える。** 「思っていたのと違ったこと」も出してよい。Tryには AIワークフロー（プロンプト・スキル・手順書）の改善を毎回1つ含める
- **金曜の夕会では、未解決の課題（GitHub Issue）の棚卸を追加でやる。** 放置Issueを作らない

### チーム目標

朝会・夕会は、この3つの達成度を毎日検査する場でもある。

| 目標   | 何を保つか                                        | どこで検査するか       |
| ---- | -------------------------------------------- | -------------- |
| 進捗   | 次のマイルストーン判定を**「間に合う」に保つ**                    | 朝会のカード3枚（毎日）   |
| 品質   | **担当ドキュメントに各自が責任を持ち、チームとしてすべてのドキュメントに責任を持つ** | PR時の連動更新＋金曜の棚卸 |
| メンタル | **詰まり・不安を1人で抱えた時間ゼロ**（1日以上1人で悩んでいた件数 = 0）    | 金曜の棚卸＋KPT      |

- 進捗: 「間に合わない」と判断したら当日まで粘らず、**前日までに計画（マイルストーン）を変更する**。
  静かに落とすのが一番悪い
- 品質: 自分の担当分はコード・決定事項と乖離させない（[連動して更新するもの](../ドキュメント/AGENTS.md)）。
  他人の担当でも乖離に気づいたら**黙って直さず指摘する**。それが「全員で責任を持つ」の意味
- メンタル: 出た詰まりを責めない。**1日以内に出たことを歓迎する**

### チームの約束

- 詰まりは1人で抱え込まない。**1日悩んだら必ず出す**（メモ欄・朝会・Issue どこでもよい）
- 「わからない」と言えたことを歓迎する。全員が新人前提、聞くことはコストではなく貢献
- AIの出力は鵜呑みにしない。**自分の仮説を立ててから聞く。** コードの正しさはテストとドキュメントで担保する

## 3. タスクを追加する

### いちばん速い方法

リポジトリのルートで Claude Code を起動して、日本語で雑に書くだけ。

```
/wbs-new ステージ画面に残り時間の表示を追加。kashiwagi、10/27まで、6hくらい
```

裏でこれだけやります。

- `タスク/` を検索して**同じタスクが無いか確認**
- 工程（`category`）を9区分から判定
- `start` を見積時間から逆算して提案
- **その人のその期間の見積合計が7h/日を超えないかチェック**
- `ドキュメント/` から**着手前に読むべき正本を探してリンクを貼る**

担当・期日・見積が抜けていれば聞き返してきます。

### Obsidianだけで作る場合

1. 左のファイル一覧で **`タスク` フォルダを右クリック → 「新規ノート」**
2. タスク名を入力して Enter（**ファイル名がそのままタスク名**になります）
3. **本文をクリックしてカーソルを置く** ← ここを飛ばすと失敗します
4. **`Alt+T`** を押して `タスク` を選ぶ
5. プロパティ欄を埋める

> ⚠️ **`Alt+T` は「今開いているノートに貼り付ける」だけの機能です。**
> 新しいノートは作ってくれません。ダッシュボードなど別のノートを開いた状態で押すと、
> **そのノートにテンプレートが流し込まれて壊れます**（フロントマターまで合体されます）。
> 必ず「新規ノートを作ってから押す」の順番で。
>
> 間違えて入れてしまったら `Ctrl+Z` で戻せます。

> `owner` と `category` は**必ず入力候補から選んでください**。手打ちすると表記ゆれで
> 集計から漏れます。

### タスクの粒度

**1タスク = 1人が1〜3日で終わる大きさ**を目安に。

- 大きすぎる例: 「曲作り機能を作る」→ 何日経っても `対応中` のままになる
- 小さすぎる例: 「ボタンの色を変える」→ 起票の手間が作業より大きい

迷ったら**「終わったと言えるかどうかを他人が判定できるか」**で切ってください。

## 4. タスクを進める

### 着手するとき

1. **ブランチを確認する。** VSCode左下が `dev/自分の名前` になっているか。`master` なら切り替える
2. `status` を `対応中` にする（プロパティ欄の値をクリックして入力）
3. **メモ欄の「関連ドキュメント」を先に読む。** これを飛ばして書き始めると、
   実装方針や設計書と食い違って手戻りします

### 作業中

- 詰まったら**メモ欄に「何で詰まっているか」を書いて共有する**。1人で半日以上悩まない
- 想定外の作業が出てきたら、そのタスクに押し込まず `/wbs-new` で別タスクを立てる
  （押し込むと見積と実績の比較が意味を失います）

### 完了するとき

この4つが揃って初めて `完了` です。

- [ ] **DoD（やること・終わったと言える条件）のチェックが全部付いている**
- [ ] `actual` に実際かかった時間を書いた
- [ ] コードを変えたなら、対応する設計書も更新した
      （[ドキュメント/AGENTS.md](../ドキュメント/AGENTS.md) の「連動して更新するもの」）
- [ ] `npm run check` が通る

そのうえで `status` を `完了` にします。

> **見積と実績がずれたら、メモ欄に理由を一行残してください。**
> 「3hの見積が8hかかった。既存の曲作りの処理を読むのに時間を使った」で十分です。
> これが溜まると次の見積が当たるようになります。**そのために `actual` を書いています。**

### まとめて反映したいとき

手で直すのが面倒なら、話し言葉で伝えれば直してくれます。

```
/wbs-close 旋律の生成を3時間やって半分くらい。あとタイトル画面の修正が1時間で完了
```

## 5. タスクの中身（プロパティ7つ）

| 項目 | 書くこと |
| --- | --- |
| `owner` | 担当者**1人**（`kashiwagi` など、個人ブランチ名と同じ文字列） |
| `status` | `未着手` → `対応中` → `完了` の**3つだけ**。他の値は入れない |
| `start` | 着手予定日。ガントの棒の**左端** |
| `due` | 期日。ガントの棒の**右端** |
| `estimate` | 見積の時間（h）。**着手前に書いて、後から書き換えない** |
| `actual` | 実際にかかった時間（h） |
| `category` | 工程。下の9つから選ぶ（番号ごと入力） |

`owner` は共同作業でも**主担当を1人**決めます。「みんなの仕事」は誰の仕事でもなくなるので。

### 区分（工程）の9つ

| 値 | 含む作業 |
| --- | --- |
| `1_プロジェクト管理` | 進捗管理、報告、課題・リスク管理、顧客調整 |
| `2_AI管理` | 憲章・規約の整備、エージェント設定、利用状況の記録 |
| `3_要件定義` | 要件の洗い出しとスコープ確定 |
| `4_基本設計` | アーキテクチャ・データ・API・画面の設計 |
| `5_詳細設計・実装・テスト` | タスク分解、実装、単体テスト、レビューと手戻り |
| `6_結合テスト観点` | 結合時の確認観点とテストデータの整理 |
| `7_インフラ連携` | 環境構築、CI/CD、外部システム接続 |
| `8_システムテスト＋検収` | 結合・システムテスト実施、不具合対応、検収 |
| `9_改善` | 既存の成果物・進め方の改善（リファクタリング、手順・ドキュメント・ツールの改善、KPTのTry対応） |

頭の番号は工程表の番号です。付けておくとガントや一覧が工程順に並びます。

## 6. ダッシュボードの見方

### 上の3枚のカード

朝会はここだけ見れば済みます。

| カード | 何が分かるか |
| --- | --- |
| **遅れ** | 期日を過ぎているのに終わっていないタスクの**見積合計（時間）**。「3件遅れ」より「8時間ぶん遅れ」の方が判断できるので時間で出しています |
| **全体の進み** | 見積ベースの消化率。完了タスクの見積合計 ÷ 全体の見積合計 |
| **次のマイルストーン** | `間に合う` / `ぎりぎり` / `間に合わない` の判定 |

判定は **残り営業日 × 1人 × 7h**（＝使える時間）と、そのマイルストーンまでに
終わらせる必要があるタスクの見積合計（＝必要な時間）を比べています。

> **会議・手戻り・レビューの時間は「使える時間」に含まれていません。**
> だから `ぎりぎり` が出た時点で、実際にはもう危ないと思ってください。

メンバー数が変わったら、ダッシュボードの `const MEMBERS = 1;` を直してください。

### マイルストーン

**ファイル名の頭を `【MS】` にするだけ**でマイルストーンになります。プロパティは増えません。

- `estimate` は `0`（作業ではなく判定ポイントなので）
- `start` と `due` は同じ日
- 本文は「この日までに揃っていること」のチェックリスト

ガントでは◆と**黄色い破線**で表示され、破線より左にあるタスクが
「そのマイルストーンまでに終わらせるもの」だと一目で分かります。
遅延・対応中・未着手などの表からは自動で除外されるので、件数や工数を汚しません。

### ガントの「工程別 / 担当別」切り替え

ガントの上のボタンで見方を変えられます。

| ボタン | 並び方 | いつ使うか |
| --- | --- | --- |
| **工程別** | マイルストーン → 工程1〜9の順 | **全体が予定どおり進んでいるか**を見る |
| **担当別** | マイルストーン → 担当者ごと | **誰が何をやっているか / 誰が詰まっているか**を見る |

2列目の表示も切り替わります（工程別なら担当名、担当別なら工程名）。
下の「👥 担当ごとのタスク」の表も同じ情報を一覧で見られます。

### ガントの色

棒の色は**3つが手入力、2つは自動判定**です。

| 色 | 意味 | 決まり方 |
| --- | --- | --- |
| 🟣 紫 | 未着手 | `status` で指定 |
| 🔵 青 | 対応中 | `status` で指定 |
| ⚪ 灰 | 完了 | `status` で指定 |
| 🔴 赤 | **期日超過** | **自動**（`due` < 今日 かつ 未完了） |
| 🟠 橙 | **値が不正** | **自動**（打ち間違いの検出） |

**「期日超過」は `status` に入力する値ではありません。** 期日が過ぎたら勝手に赤くなります。

日付の目盛りは1日単位。土日は薄く網掛けされます。
1日の幅を変えたいときは、ダッシュボードの `const DAY_W = 26;` の数字を変えてください。

### 個人別 × 日別の時間

**「誰のどの日が詰まっているか」**を見る表です。行が担当、列が日付、セットがその日の時間になります。

| ボタン | 何が出るか |
| --- | --- |
| **見積 / 実績** | `estimate` を割ったもの（予定）／ `actual` を割ったもの（実績の傾向） |
| **今週 / 4週間 / 全期間** | 表示する日付の範囲。既定は今週の月曜から4週間 |

セルの数字は、**各タスクの時間を `start`〜`due` の営業日（土日を除く）に均等割り**した概算です。

> **日ごとの工数は入力していません。** プロパティは7つのままなので、
> 「その日に実際に何時間やったか」ではなく「その日ぶんとして割り当てられている時間」です。
> 実績側も `actual` を同じ割り方で割っただけなので、**1日単位の実績としては使えません**（傾向を見るだけ）。

| 色 | 意味 |
| --- | --- |
| 🟡 黄 | 1日 **5h超** |
| 🔴 赤 | 1日 **7h超**＝入れすぎ。期日をずらす・担当を替える・タスクを割るのどれかを決める |

セルにマウスを乗せると、その日の内訳（タスク名と時間）が出ます。
右端が担当ごとの合計、最下段が日ごとの合計（チーム全体）です。
基準を変えたいときは、ダッシュボードの `const CAP = 7;`（赤）と `const WARN = 5;`（黄）を直してください。

## 7. 困ったとき

| 症状 | 原因と対処 |
| --- | --- |
| 表もガントもコードのまま表示される | Dataviewが未導入。「1. セットアップ」を実施 |
| **表は出るがガントだけ出ない** | Dataview設定の **Enable JavaScript Queries が OFF**。ONにする |
| `status` の候補に `対応中` が出ない | **vault内でまだ1件も使われていないだけ。** 1回手で打てば以降ずっと候補に出る |
| 期日を過ぎているのに赤くならない | `due` が本当に今日より前か確認。当日はまだ超過ではない |
| タスクがダッシュボードに出てこない | `status` か `category` の打ち間違い。「⚠️ 値がおかしいもの」の表に出ているはず |
| プロパティ欄が表示されない | 設定 → エディタ → 「プロパティ表示」を **「表示」** に |
| プロパティを直接編集したい | `Ctrl+E` でソースモードにすると `---` の中が生で見える |
| **`Alt+T` を押したのに何も起きない／変な所に入る** | Alt+T は**今開いているノートに貼り付ける**機能。新規ノートを作り、**本文にカーソルを置いてから**押す。間違えたら `Ctrl+Z` |
| 関係ないノートにテンプレートが混入した | `Ctrl+Z` で戻す。気づかず保存したら、増えたプロパティと `## やること` `## メモ` を手で消す |

## 8. Git

[Git運用手順](../ドキュメント/基準書/Git運用手順.md) が正本。要点だけ。

- `master` に手で直接pushしない。自分の `dev/名前` ブランチで作業する
- `rebase` は使わない。取り込みは merge
- コード変更に伴うタスク更新は**そのPRに混ぜて出す**（タスクだけのPRは作らない）
- WBSだけを先に共有したいときは **`/wbs-push`** を使う（`WBS/` 配下限定でmasterへ直接反映。夕会前の反映に便利）
- 他人が `owner` のタスクは書き換えない。1タスク1ファイルなので、
  これを守る限りコンフリクトはほぼ起きません
